# Единый канон нумерации функций F1–F4 и качество целей vision.md

**Date:** 2026-08-29
**Files:** specs/vision.md, specs/open-questions.md, src/README.md, specs/adr/README.md, specs/domain/README.md, specs/adr/ADR-DES.API.hybrid-graphrag-composition.md, specs/qa/README.md, specs/qa/gates.md, specs/qa/test-plan.md, specs/qa/e2e-api-testing.md, specs/qa/e2e-gui-testing.md, specs/qa/integration.md, specs/qa/unit-testing.md, specs/qa/smoke-testing.md
**Severity:** critical (трассируемость требований)

## Problem

Рассинхронизация нумерации функций: `specs/vision.md` (источник правды по RULES.md) определял продуктовые функции **F1–F4**, а `src/README.md`, `specs/adr/README.md`, `specs/domain/README.md` и все документы `specs/qa/` использовали **F1–F7** с другим смыслом (индексация, онтологический слой, ответы, трассируемость, накопление знаний, context compiler, контур LLM). Один и тот же код `F3` означал «ответы с grounding» в тест-плане и «вычисление влияния» в vision. Нарушен гейт `G1-TRACE` — цепочка «vision → UC → FR → тест» не строилась.

Дополнительно (по `/aif-verify`, Wiegers & Beatty): цели G1–G7 без приоритетов; TBD-метрики без срока закрытия; неоперационализированные метрики G3/G4 и критерий F3; сквозные NFR без идентификаторов.

## Root Cause

Схема F1–F7 возникла в QA/ADR/domain-артефактах как «расширенная таксономия» (функции + механизмы + вне-рамок), но использовала те же коды, что и продуктовый канон vision.md, без явного решения о единой нумерации. Схема F1–F7 также противоречила scope vision.md: F5 «накопление знаний» — вне рамок (§2.7 п.4–5), F7 «контур LLM» — сквозное требование, F2 «онтологический слой» — механизм. Отсутствие зафиксированного канона позволило документам разойтись.

## Solution

1. **Установлен канон:** функции продукта — только **F1–F4** из `specs/vision.md` §2.1–2.2 (F1 генерация проверяемых ответов, F2 индексация источников знаний, F3 оптимизация контекста для автоматической разработки, F4 доставка через MCP). Механизмы (онтологический слой, контур LLM) и сквозные требования (`NFR-*`) F-кодов не получают.
2. **Маппинг старой схемы** зафиксирован в `specs/open-questions.md` Q1.1 (F1→F2, F2→механизм, F3→F1, F4→F3, F5→вне рамок, F6→F4, F7→NFR-SEC-1).
3. **Все 14 артефактов приведены к канону:** таблицы модулей, scenario ID (`F1-01…F4-07`, `ONT-*`, `SEC-*`), разделы специфики по функциям, матрицы трассируемости, каскады событий; вне-рамок функциональность (сигналы с полей, петля обучения) удалена из тест-планов.
4. **Качество целей vision.md:** приоритеты G1–G7 (P0/P1/P2), сроки закрытия TBD, операционализация метрик G3/G4/F3, ID сквозных требований (NFR-SEC-1, NFR-PERF-1, NFR-ACC-1, NFR-PROC-1, NFR-MOD-1, NFR-IMPL-1).

## Prevention

- **Единый канон нумерации функций — из vision.md §2.1–2.2;** новые артефакты (ADR, тест-планы, DDD, src) ссылаются на F1–F4; механизмы и NFR кодируются отдельно (`ONT-*`, `SEC-*`, `NFR-*`).
- При ревью требований/документации проверять: F-код существует в vision.md (гейт `G1-TRACE`); вне-рамок функциональность не тестируется (vision §2.7).
- При изменении канона — обновлять маппинг в `open-questions.md` Q1.1 и прогонять grep-верификацию `F5|F6|F7|F1–F7` по `specs/` и `src/`.
