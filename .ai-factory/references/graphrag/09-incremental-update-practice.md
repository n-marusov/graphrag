# Инкрементальное обновление индекса GraphRAG: практика и ориентиры

> **Источник:** результаты веб-поиска владельца продукта (2026-08-30) — описания архитектур и бенчмарков инкрементальных обновлений графовых RAG-индексов; атрибуция по пунктам TBD (URL источников не зафиксированы в сводке)
> **Создано:** 2026-08-30
> **Назначение:** обоснование достижимости целей `REQ-NFR-data.performance.index-freshness` (медиана ≤ 5 мин, p90 ≤ 15 мин) и проектные входные данные для `ADR-IMPL.DATA.incremental-update-snapshot-publish`

## Обзор

Готовых измеренных цифр пилота `index-freshness` для проекта не существует — существующие материалы описывают архитектурные решения и теоретические обоснования инкрементальных обновлений, а не конкретные замеры. При этом техническая реализуемость инкрементального обновления графовых индексов в экосистеме подтверждается, и есть архитектурные ориентиры.

## Подтверждённые подходы

1. **Обнаружение изменений** — два механизма:
   - потоковые события в реальном времени (например, OS-события файловой системы, webhook) — заявленная латентность обработки изменений **менее секунды**;
   - периодический опрос (polling) с настраиваемым интервалом — **резервный механизм, по умолчанию часто ~5 минут**.
2. **Избирательное («хирургическое») обновление** — пересчёт только затронутых сущностей и связей вместо полной перестройки.
3. **Кэширование и хеширование результатов LLM-вызовов** — при добавлении нового файла уже проиндексированные файлы не пересчитываются; изменение в одном документе затрагивает только изменившиеся чанки.

## Ориентиры производительности

- Субсекундная задержка обработки изменений при событийном (event-driven) подходе.
- Сравнительная точка (из другого контекста, **не экстраполируется напрямую**): при инкрементальном обновлении средний p90 для корпуса разработки (486 документов) составил ~15 минут.

## Критическое замечание

Даже при инкрементальном подходе добавление нового контента может изменить **структуру сообществ** графа настолько, что потребуется пересчёт большей части индекса. Это подтверждает допущение A7 `vision.md` (§2.8): периодическая фоновая полная перестройка необходима, инкрементальное обновление не заменяет её полностью.

## Применение в продукте

- Цели актуальности (медиана ≤ 5 мин, p90 ≤ 15 мин) остаются в силе; подтверждаются **целевым пилотным замером** (Фаза 1.5), а не внешними цифрами.
- Параметры пилота: корпус ~1k артефактов из реальных MR; 10–20 событий с 1–50 изменёнными документами; замер «событие → публикация»; фиксация выбросов (крупные MR); при необходимости — механизм отложенной публикации (`REQ-NFR-data.performance.index-freshness`).
- Архитектурные входные данные: событийный триггер + polling-фолбэк (~5 мин); избирательный пересчёт затронутого подграфа; кэширование LLM-извлечений по хешам; санкционированная фоновая полная перестройка для санации структуры сообществ.
