# Проектирование экспертной системы на базе GraphRAG

> **Создано:** 2026-08-29
> **На основе:** Анализ 97 статей, 2 обзоров, foundational paper Microsoft Research, 14+ open-source реализаций

---

## 1. Что такое «экспертная система на базе GraphRAG»

В контексте текущего состояния технологий, **экспертная система на базе GraphRAG** — это система, которая:

1. **Индексирует** доменный корпус документов в виде графа знаний (сущности + связи + утверждения)
2. **Организует** знания иерархически (сообщества, тематические кластеры)
3. **Отвечает** на сложные аналитические запросы, требующие глобального понимания корпуса и multi-hop reasoning
4. **Объясняет** свои выводы через прослеживаемые reasoning paths и атрибуцию источников
5. **Обновляется** инкрементально при поступлении новых документов

## 2. Ключевые проектные решения

### 2.1. Стратегия построения графа (Graph Construction)

| Подход | Плюсы | Минусы | Когда использовать |
|--------|-------|--------|-------------------|
| **LLM-based extraction** (GraphRAG, LightRAG) | Богатая семантика, извлечение неявных отношений | Дорого (токены), медленно, галлюцинации | Требуется глубокое понимание домена |
| **Statistics-based** (AGRAG) | Нет галлюцинаций, быстро, дёшево | Менее выразительные отношения | Большие корпуса, фактологические задачи |
| **Relation-free** (LinearRAG) | Линейное масштабирование, стабильно | Нет явных отношений между сущностями | Очень большие корпуса |
| **Hybrid: LLM skeleton + lightweight graph** (KET-RAG) | Баланс качества и стоимости | Сложнее архитектура | Оптимально для production |
| **Ontology-guided** (OG-RAG) | Точная доменная структура, однократное обучение онтологии | Требует экспертной онтологии | Узкие профессиональные домены |
| **RL-optimized** (AutoGraph-R1) | Граф, оптимизированный под конкретную задачу | Сложный training pipeline | Когда качество критично |

**Рекомендация для экспертной системы:** Начать с гибридного подхода (KET-RAG): LLM строит skeleton графа для ключевых чанков, остальные индексируются через легковесный bipartite graph. Это даёт ~10x экономию токенов при сопоставимом качестве.

### 2.2. Стратегия детекции сообществ

| Алгоритм | Характеристика | Реализация |
|----------|---------------|------------|
| **Leiden** (Traag et al., 2019) | Гарантированно связные сообщества, быстрее Louvain | `graspologic`, `leidenalg` |
| **Louvain** (Blondel et al., 2008) | Классический, хорошо изучен | `networkx`, `community` |
| **Dually-perceived** (Youtu-GraphRAG) | Структурная топология + семантика подграфов | Кастомная |
| **LLM-based hierarchical clustering** (ArchRAG) | LLM выполняет кластеризацию на основе атрибутов | Кастомная |

**Рекомендация:** Leiden как базовый выбор. Для доменов с богатой семантикой — рассмотреть LLM-based или dually-perceived кластеризацию.

### 2.3. Стратегия retrieval

| Режим | Что ищет | Когда применять |
|-------|---------|-----------------|
| **Local (Vector)** | Конкретные чанки, релевантные запросу | Фактологические запросы, lookup |
| **Global (Communities)** | Суммаризации сообществ → map-reduce | Sensemaking, аналитические обзоры, «каковы основные темы?» |
| **Dual-level** (LightRAG) | Low-level (сущности) + High-level (темы) | Смешанные запросы |
| **Agentic** (GraphSearch, ToG, GeAR) | LLM-агент итеративно обходит граф | Multi-hop reasoning, сложная логика |
| **Hybrid** (GraphSearch, HybGRAG) | Семантический поиск по тексту + реляционный по графу | Когда нужна полнота |
| **Adaptive** (E²GraphRAG) | Автоматический выбор local/global в зависимости от запроса | Production с разнородными запросами |

**Рекомендация:** Adaptive retrieval (как E²GraphRAG) с тремя уровнями: local (BM25 + embedding), structural (KG query), global (community map-reduce). Это покрывает фактологические, реляционные и аналитические запросы.

### 2.4. Стратегия инкрементального обновления

Критично для экспертных систем, работающих с растущим корпусом.

| Подход | Реализация |
|--------|------------|
| **Полная перестройка** | Надёжно, но дорого |
| **Incremental update** (LightRAG) | Обновление только затронутых частей графа |
| **Real-time KG** (Graphiti) | Непрерывное обновление KG для AI agents |

**Рекомендация:** Инкрементальное обновление с периодической полной перестройкой (например, еженедельно).

## 3. Архитектурные решения для экспертной системы

### 3.1. Рекомендуемая high-level архитектура

```
┌────────────────────────────────────────────────────┐
│                  Ingest Pipeline                     │
│  Documents → Chunking → Entity/Relation Extraction  │
│            → Graph Construction → Community Detect   │
└──────────────────────┬─────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────┐
│                Knowledge Index                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │
│  │Entity KG │  │Community │  │Vector Index      │  │
│  │(Neo4j/   │  │Summaries │  │(pgvector/        │  │
│  │FalkorDB) │  │(JSON/DB) │  │Qdrant/Milvus)    │  │
│  └──────────┘  └──────────┘  └──────────────────┘  │
└──────────────────────┬─────────────────────────────┘
                       ▼
┌────────────────────────────────────────────────────┐
│               Query Engine                           │
│  ┌──────────────────────────────────────────────┐  │
│  │          Adaptive Router                      │  │
│  │  (LLM определяет тип запроса → стратегия)    │  │
│  └───────┬──────────┬──────────┬────────────────┘  │
│          ▼          ▼          ▼                    │
│    ┌─────────┐ ┌─────────┐ ┌──────────┐            │
│    │ Local   │ │Structural│ │ Global   │            │
│    │Retrieval│ │Retrieval│ │Retrieval │            │
│    └────┬────┘ └────┬────┘ └────┬─────┘            │
│         └───────────┼───────────┘                   │
│                     ▼                               │
│         ┌──────────────────────┐                    │
│         │   Response Generator │                    │
│         │   (LLM + контекст)   │                    │
│         └──────────────────────┘                    │
└────────────────────────────────────────────────────┘
```

### 3.2. Выбор технологического стека

| Компонент | Рекомендация | Альтернативы |
|-----------|-------------|--------------|
| **LLM** | GPT-4o / Claude Sonnet для качества; Llama-3.1-8B/Llama-3.1-70B для降低成本 | DeepSeek-V3, Qwen-2.5 |
| **Graph DB** | Neo4j (зрелый, Cypher, графовые алгоритмы) | FalkorDB, Kuzu (embedded) |
| **Vector DB** | pgvector (встроен в Postgres) | Qdrant, Milvus |
| **Embeddings** | text-embedding-3-large (OpenAI) или mxbai-embed-large (open-source) | BGE-M3, E5 |
| **Graph Library** | NetworkX + graspologic | igraph, cuGraph (GPU) |
| **Orchestration** | LangChain / LlamaIndex (быстрый старт) | Кастомный pipeline (гибкость) |
| **API Framework** | FastAPI (Python) | Fastify (Node.js), Axum (Rust) |

### 3.3. Стратегия chunking

| Размер чанка | Плюсы | Минусы |
|-------------|-------|--------|
| **Малый (256-512 токенов)** | Высокий recall сущностей | Много LLM-вызовов → дорого |
| **Средний (600-1200 токенов)** | Баланс (используется в MS GraphRAG) | Может терять контекст |
| **Большой (2000+ токенов)** | Дешевле, больше контекста | Деградация recall на ранней информации в чанке |

**Рекомендация:** 600-800 токенов с перекрытием 100 токенов + sliding window для длинных документов.

## 4. Стратегия оценки качества

### 4.1. Метрики

| Метрика | Для каких запросов |
|---------|-------------------|
| **Comprehensiveness** (полнота) | Глобальные / sensemaking |
| **Diversity** (разнообразие) | Глобальные / sensemaking |
| **Empowerment** (практическая полезность) | Экспертные / аналитические |
| **Factual Accuracy** (фактическая точность) | Фактологические |
| **Faithfulness** (верность источнику) | Все типы |
| **Attribution** (атрибуция) | Все типы |
| **Latency** (задержка) | Production метрика |
| **Token Cost** (стоимость токенов) | Бюджетная метрика |

### 4.2. Методология оценки

1. **Автоматическая:** LLM-as-a-judge (head-to-head сравнение) + Claimify (извлечение утверждений → comprehensiveness/diversity через кластеризацию)
2. **Бенчмарки:** GraphRAG-Bench (2025) — наиболее полный специализированный бенчмарк; MultiHop-RAG — для multi-hop reasoning
3. **Экспертная:** доменные эксперты оценивают ответы по критериям
4. **A/B тестирование:** сравнение с baseline (Vector RAG) и альтернативными конфигурациями

### 4.3. Рекомендуемый набор тестов

```
1. Factual QA (10-20 вопросов): "Когда произошло X?" "Кто открыл Y?"
2. Multi-hop QA (10-20 вопросов): "Как открытие X повлияло на развитие Y?"
3. Comparative QA (10 вопросов): "Сравните подходы A и B к проблеме Z"
4. Global sensemaking (5-10 вопросов): "Каковы основные темы/тренды в корпусе?"
5. Contradictory check: "Есть ли противоречия в документах по теме X?"
```

## 5. Типичные проблемы и их решения

| Проблема | Причина | Решение |
|----------|---------|---------|
| **Галлюцинации LLM при extraction** | LLM выдумывает несуществующие сущности/связи | Statistics-based extraction (AGRAG), stricter prompting, human-in-the-loop |
| **Избыточность retrieved информации** | Слишком много retrieved контекста | Flow-based pruning (PathRAG), relevance scoring, PCST (G-Retriever) |
| **Подавление внутреннего reasoning LLM** | Слишком сильная опора на внешний KG | Logits-based selection (GraphRAG-FI), баланс internal/external |
| **Шум в графе** | Некачественное entity resolution, дубликаты | Deduplication + entity resolution (exact/soft matching), двухэтапная фильтрация (GraphRAG-FI) |
| **Дорогая индексация** | LLM extraction для каждого чанка | KET-RAG (skeleton + lightweight), LinearRAG (без отношений), статистические методы |
| **Несоответствие структуры графа запросу** | Pre-built граф не подходит под конкретный тип запроса | LogicRAG (inference-time DAG), StructRAG (динамическая структуризация) |
| **Деградация на фактологических запросах** | GraphRAG оптимизирован под глобальные запросы | Hybrid RAG (Vector + Graph), adaptive routing |
| **Slow retrieval** | Полный обход графа, большие подграфы | Индексы, кэширование, sparse matrices (MixPR), early termination |

## 6. План внедрения (Roadmap)

### Фаза 1: MVP (2-4 недели)
- Выбрать домен корпуса (100-1000 документов)
- Реализовать базовый GraphRAG pipeline (microsoft/graphrag или nano-graphrag)
- Настроить chunking и extraction prompts под домен
- Базовая оценка на 50 вопросах

### Фаза 2: Оптимизация (4-8 недель)
- Внедрить гибридный retrieval (Vector + Graph)
- Добавить adaptive routing (local vs global)
- Оптимизировать стоимость индексации (KET-RAG подход)
- Инкрементальное обновление
- A/B тестирование против Vector RAG baseline

### Фаза 3: Экспертная система (8-16 недель)
- Доменная онтология (если применимо)
- Multi-hop reasoning с agentic retrieval (GraphSearch, ToG)
- Explainability: reasoning paths + source attribution
- Пользовательский интерфейс (чат + графовая визуализация)
- Production deployment

## 7. Ключевые рекомендации (Summary)

1. **Начните с готового:** Microsoft GraphRAG или LightRAG как стартовая точка; не изобретайте pipeline с нуля
2. **Гибридный retrieval обязателен:** Один только глобальный GraphRAG недостаточен — нужен и локальный retrieval для фактологических запросов
3. **Домен имеет значение:** Extraction prompts и few-shot examples должны быть адаптированы под домен. Для узких профессиональных доменов рассмотрите ontology-guided подход
4. **Стоимость — ключевой фактор:** LLM-based extraction — самый дорогой этап. KET-RAG и LinearRAG показывают, что можно радикально снизить стоимость без потери качества
5. **Обновляемость:** Планируйте инкрементальное обновление с самого начала — полная перестройка индекса неприемлема для production
6. **Оценка:** Используйте комбинацию автоматических метрик (LLM-as-judge + Claimify) и экспертной оценки. GraphRAG-Bench — обязательный бенчмарк
7. **Agentic — будущее:** Тренд 2025-2026 — агентный подход к retrieval (GraphSearch, GeAR, Youtu-GraphRAG). Планируйте переход к agentic архитектуре
8. **Graph Foundation Models — горизонт:** GFM-RAG и G-reasoner показывают, что предобученные графовые модели могут заменить дорогую LLM-индексацию для новых датасетов
