# Правила проекта

> Краткие, выполнимые правила и конвенции проекта. Автоматически загружаются /aif-implement перед выполнением.

## Правила

- Вся кодовая база пишется на Go; Python и Rust исключены; нативный код — только через CGo к зрелым C-библиотекам и при измеримом критерии (профилирование/бенчмарк). Фронтенд — TypeScript (тонкий SPA, `ADR-DES.UI.spa-typescript-frontend`), вне серверной кодовой базы.
- Спецификации — источник правды: код не должен противоречить `specs/vision.md`, `specs/glossary.md` и принятым ADR.
- Продукт — evidence-based context layer: каждый ответ обязан иметь grounding и provenance; не реализуй «поиск по документам» или чат-бот.
- Соблюдай границы проекта: GraphRAG — не источник правды и не замена управленческих решений; fine-tuning и real-time обновление графа — вне MVP.
- Принцип «агент готовит — человек подтверждает»: ИИ-сгенерированный код и артефакты проходят подтверждение человеком (ревью, контрактные тесты).
- Фиксируй эталонные кейсы (K1, K4, K5, K17) контрактными тестами до реализации метода.
- Минимизируй потребление токенов и число LLM-вызовов — сквозное требование для локального контура с open-weight моделями.
- Данные разработки не покидают периметр: LLM исполняется только в контролируемом контуре с фильтрацией утечек и аудитом.
- Используй markdown-спеки как authoritative-источник; PDF — только для книг/legacy; Confluence исключён.
- Онтологический слой — машинно-читаемая модель предметной области (онтология); исходная модель поставляется из репозитория модели; автоматическое построение из корпуса — Фаза 3.
- Используй термины единого языка из `specs/glossary.md` во всех документах, ADR и коде.
- Новые ADR именуй по шаблону `ADR-<LEVEL>.<AREA>.<semantic-tag>` с уникальным ID и обязательными полями; изменение принятого ADR оформляй через статус «ЗАМЕНЕНО» и новый ADR.
- Фиксируй целевые метрики до реализации (например, точность ответов RAG ≥ 70%) и валидируй их бенчмарками на целевом корпусе.
- Spec-driven development: спецификации — источник правды, тесты и код выводятся из требований (FR/US/BR — 100% требование-уровневое покрытие тестами); контрактные тесты эталонных кейсов (K1, K4, K5, K17) — до реализации метода.
- Политика разработки (решение 2026-08-30): код в основном генерируется ИИ-агентами и подтверждается человеком; максимальная автоматизация (что можно автоматизировать — автоматизируется); README-файлы — на русском языке; комментарии — человеко-читаемые (бизнес-логика — на русском, идентификаторы — на английском); используй стандартные инструменты и практики индустрии (что возможно — максимально стандартно и привычно); фреймворк — AI Factory.
- Поддерживай разделение каталогов: спецификации — в `specs/`, код — в `src/`, планы и исследования — в `.ai-factory/`, скиллы — в `.agents/skills/`. Внутри `src/` разделяй `frontend/` (SPA, TS) и `backend/` (Go, единый модуль `cmd/` + `internal/`) — `ADR-DES.STACK.src-directory-structure`.
- Соблюдай цикл TDD: сначала пиши тест, фиксирующий требуемое поведение (red), затем минимальную реализацию до его прохождения (green), затем рефакторинг (refactor); не пиши реализацию без предварительного теста.
- Используй pnpm последней стабильной версии как единственный менеджер пакетов Node.js; `pnpm-lock.yaml` — файл блокировки зависимостей.
- Перед изменением артефакта определи его место в карте зависимостей (`AGENTS.md`, «Трассируемость артефактов»): вышележащие — источники, нижележащие — зависимые.
- При изменении артефакта обязательно проверь и исправь все нижележащие артефакты из строки таблицы «Что проверять при изменении» (`AGENTS.md`); непроверенный нижележащий артефакт — дефект трассируемости (гейт `G1-TRACE`).
- Если изменение требует правки вышележащего артефакта (новый термин → `specs/glossary.md`, границы → `specs/vision.md`, решение → `specs/adr/`), не редактируй его молча: задай уточняющий вопрос, как именно исправить вышележащий артефакт, и вноси правку только после ответа.
- Новый термин или изменение определения фиксируется в `specs/glossary.md` до использования в других артефактах; изменение глоссария требует проверки всех артефактов на корректность употребления термина.
- Изменение `specs/vision.md` (F1–F4, границы, MVP, roadmap) каскадируется вниз: UC, US, FR, NFR, domain, тесты; при изменении функций или границ — также ADR и C4.
- Изменение требования (FR, NFR, UC, контракта) начинается с обновления теста (red), затем кода (green): код обязан соответствовать тесту, а не наоборот.
- Изменение ADR — только через новый ADR со статусом «ЗАМЕНЕНО»; проверь C4, контракты, код и тесты, зависящие от решения.
- Изменение контракта (`specs/contracts/`) требует обновления сгенерированного клиента, мапперов, integration- и E2E API-тестов; breaking change — только через миграцию и version bump.
- US не трассируются на BR и не порождают FR: изменение US затрагивает UC и E2E GUI; изменение BR затрагивает FR, NFR, ADR, контракты, тесты и код.
- BR и QA-методология — внешние слои: ссылайся на них по ID, но не редактируй для подгонки под проект без явного согласования.
- BR не может ссылаться на нижележащие артефакты (NFR, ADR, C4, контракты, QA, `src/`): нижележащие артефакты ссылаются на BR по ID, а не наоборот.
- Вышележащий артефакт не ссылается в своём тексте на нижележащие артефакты: ссылки в тексте идут от нижележащего артефакта к вышележащему (источнику).
