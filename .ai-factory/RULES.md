# Правила проекта

> Краткие, выполнимые правила и конвенции проекта. Автоматически загружаются /aif-implement перед выполнением.

## Правила

- Вся кодовая база пишется на Go; Python и Rust исключены; нативный код — только через CGo к зрелым C-библиотекам и при измеримом критерии (профилирование/бенчмарк).
- Спецификации — источник правды: код не должен противоречить `specs/vision.md`, `specs/glossary.md` и принятым ADR.
- Продукт — evidence-based context layer: каждый ответ обязан иметь grounding и provenance; не реализуй «поиск по документам» или чат-бот.
- Соблюдай границы проекта: GraphRAG — не источник правды и не замена управленческих решений; fine-tuning и real-time обновление графа — вне MVP.
- Принцип «агент готовит — человек подтверждает»: ИИ-сгенерированный код и артефакты проходят подтверждение человеком (ревью, контрактные тесты).
- Фиксируй эталонные кейсы (K1, K4, K5, K17) контрактными тестами до реализации метода.
- Минимизируй потребление токенов и число LLM-вызовов — сквозное требование для локального контура с open-weight моделями.
- Данные разработки не покидают периметр: LLM исполняется только в контролируемом контуре с фильтрацией утечек и аудитом.
- Используй markdown-спеки как authoritative-источник; PDF — только для книг/legacy; Confluence исключён.
- Онтологический слой — машинно-читаемая DDD-модель (bounded contexts, единый язык, агрегаты, доменные события); в MVP модель ведётся кураторами вручную.
- Используй термины единого языка из `specs/glossary.md` во всех документах, ADR и коде.
- Новые ADR именуй по шаблону `ADR-<LEVEL>.<AREA>.<semantic-tag>` с уникальным ID и обязательными полями; изменение принятого ADR оформляй через статус «ЗАМЕНЕНО» и новый ADR.
- Фиксируй целевые метрики до реализации (например, точность ответов RAG ≥ 70%) и валидируй их бенчмарками на целевом корпусе.
- Поддерживай разделение каталогов: спецификации — в `specs/`, код — в `src/`, планы и исследования — в `.ai-factory/`, скиллы — в `.agents/skills/`.
