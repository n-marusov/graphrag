# Гейты AI Factory — методология и каталог

> Назначение: определить принципы и каталог гейтов AI Factory для LLM-генерации артефактов спецификации и для проверки достижения функциональных требований (FR) кодом. Гейты превращают генерацию артефактов из «ускоренного гадания» в управляемый процесс с измеримыми проверками на каждой стадии жизненного цикла артефакта, а реализацию FR — из декларации в подтверждённое тестами достижение.
> Методологическая база: матрица программирования качества (5 факторов × 4 этапа ЖЦ, `qa/README.md` §2.4, §5.1), принципы контроля качества `qa/README.md` §3, каталог фитнес-функций `.ai-factory/references/fitness-functions.md` (метрики + автоматизация + пороги = гейт).

---

## 1. Назначение и область применения

| Аспект | Значение |
|---|---|
| **Что описывает** | Принципы и каталог гейтов AI Factory: (1) для артефактов, генерируемых/редактируемых LLM-контуром; (2) для проверки достижения функциональных требований (FR) кодом — условия приёмки задачи от агента (класс FG, раздел 6.4); (3) для проверки соответствия реализации архитектуре — C4-модели, ADR, границам компонентов и контрактам (класс AG, раздел 6.5) |
| **Контур** | Артефакты спецификации: `vision.md`, `glossary.md`, `adr/`, `qa/`, планы и roadmap (`.ai-factory/`), `references/`; планируются (vision.md §2.2): `use-cases/`, `fun-req/`, `nonfun-req/`, `user-strories/`, `business-rules/`, `c4/`, `domain/`; реализация: `src/` — Go-модули по функциям F1–F4 (канон vision.md §2.1–2.2): ядро, оркестрация пайплайнов индексации (F2), движок запросов (F1), MCP-сервер (F4), интеграции, CPU-компоненты |
| **Проблема** | Две: (1) LLM-генерация быстра и объёмна, но качество непредсказуемо — галлюцинации (выдуманные ID, ссылки, требования), противоречия с существующими артефактами, нарушение шаблонов, разрывы трассируемости, непроверяемые формулировки; (2) реализация FR без подтверждения — код собирается, но достижение критериев приёмки не доказано тестами. | **Для кого** | Агенты AI Factory (LLM-контур), владельцы артефактов, QA-инженеры, ревьюеры, архитекторы, DevOps |

## 2. Модель: артефакты, LLM-контур, гейты

- **Артефакт** — единица спецификации с владельцем, схемой идентификаторов и шаблоном (определяется README каталога). Артефакт проходит стадии жизненного цикла (раздел 3).
- **LLM-контур** — агенты AI Factory, которые генерируют, редактируют и проверяют артефакты. Гейты применяются **внутри** контура (shift-left) и **снаружи** (CI, ревью).
- **Гейт** — проверка с измеримым результатом (`pass`/`fail`/`warn`), которая блокирует переход артефакта на следующую стадию. Гейт ≠ галочка: результат подтверждается артефактом проверки (отчёт, JSON, ревью-комментарий).
- **Владелец артефакта** — роль, принимающая решения по артефакту (критерии приёмки, приоритеты, TBD) и утверждающая его.
- **FR (функциональное требование)** — артефакт с критериями приёмки (`fun-req/`, планируется — vision.md §2.2), который после спецификации (`live`) переходит в реализацию: задача агенту → код → подтверждение тестами. Достижение FR подтверждается гейтами класса FG (раздел 6.4); FR без теста на критерии приёмки — «задекларировано», а не «реализовано».
- **Архитектурные артефакты** — C4-модель (планируется; текущий архитектурный источник — `adr/` и `vision.md` §3.3) и архитектурные решения (`adr/`). Они задают ожидаемую структуру системы: расхождение реализации с диаграммой (изменённый/добавленный контракт, новый канал, отсутствующий компонент) — дефект, который ловят гейты класса AG (раздел 6.5) (`qa/README.md` §4.2).

## 3. Жизненный цикл артефакта и точки гейтинга

```
 draft ──G1──▶ validated ──G2──▶ reviewed ──G3──▶ approved ──▶ live
 (гене-   детермини-   LLM-проверки   ручное    утверждён,    (master,
 рация)   рованные     (скиллы-       ревью     готов к       источник
           скрипты/CI   аудиты)       человеком  merge        правды)
                                                              │
                                                    deprecated / archived
                                                    (вывод из эксплуатации)
```

| Стадия | Вход | Гейты на выходе | Результат |
|---|---|---|---|
| `draft` | Задача/план/идея | G1 (обязательный минимум: FMT, ID, LINK, DUP) | Черновик с корректной структурой и ссылками |
| `validated` | Черновик | G1 полный набор по типу артефакта (раздел 7) | Артефакт соответствует шаблону, схеме ID и трассировке |
| `reviewed` | Валидированный | G2 (CONSIST, QMATRIX, DEF, FF, QA, SEC, REVIEW по типу) | Подтверждена непротиворечивость и полнота |
| `approved` | Отревьюенный | G3 (OWNER, ARCH, QA, APPROVE по типу) | Решения человеком приняты, waiver-ы зафиксированы |
| `live` | Утверждённый | merge в `master`, CI-гейты | Артефакт становится источником для последующей генерации |
| `deprecated` | Вывод из эксплуатации | G1-LINK (регресс ссылок), запись замены | Нет «битых» ссылок; замена зафиксирована |

Правило: артефакт **не переходит** на следующую стадию, пока не пройдены все гейты текущей. Пропуск гейта — только по процедуре исключения (раздел 9).

Жизненный цикл FR не заканчивается на `live`: спецификация переходит в реализацию, и достижение подтверждается гейтами FG:

```
 live (спецификация FR, критерии приёмки)
   │
   ▼
 Реализация (задача агенту, aif-implement)
   │
   ▼
 FG-гейты достижения FR (локально у агента + CI)
   ├─ FG-BUILD — код собирается
   ├─ FG-UNIT — модульные тесты (локальные регрессионные) проходят
   ├─ FG-REGRESSION — существующий набор тестов не сломан
   ├─ FG-TEST — критерии приёмки FR покрыты автоматическим тестом
   ├─ FG-TRACE — FR ↔ тест: двухсторонняя трассировка, нет «сиротских» тестов
   ├─ FG-TEST-QUALITY — тесты верифицированы: детерминизм, нет тривиальных/«флаки»
   ├─ FG-MUTATION — мутационное тестирование критичных модулей
   └─ FG-VERIFY — верификация против плана (aif-verify)
   │
   ▼
 AG-гейты — архитектурные проверки (локально + CI)
   ├─ AG-C4 / AG-ADR — соответствие C4-модели и ADR
   ├─ AG-CYCLES / AG-LAYERS / AG-BOUNDARIES — структура и границы
   ├─ AG-CONTRACTS — контракты API/MCP (breaking changes)
   └─ AG-DEPS / AG-STRUCT — зависимости и структурные метрики
   │
   ▼
 Задача принята (Definition of Done) → CI (README.md §8, целевое состояние) → merge
```

**Правило приёмки:** задача от агента принимается, **только если код собирается (`FG-BUILD`) и проходят модульные тесты — локальные регрессионные (`FG-UNIT`)**. Этот минимальный блокер обязателен независимо от остальных результатов; `FG-BUILD` и `FG-UNIT` не подлежат waiver (раздел 9).

## 4. Принципы гейтов LLM-генерации

1. **Измеримость.** Каждый гейт — бинарный критерий (`pass`/`fail`/`warn`) с детерминированным алгоритмом проверки или обоснованным заключением. «Проверено вручную» без измеримого результата гейтом не является (`qa/README.md` §3, принцип 12).
2. **Автоматизация по умолчанию.** Детерминированные проверки (G1) — скриптами в CI и в агенте; LLM-проверки (G2) — только там, где нет детерминированного алгоритма; ручные (G3) — только решения человека. Метрика без регулярного автоматического применения с порогом — не гейт, а отчёт (`fitness-functions.md`, Best Practices 3).
3. **Shift-left.** Гейты применяются в момент генерации, а не только при ревью: агент обязан прогнать G1 до выдачи результата (`qa/README.md` §3, принцип 10).
4. **Гейт на выходе каждой стадии.** Переход `draft → validated → reviewed → approved → live` блокируется непройденными гейтами текущей стадии.
5. **Трассируемость.** Артефакт, разрывающий цепочку `vision → UC → FR/NFR → US → тест`, не проходит `G1-TRACE`; нарушение иерархии — дефект, а не стилистика.
6. **Детерминизм.** Одинаковый вход → одинаковый результат гейта. «Флаки»-гейт хуже отсутствующего: он обесценивает сигнал (`qa/README.md` §3, принцип 8).
7. **Полнота по жизненному циклу.** Набор гейтов закрывает все ячейки матрицы программирования качества процесса генерации (раздел 8); концентрация гейтов только на «Функции × Генерация» — перекос, оставляющий вне контроля сопровождение и вывод из эксплуатации артефактов.
8. **Исключения фиксируются.** Гейт может быть пропущен только по процедуре waiver: запись в `.ai-factory/RESEARCH.md` (Open questions; риск, владелец, срок). Молчаливый пропуск — дефект процесса.
9. **Гейт подтверждается артефактом проверки.** Отчёт, `aif-gate-result` JSON, комментарий ревью. Без подтверждения гейт не засчитывается.
10. **Критичность определяет глубину.** Артефакты P0-доменов (контур LLM, онтологический слой, извлечение знаний, анализ влияния, MCP-компилятор) проходят полный набор гейтов; P2 — по решению владельца (`qa/README.md` §3, принцип 4).
11. **Достижение FR подтверждается тестом.** FR считается достигнутым, только если его критерии приёмки покрыты автоматическим тестом (минимум unit-уровень). Реализация без теста — «задекларировано», а не «реализовано».
12. **Минимальный блокер приёмки задачи.** Задача от агента принимается, только если код собирается (`FG-BUILD`) и проходят модульные тесты — локальные регрессионные (`FG-UNIT`). Эти два гейта не подлежат waiver.
13. **Локальный прогон обязателен.** Гейты FG исполняются агентом локально до выдачи результата (shift-left); CI — повторный контроль, а не замена локального прогона.
14. **Архитектура — объект проверки.** Реализация сверяется с C4-моделью и ADR автоматически (класс AG): расхождение реализации с диаграммой (новый контракт, канал, отсутствующий компонент) — дефект, а не стилистика (`qa/README.md` §4.2). AG исполняются до приёмки задачи, наравне с FG.
15. **Тесты — объект контроля, а не только инструмент.** Качество тестов проверяется тремя уровнями: верификация (`FG-TEST-QUALITY` — детерминизм, отсутствие тривиальных/always-pass/`t.Skip`-заглушек), трассировка к требованиям (`FG-TRACE` — двухсторонняя связь FR ↔ тест, нет «сиротских» тестов) и мутационное тестирование (`FG-MUTATION` — тест убивает мутации в критичных модулях). Тест, который не может упасть, — не тест.

## 5. Классификация гейтов

| Класс | Тип | Результат | Кто выполняет | Когда |
|---|---|---|---|---|
| **G1** | Детерминированные автоматические | `pass`/`fail` | Скрипты, CI, агент (shift-left) | В момент генерации и при merge |
| **G2** | LLM-проверки (аудиты) | `pass`/`warn`/`fail` + обоснование | Скиллы AI Factory, кросс-ревью свежим контекстом | После валидации, перед ручным ревью |
| **G3** | Ручные ревью | `approve`/`reject` | Владелец, архитектор, QA, PO/PM | Перед утверждением и merge |
| **FG** | Детерминированные, достижение FR | `pass`/`fail` | Агент (локально, shift-left), CI | При завершении задачи реализации FR |
| **AG** | Детерминированные, архитектурные | `pass`/`fail` | Агент (локально), CI, интеграционные | При завершении задачи реализации FR |

G1 ловит нарушения формы (структура, ID, ссылки, формат), G2 — нарушения содержания (противоречия, полнота, измеримость, галлюцинации), G3 — решения, которые не автоматизируются (критерии приёмки, приоритеты, допущения).

**FG (FR Gates)** — гейты достижения функциональных требований: исполняются агентом локально при завершении задачи и подтверждаются в CI (README.md §8, целевое состояние). FG проверяют не форму артефакта, а факт реализации FR: сборку, модульные тесты, регресс, покрытие критериев приёмки тестами.

**AG (Architecture Gates)** — архитектурные гейты: проверяют соответствие реализации C4-модели и ADR, границы компонентов, циклы зависимостей, контракты. AG исполняются до приёмки задачи (наравне с FG) и повторяются в CI (README.md §8, целевое состояние).

## 6. Каталог гейтов

### 6.1. G1 — детерминированные автоматические

| ID | Гейт | Что проверяет | Артефакты | Реализация |
|---|---|---|---|---|
| `G1-FMT` | Формат и шаблон | Обязательные поля раздела, структура заголовков, язык (русский, термины — английский) | Все | Скрипт-валидатор markdown (план); частично — grep/CI |
| `G1-ID` | Схема идентификаторов | ID соответствуют схемам: `REQ-FR-<domain>.<qualifier>.<action>`, `REQ-NFR-*`, `UC-*`, `US-<domain>.<subdomain>.<action>`, `BR-*`, `ADR-*` | FR, NFR, UC, US, BR, ADR | Скрипт-валидатор (план) |
| `G1-LINK` | Целостность ссылок | Относительные ссылки ведут на существующие файлы; якоря `<a id>` и `[TBD-xx]` существуют; нет ссылок на несуществующие ID | Все | Скрипт-валидатор (план) |
| `G1-TRACE` | Трассируемость | FR имеет «Источник» (UC); US связана с `@UC-*` (тег опционален для US доменов жизненного цикла `US-ops.*`/`US-decommission.*` — UC отсутствуют, open-questions.md Q1.2); NFR ссылается на цель/ограничение `vision.md`; тест-артефакт ссылается на требование | FR, NFR, US, UC, qa | Скрипт по полям (план); LLM-fallback |
| `G1-PRIO` | Приоритеты | Поле «Приоритет» P0/P1/P2 присутствует; согласовано с приоритетом UC; P0/P1 имеют тест-покрытие | FR, US, UC | Скрипт (план) |
| `G1-METRIC` | Измеримость | NFR: метрика + целевое значение; FR: критерии приёмки без размытых слов («быстро», «надёжно», «как правило», «и т. п.») | NFR, FR | Скрипт-детектор размытых формулировок (план); LLM-fallback |
| `G1-GHERKIN` | Gherkin-синтаксис US | Теги `@US-*`, `@P0–P2`; `@UC-*` — опционален для доменов ЖЦ (ops/decommission); структура `Feature/Background/Scenario/Given/When/Then`; один сценарий — один результат | user-strories (планируется) | Скрипт-парсер Gherkin (план) |
| `G1-GLOSS` | Глоссарий | Доменные термины определены в `glossary.md`; новые термины заведены; нет «висячих» понятий | Все + glossary | LLM + скрипт (гибрид) |
| `G1-C4` | Валидация C4-диаграмм | Mermaid-блоки (flowchart/C4/sequence) проходят синтаксический разбор `mermaid.parse`; синтаксис по конвенции (референс — `.ai-factory/references/mermaid-c4-diagrams.md`) | c4/, use-cases/, все `.md` с mermaid-блоками (specs/, src/) | ✅ Скрипт `tools/validate-mermaid.js` (npm `validate:mermaid`) + CI-джоба `validate-mermaid` в `.gitlab-ci.yml` (требуется активный GitLab runner) |
| `G1-DUP` | Дубликаты | Уникальность ID в каталоге; отсутствие дублирующих требований (одинаковое описание/критерии) | FR, NFR, UC, US, BR | Скрипт по ID (план) |
| `G1-TBD` | Реестр TBD | Каждый `[TBD-xx]` в артефакте заведён в `.ai-factory/RESEARCH.md` (Open questions) с владельцем, областью и сроком; закрытые TBD удалены из артефактов | Все | Скрипт-сверка (план) |
| `G1-MACHINE` | Машинная читаемость | JSON/OWL/RDF валидируются по схеме; `domain/` (DDD-модель, планируется — vision.md §2.2) согласована с текстовыми артефактами | domain/ (планируется), glossary | Скрипты (план) |

### 6.2. G2 — LLM-проверки (аудиты скиллами)

| ID | Гейт | Что проверяет | Механизм | Статус |
|---|---|---|---|---|
| `G2-RULES` | Соответствие правилам | Изменённые файлы не нарушают `RULES.md` и правила областей; verdict `PASS/WARN/FAIL` + `aif-gate-result` JSON | Скилл `aif-rules-check` | **Есть** |
| `G2-CONSIST` | Непротиворечивость | Новые/изменённые артефакты не конфликтуют с существующими (FR↔NFR↔BR↔UC↔US), терминология согласована, иерархия не нарушена | Кросс-ревью LLM (свежий контекст) | План |
| `G2-QMATRIX` | Полнота по матрице 5×4 | Незакрытые ячейки матрицы программирования качества, лакуны, неизмеримые формулировки, нарушения иерархии | Скилл `quality-matrix` | **Есть** |
| `G2-DEF` | Формальная состоятельность | Определения: тавтологии, циклические ссылки, висячие понятия, родо-видовая корректность | Скилл `formal-definition` | **Есть** |
| `G2-FF` | Сверка с фитнес-функциями | Каждый NFR сопоставлен с фитнес-функцией/проверкой (метрика → порог → место запуска); NFR без измеримой проверки — риск релиза | Сверка LLM с `fitness-functions.md` и `qa/README.md` §5 | План |
| `G2-QA` | QA-артефакты | Для P0/P1 есть тест-покрытие (test-plan/test-cases или запись в матрице качества); включены негативные сценарии | Скилл `aif-qa` + матрица качества | **Есть** (контур) |
| `G2-SEC` | Security-аудит | В артефакты не попали секреты/учётные данные; учтена регуляторика (152-ФЗ — система не оператор ПДн, vision §2.7 п.12) и лицензии open-weight моделей и open-source (SCA); OWASP-применимое | Скилл `aif-security-checklist` | **Есть** |
| `G2-REVIEW` | Ревью изменений | Баги, пробелы, соответствие намерению изменения; опционально `+check` — валидация выводов свежим контекстом | Скилл `aif-review` | **Есть** |

|---|---|---|---|
| `G3-OWNER` | Ревью владельца требований | Критерии приёмки, приоритеты, решения по P2-покрытию и TBD | Владелец требований (BA/PO) |
| `G3-ARCH` | Ревью архитектора | Соответствие C4-модели и ADR, границы компонентов, контракты, топология | Архитектор |
| `G3-QA` | Ревью QA | Проверяемость требований, полнота негативных сценариев, актуальность матрицы качества | QA-инженер |

### 6.4. FG — гейты достижения FR

Условие приёмки задачи от агента (Definition of Done). **Минимальный блокер — `FG-BUILD` + `FG-UNIT`** (обязателен для любой задачи); полный набор — по приоритету FR: P0/P1 — обязателен, P2 — по решению владельца. Локальный прогон у агента обязателен до выдачи результата; CI — повторный контроль (README.md §8, целевое состояние).

| ID | Гейт | Что проверяет | Где исполняется | Статус |
|---|---|---|---|---|
| `FG-BUILD` | Сборка | Код собирается: `go build ./...` для целевой платформы компонента, без ошибок компиляции | Локально у агента + CI | 🔴 CI не настроен (этап видения); локальный прогон обязателен; CI — целевое состояние |
| `FG-UNIT` | Модульные тесты | Локальные регрессионные тесты проходят: `go test -race ./...` | Локально у агента + CI | 🔴 CI не настроен (этап видения); локальный прогон обязателен; CI — целевое состояние |
| `FG-REGRESSION` | Регресс | Существующий набор тестов смежных пакетов не сломан; нет регрессий в зависимых FR | Локально + CI | 🟡 Покрывается `FG-UNIT` при прогоне всего модуля; отдельный регресс-прогон — целевое |
| `FG-TEST` | Критерии приёмки | Каждый критерий приёмки FR покрыт автоматическим тестом (минимум unit-уровень); негативные сценарии включены | Агент (пишет тест) + ревью | 🔴 Правило вводится; тест на FR обязателен |
| `FG-TRACE` | Трассируемость | Двухсторонняя связь FR ↔ тест: каждый критерий приёмки FR покрыт тестом (forward); каждый тест трассируется к FR/US — нет «сиротских» тестов (backward); сверка с матрицей качества (`qa/README.md` §5) | Агент + скрипт (план) | 🔴 План |
| `FG-TEST-QUALITY` | Верификация тестов | Тесты сами проверяются: детерминизм (нет «флаки»), отсутствие тривиальных/always-pass/пустых тестов и `t.Skip`-заглушек, наличие негативных сценариев, реальные проверки (assert) | Агент (пишет тесты) + линтеры тестов + CI | 🔴 Нет; линтеры тестов (testpackage, paralleltest, tparallel) — план |
| `FG-MUTATION` | Мутационное тестирование | Мутации вносятся в критичные модули GraphRAG (контур LLM/фильтрация утечек, онтологический слой, извлечение знаний, анализ влияния, MCP-компилятор, инкрементальное обновление графа); выжившие мутации = пробел в тестах; mutation score ≥ 80% | Локально (критичные модули) + CI (ночной/релизный прогон — целевое состояние) | 🔴 Нет; инструменты Go: go-mutesting / gremlins |

Порядок внедрения контроля качества тестов: 1) `FG-TEST-QUALITY` (линтеры тестов, анти-«флаки») → 2) `FG-TRACE` (скрипт-сверка FR ↔ тест) → 3) `FG-MUTATION` (мутационный прогон критичных модулей, порог 80%).
| `FG-VERIFY` | Верификация против плана | Реализация закрывает задачи плана; нет дрейфа план ↔ код; задача не «закрыта галочкой» | Скилл `aif-verify` | ✅ Есть (strict mode) |
| `FG-COVERAGE` | Порог покрытия | Покрытие критичных модулей ≥ порога (NFR/проект); enforced, а не отчёт | CI (целевое состояние: cobertura + fail-джоба) | 🔴 Порог задан в `qa/unit-testing.md` §12: требование-уровневое покрытие FR/US/BR — 100%; критичные модули — line/branch ≥ 80% |
| `FG-RAG-EVAL` | Оценка качества ответов (RAGAS) | Прогон RAGAS на golden-наборах/эталонных кейсах K1/K4/K5/K17 в CI: faithfulness ≥ 70% (порог REQ-NFR-api.compliance.rag-accuracy); валидация ссылок (реальные URL GitLab/S3); провал — блокер релиза | CI (внешний eval-процесс; Go-кодовая база не затрагивается) | 🔴 План: инструмент — RAGAS (индустриальный стандарт RAG-оценки) |

### 6.5. AG — архитектурные гейты

Проверяют соответствие реализации архитектурным артефактам (C4-модель, ADR) и архитектурным характеристикам (связанность, структура, контракты). База: `qa/README.md` §4.2 («расхождение реализации с C4 — дефект»), каталог фитнес-функций (категория «Связанность и структура», `fitness-functions.md`). Исполняются до приёмки задачи (наравне с FG) и повторяются в CI (README.md §8, целевое состояние).

| ID | Гейт | Что проверяет | Где исполняется | Статус |
|---|---|---|---|---|
| `AG-C4` | Соответствие C4 | Реализация соответствует C4 (планируется): контейнеры, компоненты, каналы связи (GitLab API/webhook, HTTP API, MCP (JSON-RPC), LLM-inference endpoint, хранилище графа/векторов, импорт сигналов); нет отсутствующих компонентов и каналов вне модели; диаграммы актуальны | Локально у агента + CI (целевое состояние) | 🔴 C4-модель отсутствует (этап видения); сверка реализации с диаграммами — целевое состояние |
| `AG-ADR` | Следование ADR | Реализация не нарушает зафиксированные решения (например, `ADR-IMPL.STACK.go-single-language-adoption`: серверная кодовая база — Go; `ADR-DES.UI.spa-typescript-frontend`: фронтенд — TypeScript) | Ревью + CI | 🟡 Ручное ревью; автоматизация — план |
| `AG-CYCLES` | Циклы зависимостей | Нет циклических зависимостей между пакетами и компонентами (аналог ArchUnit `beFreeOfCycles` для Go) | CI (статический анализ графа импортов) | 🔴 Нет |
| `AG-LAYERS` | Слои и границы | Соблюдение слоёв: `internal/` не импортируется извне; нет зависимостей «снизу вверх» (handler/usecase → domain) | CI (go vet, go-arch-lint, custom lint) | 🔴 Нет |
| `AG-BOUNDARIES` | Границы компонентов | Модули F1–F4 не зависят друг от друга напрямую — только через контракты/EventBus/хранилище | CI + интеграционные | 🔴 Нет |
| `AG-CONTRACTS` | Контракты API/MCP | Изменение контракта API/MCP ломает контрактные тесты (breaking changes); эталонные кейсы K1, K4, K5, K17 зафиксированы контрактными тестами до реализации; схема MCP-инструментов синхронизирована | Локально у агента + CI (целевое состояние) | 🔴 Нет (этап видения); контрактные тесты — целевое состояние |
| `AG-DEPS` | Зависимости | Только разрешённые внешние библиотеки (depguard); лицензии совместимы (SCA); нет запрещённых импортов | CI (golangci-lint depguard, trivy) | 🟡 План: golangci-lint (depguard); SCA — целевое состояние для всей кодовой базы |
| `AG-STRUCT` | Структурные метрики | Связанность, сложность, размер модулей в допустимых пределах (fitness-functions: CC ≤ порога, Relative Cyclicity, Structural Debt) | CI | 🔴 Нет |

## 8. Связь с матрицей программирования качества

Матрица программирования качества (`qa/README.md` §2.4) применена к **процессу генерации артефактов**: факторы обусловленности × этапы жизненного цикла артефакта. Каждая ячейка закрывается минимум одним гейтом из каталога; пустая или неизмеримая ячейка — «свободный параметр» процесса и фиксируется в `.ai-factory/RESEARCH.md` (Open questions).

| Фактор \ Этап ЖЦ артефакта | 1. Генерация (draft) | 2. Валидация и использование (validated/reviewed) | 3. Сопровождение (актуализация) | 4. Вывод из эксплуатации (deprecated) |
|---|---|---|---|---|
| **1. Среда** (контекст генерации: глоссарий, референсы, язык, регуляторика) | `G1-GLOSS`, `G1-FMT` (язык); контекст из актуальных `live`-артефактов | `G2-CONSIST` (согласованность с референсами); `G1-LINK` | `G1-LINK` (ссылки на актуальные источники); `G2-CONSIST` при изменениях | Пометка замены; ссылки на преемника |
| **2. Эргономика** (читаемость, однозначность, навигация) | `G1-FMT` (структура); запрет размытых формулировок | `G2-RULES` (стиль); `G2-QMATRIX` (неизмеримые формулировки) | Ревью актуализации `G3-*` | Пометка `deprecated` в шапке |
| **3. Функции** (содержание, полнота, трассируемость) | `G1-TRACE`, `G1-PRIO`, `G1-METRIC`, `G1-DUP`; реализация: `FG-BUILD`, `FG-UNIT`, `FG-TEST`, `FG-TRACE`, `AG-CONTRACTS` | `G2-QMATRIX` (полнота 5×4); `G2-QA` (тест-покрытие P0/P1) | `G2-CONSIST`, `G1-TRACE` при изменениях | `G1-TBD`: удаление/замена зафиксированы |
| **4. Аварии/Катастрофы** (галлюцинации, противоречия, разрывы) | `G1-ID`, `G1-LINK`, `G1-DUP`: нет выдуманных ID и ссылок; реализация: `FG-REGRESSION` (негативные сценарии), `FG-TEST-QUALITY`, `FG-MUTATION` (тесты сами ловят дефекты) | `G2-REVIEW` (кросс-ревью), `G2-SEC` (секреты, регуляторика) | `G1-LINK`-регресс; `G2-CONSIST` против конфликтов | `G1-LINK`: регресс ссылок при выводе |
| **5. Тех. обеспеченность ЖЦ** (автоматизация, версии, CI) | `G1-C4`, скрипты валидации; `aif-gate-result` в CI; реализация: `FG-COVERAGE` (порог enforced), `AG-C4`, `AG-CYCLES`, `AG-LAYERS`, `AG-BOUNDARIES`, `AG-DEPS`, `AG-STRUCT` | `G2-RULES` (`aif-rules-check`), `aif-verify` при реализации | Версионирование, история изменений, `G1-TBD` | Архивация, утилизация, передача знаний |

Пояснения:

- Гейты — инструмент закрытия ячеек матрицы для процесса генерации: **каждый гейт измерим** (принцип 1), поэтому ячейка считается закрытой, только если проверка даёт `pass`/`fail`/`warn` с обоснованием.
- FG-гейты закрывают ячейки этапа 1 (Генерация/Реализация) для кода: критерии приёмки, заданные при спецификации FR (`G1-METRIC`), превращаются в тесты (`FG-TEST`) и подтверждаются сборкой и прогоном (`FG-BUILD`, `FG-UNIT`).
- Контроль качества тестов (мета-уровень) закрывает ячейку «Аварии × Реализация»: `FG-TEST-QUALITY` (тест не тривиален и не «флакает»), `FG-MUTATION` (тест убивает мутации — реально ловит дефекты), `FG-TRACE` (тест связан с требованием — нет «сирот»). Покрытие утверждений (`FG-COVERAGE`) показывает широту, mutation score — глубину тестов.
- AG-гейты закрывают те же ячейки для архитектуры: C4 и ADR задают ожидаемую структуру, а `AG-C4`/`AG-CYCLES`/`AG-LAYERS`/`AG-BOUNDARIES`/`AG-CONTRACTS` подтверждают, что реализация не разошлась с ней (структурные фитнес-функции, `fitness-functions.md` «Связанность и структура»).
- Концентрация гейтов только в ячейке «Функции × Генерация» — перекос («ловушка 3.2» из `qa/README.md` §2.4): вне контроля остаются актуализация артефактов и их вывод из эксплуатации. Поэтому `G1-LINK`-регресс и `G1-TBD` обязательны для всех типов артефактов.
- Метрики процесса (доля артефактов, прошедших гейты; доля waiver-ов; время от draft до live) — кандидаты на continual-фитнес-функции процесса (`fitness-functions.md`, категория «Pipeline & Process»).

## 9. Политика исключений (waiver) и TBD

1. **Waiver** — официальный пропуск гейта. Оформляется записью в `.ai-factory/RESEARCH.md` (Open questions): ID исключения, пропущенный гейт, риск, владелец, срок закрытия.
2. Waiver допустим только для `G2`/`G3`; для `G1` — только на стадии `draft` (черновик может быть неполным, но обязан иметь корректные ID и ссылки, иначе дефекты тиражируются).
3. **TBD-флаг** — пробел в артефакте. Артефакт с `[TBD-xx]` не переходит в `live`, пока TBD не закрыт или не зафиксирован как waiver с владельцем и сроком (правило каталога `fun-req/` (планируется, vision.md §2.2): «требование не считается готовым, пока TBD не закрыт»).
4. Молчаливый пропуск гейта (без waiver) — дефект процесса, фиксируется в `qa/` и разбирается в ревью процесса.
5. **FG-гейты**: `FG-BUILD` и `FG-UNIT` — минимальный блокер приёмки задачи, waiver не подлежат (принцип 12). `FG-TEST`, `FG-TRACE`, `FG-COVERAGE` — waiver допустим только с владельцем и сроком (например, тест на критерии приёмки FR отложен на одну итерацию с записью в `.ai-factory/RESEARCH.md`).
6. **Контроль качества тестов**: `FG-TEST-QUALITY` — waiver не подлежит (тривиальный тест хуже отсутствующего: он создаёт ложную уверенность). `FG-MUTATION` — waiver допустим для некритичных модулей; для критичных модулей GraphRAG (контур LLM, онтологический слой, извлечение знаний, анализ влияния, MCP-компилятор) — обязателен, mutation score ≥ 80%; снижение порога — только с QA-инженером и владельцем (запись в `.ai-factory/RESEARCH.md`).
7. **AG-гейты**: waiver допустим только с владельцем-архитектором и сроком; `AG-CONTRACTS` и `AG-CYCLES` — без waiver (тиражируют дефекты в контракты и связанность компонентов).

## 10. Порядок применения в AI Factory-контуре

```
Генерация (агент)
  ├─ shift-left: G1-FMT, G1-ID, G1-LINK, G1-DUP — до выдачи результата
  ├─ G1 полный набор по типу артефакта (раздел 7)
  └─ aif-gate-result (JSON) прикладывается к результату
        │
        ▼
LLM-проверки (G2)
  ├─ G2-RULES (aif-rules-check) — обязателен для изменённых файлов
  ├─ G2-CONSIST / G2-QMATRIX / G2-DEF / G2-FF / G2-QA / G2-SEC / G2-REVIEW — по типу
  └─ Каждый гейт: verdict + обоснование; fail → возврат на генерацию
        │
        ▼
Ручные ревью (G3)
  ├─ G3-OWNER / G3-ARCH / G3-QA — по типу артефакта
  ├─ G3-APPROVE — перед merge в master
  └─ reject → возврат; waiver → запись в .ai-factory/RESEARCH.md
        │
        ▼
live (master)
  └─ CI: G1-C4, G1-детерминированные скрипты, aif-gate-result из отчётов

Реализация FR (задача агенту, из плана)
  ├─ FG-BUILD: go build ./... — до выдачи результата (shift-left)
  ├─ FG-UNIT: go test -race ./... — локальные регрессионные тесты
  ├─ FG-TEST: тест на критерии приёмки FR (минимум unit) + FG-TRACE (FR ↔ тест)
  ├─ FG-TEST-QUALITY: тесты верифицированы — детерминизм, нет тривиальных/always-pass
  ├─ FG-MUTATION: мутационный прогон критичных модулей (локально) — тест убивает мутации
  ├─ FG-REGRESSION: существующий набор тестов не сломан
  ├─ FG-VERIFY: aif-verify (strict mode) — задача закрыта только при прохождении
  ├─ AG-C4 / AG-ADR / AG-CYCLES / AG-LAYERS / AG-BOUNDARIES / AG-CONTRACTS — архитектурные проверки
  └─ результат: отчёт FG + AG + aif-gate-result; без FG-BUILD + FG-UNIT задача не принимается
        │
        ▼
CI (README.md §8, целевое состояние): golangci-lint → go test -race → сборка → контрактные тесты → интеграционные → e2e → NFR — повторный контроль FG/AG
```

Порядок исполнения: агент не завершает задачу, пока не пройдены гейты своей стадии; нарушение фиксируется как дефект процесса. Связка «артефакт → гейты → отчёты» — кандидат на проверку автоматической связкой «задача → MR» (план, `.ai-factory/PLAN.md`).
