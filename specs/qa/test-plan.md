| BR | ✅ | ✅ | — | — | ✅ |

GUI в продукте отсутствует (MVP — серверные компоненты); столбец E2E GUI зарезервирован методологией — применяется, если появится управляющий интерфейс (уточняется). Требования формата US/UC/FR/NFR/BR планируются (vision §2.2); до появления каталогов таблица отражает целевую модель.

**Правила стратегии:**
1. **P0-сценарии** — обязательно на всех уровнях; smoke-набор = критический путь ≤ 15 мин: приём документа (GitLab webhook/MR) → автоиндексация → обновление графа → ответ с grounding → анализ влияния → компиляция контекста (MCP).
2. **Негативные сценарии и границы** — не менее 30 % набора каждой функции (пустой/невалидный корпус, дубликаты, противоречия, недоступные GitLab/LLM-endpoint, невалидная модель предметной области, таймауты, идемпотентность).
3. **Каскады событий** — интеграционные тесты: `DocumentIngested → EntityExtracted → GraphUpdated`; `GraphUpdated → CommunityRecomputed`; `SignalReceived → KnowledgeRefreshed`; `ConflictDetected → ReviewCompleted`; `SecurityEventEmitted → аудит`.
4. **Платформозависимость** — развёртывание и запуск контура на целевом стенде (Linux, NVIDIA GPU, CUDA): GPU-контур, драйверы, пути, привилегии.
5. **Детерминированность** — фиксированные тестовые корпуса, заглушки GitLab, эмулятор LLM с golden-ответами, без зависимости от внешней среды.
6. **Источник E2E-сценариев** — E2E-сценарии выводятся из vision.md (функции F1–F4, критерии успеха §1.4) и эталонных кейсов K1–K24; до появления каталогов требований сценарии исполняются на integration-уровне (правило — `e2e-api-testing.md` §4).

## 5. Тестовые данные (фиксированные наборы)

- **Корпуса:** фиксированные тестовые корпуса — markdown-спеки (в т. ч. спеки проекта в формате GitLab) и PDF-книги; с известным составом сущностей/связей/утверждений; детерминированные, изолированные от продуктивных.
- **Онтология (модель предметной области):** модели-фикстуры — валидная, неполная, конфликтующая — для проверки резолвинга и канонических терминов (механизм F1/F3).
- **Golden-наборы:** наборы «запрос → эталонный ответ → источники» для эмулятора LLM (детерминированные golden-ответы) и проверки точности ответов и grounding (F1).
- **Граф-фикстуры:** графы знаний с известными сообществами, дубликатами сущностей и противоречиями (для F2, F3, детекции противоречий); графы связей артефактов (F3).
- **Сигналы:** вне рамок проекта (vision §2.7 п.4–5) — фикстуры не разрабатываются.
- **MCP-запросы:** эталонные MCP-запросы ИИ-агентов и ожидаемые компиляции контекста (F4).
- **Security-данные (REQ-NFR-security.compliance.llm-contour):** тестовые секреты/ПДн и сценарии утечек для проверки фильтрации и аудита; отчёты о затратах LLM-вызовов.

## 6. Критерии входа/выхода

**Вход (для каждого уровня):**
- Требования функций F1–F4 проверены на полноту (нет незакрытых TBD, влияющих на тест); P0/P1 — готовы критерии приёмки (каталоги требований планируются — vision §2.2).
- Стенды развёрнуты (dev, тестовый контур: заглушки GitLab, эмулятор LLM, тестовые хранилища графа/векторов), данные изолированы.
- Предыдущий уровень зелёный (unit → integration → smoke → e2e).

**Выход (глобальный):**
- 100 % сценариев P0 и ≥ 90 % сценариев P1 покрыты прошедшими тестами; контрактные тесты K1/K4/K5/K17 — зелёные.
- Негативные сценарии по каждой функции (чек-лист §7) выполнены.
- Точность ответов RAG ≥ 70 % (порог продолжения внедрения, vision §3.2) подтверждена на golden-наборах; security-проверки контура LLM (REQ-NFR-security.compliance.llm-contour) — без блокеров; целевые значения большинства метрик фиксируются после замера исходного уровня (vision §1.4).
- Нет открытых Blocker/Critical дефектов; Major — согласованы с владельцем требований.
- Доля «флаки»-прогонов ≤ допустимого порога (целевое состояние).

### 7.3. Функция F1 — генерация проверяемых ответов (F1.1, F1.2)

**Объём:** каталог требований планируется (vision §2.2); распределение P0/P1/P2 — предварительное (уточняется).
**Компоненты:** движок запросов (dual-level retrieval: LightRAG, PathRAG, PPR); LLM-inference endpoint (локальный GPU-контур).
**Цель:** подтвердить ответы со ссылками на источники (grounding/provenance), обработку глобальных и multi-hop вопросов, детекцию противоречий, точность RAG ≥ 70 %.

**Ключевые сценарии:**

| # | Сценарий | Приоритет | Уровень |
|---|---|---|---|

| F1-03 | Dual-level retrieval: локальные и глобальные вопросы (LightRAG/PathRAG/PPR) | P1 | integration |
| F1-04 | Multi-hop: ответ требует связей через несколько сущностей | P1 | E2E API |

| F1-06 | LLM-as-judge: оценка качества ответов (методика — уточняется) | P1 | e2e |
| F1-07 | **Negative:** вопрос вне корпуса — ответ «нет данных» без галлюцинаций (критерий — уточняется) | P1 | E2E API |
| F1-08 | **Negative:** недоступный LLM-endpoint — понятная ошибка, ретраи | P1 | integration |

**Данные:** golden-наборы «запрос → эталонный ответ → источники»; граф-фикстуры с противоречиями.
**Риски:** качество open-weight моделей (порог ≥ 70 % — vision §3.2); детерминизм LLM — эмулятор golden.

| F3-02 | Анализ влияния: изменение артефакта → список затронутых (K4 — контрактный тест) | P0 | E2E API |
| F3-03 | Сверка результат↔источник: результат сопоставим с источниками (K5 — контрактный тест) | P0 | E2E API |
| F3-04 | Граф до клиентского результата: прослеживаемость от артефакта до результата (уточняется) | P1 | integration |
| F3-05 | Сигналы владельцу: изменение связанных артефактов → сигнал владельцу | P1 | integration |
| F3-06 | **Negative:** артефакт без связей — фиксируется; доля связности не ниже порога (уточняется) | P1 | e2e |

**Данные:** граф-фикстуры артефактов; эталонные наборы K4/K5.
**Риски:** гранулярность связей — уточняется после замера исходного уровня (vision §1.4).

### 7.5. Вне рамок проекта (vision §2.7 п.4–5)

Накопление знаний из внешних сигналов, импорт сигналов с полей и петля обучения — **вне рамок проекта** (vision.md §2.7 п.4–5). Тесты не разрабатываются; связанные метрики («время сигнал → фикс») в тест-план не включаются.

### 7.6. Функция F4 — доставка ответов и контекста через MCP

**Объём:** каталог требований планируется (vision §2.2); распределение P0/P1/P2 — предварительное (уточняется).
**Компоненты:** MCP-сервер (context compiler); интеграции (ИИ-агенты по MCP).
**Цель:** подтвердить компиляцию точного контекста для ИИ-агентов через MCP, сверку контекста со спецификациями, предзавершающий гейт (Фаза 2/3), QA-контекст.

**Ключевые сценарии:**

| # | Сценарий | Приоритет | Уровень |
|---|---|---|---|
| F4-01 | MCP-сервер: агент получает скомпилированный контекст (K17 — контрактный тест) | P0 | E2E API |
| F4-02 | Точность контекста: контекст соответствует запросу агента и сверяется со спецификациями | P0 | E2E API |
| F4-03 | Базовая сверка со спецификациями: компиляция контекста сверена с источниками (MVP) | P1 | integration |
| F4-04 | Предзавершающий гейт полного объёма — вне области (Фаза 2/3, vision §2.6); сценарий фиксирует целевую модель | P2 | E2E API (целевая модель) |
| F4-05 | QA-контекст: компиляция контекста для QA-проверок (уточняется) | P1 | integration |
| F4-06 | **Negative:** недоступны онтология/граф — контекст не скомпилирован, понятная ошибка агенту | P1 | integration |
| F4-07 | **Negative:** минимизация токенов — контекст в пределах порога (сквозное требование §8) | P1 | e2e |

**Данные:** эталонные MCP-запросы агентов и ожидаемые компиляции контекста.
**Риски:** формат контекста и протокол MCP — уточняется (MVP — базовый режим).

### 7.7. Сквозное требование: безопасный контур LLM (REQ-NFR-security.compliance.llm-contour)

**Объём:** каталог требований планируется (vision §2.2); распределение P0/P1/P2 — предварительное (уточняется).
**Компоненты:** интеграции (GPU-контур: vLLM/Ollama/llama.cpp, OpenAI-совместимый endpoint); фильтрация утечек, аудит.
**Цель:** подтвердить локализацию LLM-контура на GPU компании, фильтрацию утечек и аудит, контроль затрат, лицензионную чистоту моделей и зависимостей.

**Ключевые сценарии:**

| # | Сценарий | Приоритет | Уровень |
|---|---|---|---|
| SEC-01 | Локальный GPU-контур: все обращения к LLM идут через корпоративный канал; 0 обращений вне контура | P0 | e2e |
| SEC-02 | Фильтрация утечек: секреты/ПДн не покидают контур (на входе и выходе) | P0 | integration |
| SEC-03 | Аудит: события безопасности (событие `SecurityEventEmitted`) логируются, аудит доступен ИБ | P1 | integration |
| SEC-04 | Контроль затрат: замер токенов и числа LLM-вызовов на запрос (сквозное требование §8) | P1 | e2e |
| SEC-05 | Лицензии: open-weight модели и open-source зависимости (SCA) — лицензионная чистота | P1 | CI |
| SEC-06 | ПДн: обработка персональных данных соответствует 152-ФЗ (уточняется с ИБ) | P1 | аудит (уточняется) |
| SEC-07 | **Negative:** обращение к внешнему LLM-endpoint вне контура блокируется | P0 | integration |
| SEC-08 | **Negative:** утечка в ответе (секрет/ПДн) — фильтрация срабатывает, событие в аудите | P1 | integration |

**Данные:** тестовые секреты/ПДн; сценарии утечек; отчёты о затратах LLM-вызовов.
**Риски:** реальный GPU доступен только на прод-подобном стенде; политики контроля затрат — уточняется (G6).

### 7.8. Контракты и security-gaps (сквозная проверка)

**Основание:** эталонные кейсы K1–K24 (`../../.ai-factory/RESEARCH.md`); K1 (ответ с grounding), K4 (анализ влияния), K5 (сверка результат↔источник), K17 (context compiler) — контрактные тесты до реализации.
**Цель:** подтвердить соответствие реализации контрактным кейсам до реализации (K1/K4/K5/K17) и закрытие security-пробелов контура LLM (REQ-NFR-security.compliance.llm-contour). Negative-сценарии фиксируют целевое поведение; до реализации сценарии выполняются как «ожидаемое усиление» (статус — §10).

| # | Сценарий | Приоритет | Уровень |
|---|---|---|---|
| K-01 | Контракт K1: ответ с grounding — каждый ответ содержит ссылки на источники | P0 | E2E API |
| K-02 | Контракт K4: анализ влияния — список затронутых артефактов | P0 | E2E API |
| K-03 | Контракт K5: сверка результат↔источник — результат сопоставим с источниками | P0 | E2E API |
| K-04 | Контракт K17: context compiler — MCP-контекст соответствует запросу и спецификациям | P0 | E2E API |
| K-05 | Остальные кейсы K1–K24 — контрактные тесты по мере готовности (уточняется) | P1 | (уточняется) |
| K-06 | **Negative (REQ-NFR-security.compliance.llm-contour):** обращение к LLM вне контура блокируется (см. SEC-07) | P0 | integration |
| K-07 | **Negative (REQ-NFR-security.compliance.llm-contour):** утечки (секреты/ПДн) фильтруются и фиксируются в аудите (см. SEC-08) | P1 | integration |
| K-08 | **Negative (F2):** повторная подача документа не дублирует граф — идемпотентность (см. F2-07) | P1 | integration |

**Данные:** golden-наборы K1/K4/K5/K17; эмулятор LLM с детерминированными golden-ответами.
**Риски:** детерминизм LLM — эмулятор golden; методики оценки качества (LLM-as-judge) — уточняется.

## 8. План тестирования NFR (метрики vision.md §1.4 и glossary.md §8)

Методика: каждая метрика проверяется тестом по своим критериям приёмки (метрика + целевое значение) — `README.md` §7.

| Метрика (vision §1.4 / glossary §8) | Целевое значение | Тип проверки | Сценарии |
|---|---|---|---|
| Точность ответов RAG | ≥ 70 % (порог продолжения внедрения, vision §3.2) | e2e на golden-наборах | Ответы на golden-наборы «запрос → эталонный ответ → источники» соответствуют эталону (F1-02); LLM-as-judge (F1-06) |
| Время ожидания ответа | медиана и p90 (целевое значение — после замера исходного уровня) | нагрузочные, e2e | Замер времени «запрос → ответ» на тестовом контуре и прод-подобном стенде; p90 при пиковой нагрузке |
| Число противоречий | (после замера исходного уровня) | integration | Детекция противоречий на граф-фикстурах с известными противоречиями (F1-05); ложные срабатывания (уточняется) |
| Доля артефактов со связями в графе | (после замера исходного уровня) | integration, e2e | Связность графа артефактов на фикстурах и реальных данных (F3-01); порог — после замера |
| Доля вопросов, закрытых без аналитика (G7) | (после замера исходного уровня) | e2e | Доля типовых вопросов, закрытых системой знаний без участия аналитика |
| Доля обращений к LLM через корпоративный канал | 100 %; 0 вне контура | integration, e2e | Все обращения идут через локальный GPU-контур; обращение к внешнему endpoint блокируется (SEC-01, SEC-07) |
| Минимизация токенов и числа LLM-вызовов | (сквозное требование; после замера) | e2e, unit | Число токенов/вызовов на запрос в пределах порога (ONT-06, F4-07, SEC-04); контекст не дублируется |
| Инкрементальное обновление (время пересчёта) | (после замера исходного уровня) | бенчмарк | Время пересчёта при изменении документа меньше полной переиндексации (F2-03, F2-09) |
| Производительность CPU-компонентов (HNSW, Leiden, токенизатор) | (после замера на целевом корпусе) | бенчмарк | Поиск по HNSW, детекция сообществ Leiden, токенизация на целевом корпусе (масштаб 1k vs 100k — открытый вопрос RESEARCH.md) |

**Целевые значения большинства метрик фиксируются после замера исходного уровня (vision §1.4).** Каталог NFR (`nonfun-req/`) ведётся — сквозные `REQ-NFR-*` перенесены из vision.md §2.5; структура разделов NFR приведена к каталогу.

## 10. Риски и ограничения плана

1. **Этап видения:** кодовой базы и тестов нет — план фиксирует целевое состояние MVP (vision §2.5); до реализации — контрактные тесты K1/K4/K5/K17 и тесты-заглушки на тестовом контуре.
2. **Реальный GPU-контур недоступен в dev/CI** — LLM заменяется эмулятором с golden-ответами; прод-подобные проверки (производительность, качество open-weight моделей) — на выделенном стенде.
3. **Открытые вопросы:** масштаб корпуса (1k vs 100k — RESEARCH.md), методика оценки качества ответов (LLM-as-judge), целевые значения метрик (после замера исходного уровня, vision §1.4) — сценарии зависят от решений владельца требований.
4. **Качество open-weight моделей** — точность ответов RAG ≥ 70 % (порог продолжения внедрения, vision §3.2) проверяется на golden-наборах; при недостижении порога внедрение приостанавливается.
5. **E2E-проверки** требуют тестового контура (заглушки GitLab, эмулятор LLM, тестовые хранилища графа/векторов) — высокая стоимость поддержки, ограниченный параллелизм.
6. **Стабильность тестов и детерминизм:** эмулятор LLM с детерминированными golden-ответами обязателен; недоступность внешних систем (GitLab, GPU) не должна ломать прогоны (принцип 8 `README.md`).
7. **Security контура LLM (REQ-NFR-security.compliance.llm-contour):** negative-сценарии (утечки, обращения вне контура, аудит) фиксируют целевое поведение; политики контроля затрат и обработки ПДн (152-ФЗ) — уточняются с ИБ.
8. **Эталонные кейсы K1–K24 (RESEARCH.md) как эталон:** контрактные тесты до реализации фиксируют ожидаемое поведение; расхождения сценариев с реализацией фиксируются в RESEARCH.md и уточняются с владельцем требований.
