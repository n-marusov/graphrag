## Описание

Безопасный контур LLM: локальные GPU и open-weight модели — основной вариант исполнения; внешний провайдер — только по договору через корпоративный шлюз (оба варианта — с фильтрацией утечек и аудитом); данные разработки (код, спеки) не покидают периметр; система не обрабатывает ПДн как бизнес-данные (vision §2.7 п.12); фильтрация утечек и аудит обращений к LLM.

## Критерии приёмки

- Доля обращений к LLM через корпоративный канал — 100%; обращений вне контура — 0 (G6). Внешний провайдер по договору — только через корпоративный шлюз (в рамках контура); оба варианта исполнения (локальные GPU, корпоративный шлюз) — с фильтрацией утечек и аудитом.
- Данные разработки не покидают периметр: отсутствует исходящий трафик к внешним LLM-провайдерам вне корпоративного шлюза (проверка на тестовом контуре, DevSecOps-сканы). Система не обрабатывает ПДн как бизнес-данные (vision §2.7 п.12); фильтрация утечек блокирует попадание ПДн/секретов в промпты и ответы.
- События безопасности контура (`SecurityEventEmitted`, vision §2.4) фиксируются; фильтрация утечек работает
- Перечень типов данных, блокируемых фильтрацией утечек (2026-08-30): токены/ключи (API-ключи, пароли, JWT, приватные ключи), ПДн (персональные данные при попадании в промпты/ответы); детектор — правила (regex/энтропия) + классификатор (реализация); детерминированная проверка — негативные E2E-кейсы «промпт с секретом/ПДн (блок + аудит)» (e2e-api §11.7)

> Граница с BR-constraint.sso-readonly-access: RBAC отсутствует (один пользователь по умолчанию, ролей нет), запросы — только на чтение; аудит обращений к LLM на уровне контура безопасности — действует (включая события фильтрации утечек).
