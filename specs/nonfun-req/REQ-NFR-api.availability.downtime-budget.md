## Описание

Система — производная вспомогательная (индекс поверх источника правды), не критичная: допустимый простой — **15 минут в день суммарно на инстанс** (planned + unplanned). Исходные артефакты не хранятся в системе (источник правды — GitLab/S3, вне системы) → RPO для исходников равен 0. Индекс — производный, не самоценность: восстанавливается полной перестройкой (фоновая) или из снапшота, отдельные RPO-гарантии на индекс не устанавливаются.

**Процедура восстановления (подтверждена владельцем 2026-08-30):** остановка инстанса (или переключение трафика) → восстановление из бэкапа (`neo4j-admin database load` / dump) → перезапуск → при необходимости smoke-прогон K1/K4/K5/K17. Восстановление из опубликованного снапшота (`REQ-NFR-data.maintainability.versioned-provenance`) быстрее полной перестройки; если перестройка неизбежна, время может превысить 15 мин — поэтому приоритетный путь — откат к снапшоту.

## Критерии приёмки

- Бюджет простоя: ≤ 15 мин/день суммарно на инстанс (плановые и внеплановые окна); «система не критичная» — без строгого SLA на месячную доступность
- RPO: 0 для исходных артефактов (они в GitLab/S3, система — индекс и контекст, vision §2.7 п.1); потери состояния индекса допустимы — восстановление полной перестройкой
- RTO: восстановление обслуживания запросов ≤ 15 мин на инцидент (в рамках дневного бюджета); при наличии опубликованного снапшота — откат к предыдущей версии без перестройки (`REQ-NFR-data.maintainability.versioned-provenance`); приоритетный путь восстановления — из dump/снапшота (`neo4j-admin database load`), полная перестройка — только при отсутствии снапшота
- Восстанавливаемость подтверждается автотестом: restore-тест в CI — развёртывание из бэкапа (dump Neo4j) → прогон эталонных кейсов K1/K4/K5/K17; **критерий успеха — все 4 теста проходят на восстановленном индексе**: K1 (базовый вопрос по спеке/коду со ссылкой на артефакт), K4 (глобальный поиск, синтез ответа из нескольких источников), K5 (трассируемость «где реализовано требование X»), K17 (компиляция JSON-контекста для генерации). Периодичность (решение владельца 2026-08-30): ежеквартально — минимальная; дополнительно — после каждого крупного обновления (изменение схемы графа, замена хранилища) и перед каждым релизом
- Откат неудачного обновления проверяется тестами (negative-сценарии обновления, версионные снапшоты)
