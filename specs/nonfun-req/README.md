# Нефункциональные требования — GraphRAG

В этой директории хранятся формализованные нефункциональные требования (NFR) к проекту **GraphRAG** — корпоративной системы знаний на базе ontology-grounded GraphRAG: evidence-based context layer / context compiler для ИИ-агентов автоматизации разработки. NFR задают ограничения качества (безопасность, производительность, точность, доступность, наблюдаемость) поверх функциональных требований из `fun-req/` (каталог планируется).

Методологическая основа: Software Requirements Engineering (Wiegers & Beatty, 3rd ed.) — трёхуровневая модель требований (business → user → functional/nonfunctional) и цикл разработки требований (Elicitation → Analysis → Specification → Validation). NFR покрывают два класса из таксономии W&B: **атрибуты качества** (измеримые свойства: безопасность, производительность, точность) и **ограничения** (на выбор разработчика: стек, хранилище, контур LLM).

> **Статус:** проект находится на этапе видения (Фаза 0), `src/` не содержит реализации; каталог вводится с нуля. На 2026-08-29 в каталоге **11 NFR** — сквозные требования перенесены из `vision.md` §2.5 для устранения дублирования; NFR отзывчивости/актуальности индекса и агентского контура добавлены по итогам фиксации ADR (инкрементальное обновление со снапшотами, agent gateway); кандидаты на новые области — в разделе «Текущее состояние».

## Иерархия требований

Требования организованы по трём уровням (W&B: Business / User / Functional requirements):

```
specs/nonfun-req/ — нефункциональные требования (NFR): измеримые границы качества поверх FR; сквозные требования из vision.md §2.5 перенесены сюда
└─ REQ-NFR-<area>.<qualifier>.<attribute>.md — отдельные NFR (по одному файлу на требование)

NFR управляются требованиями проекта GraphRAG (specs/):
├─ vision.md — бизнес-требования (Business): SMART-цели G1–G7, проблемы P1–P6, функции F1–F4, сквозные NFR-* §2.5, ограничения §2.7
├─ use-cases/ — пользовательские требования (User): полное описание поведения системы (UC)
├─ user-stories/ — пользовательские истории (подмножество поведения, Gherkin) → US-*
├─ fun-req/ — функциональные требования (FR) — каталог планируется
├─ business-rules/ — бизнес-правила (BR-*): политики, на которые ссылаются NFR
├─ qa/ — контроль качества: тестирование NFR (§7)
├─ domain/ — DDD-модели: ограниченные контексты, инварианты
├─ adr/ — архитектурные решения (ADR): trade-offs атрибутов качества
├─ glossary.md — глоссарий: единый язык предметной области
└─ open-questions.md — открытые вопросы по требованиям (лакуны)
```

Связи между артефактами:

- **NFR задают измеримые границы качества** для FR и архитектурных решений: NFR выводятся из бизнес-целей (G1–G7), проблем (P1–P6) и ограничений `vision.md` §2.7, а не из UC.
- **NFR не дублируют функциональность**: поведение описывают FR; NFR ограничивают его качество. Если ограничение относится к конкретному FR, NFR ссылается на него (перекрёстная трассировка FR ↔ NFR).
- **NFR не порождают пользовательских историй**: US выводятся из UC; границы качества не описываются историями.
- **Бизнес-правила (`BR-*`) — отдельный актив** (W&B: enterprise-level asset): политики и ограничения хранятся в [business-rules/](../business-rules/README.md); NFR ссылаются на них, но не включают их текст (например, `REQ-NFR-security.compliance.llm-contour` ← `BR-constraint.data-stays-in-perimeter`).

## NFR в жизненном цикле требований

NFR выявляются на стадии **Analysis** (шаг 7 процесса W&B: «analyze requirements for quality attributes and business rules») и специфицируются на стадии **Specification**. Стадии цикла W&B применяются к NFR так:

| Стадия | Что делаем с NFR |
|--------|------------------|
| **Elicitation** | Выявление атрибутов качества и ограничений из бизнес-целей (G1–G7), проблем (P1–P6) и ограничений §2.7 `vision.md`; сквозные требования §2.5 — базовый набор для MVP |
| **Analysis** | Отделение NFR от FR и бизнес-правил; определение относительной важности атрибутов качества (trade-offs) |
| **Specification** | Оформление по шаблону: ID, приоритет, источник, связанные функции, описание, измеримые критерии приёмки |
| **Validation** | Проверка измеримости (метрика + целевое значение), ревью (чек-лист дефектов ниже), тесты производительности/безопасности (`qa/` §7) |

## Формат идентификатора NFR

```
REQ-NFR-<area>.<qualifier>.<attribute>
```

Где:

| Часть | Описание |
|-------|----------|
| **area** | Область ограничения: `api` · `security` · `data` · `infra` · `ui` · `ops` · `integration` · `process` · `doc` |
| **qualifier** | Категория качества: `performance` · `availability` · `observability` · `compliance` · `maintainability` |
| **attribute** | Конкретный атрибут качества в kebab-case (ограничение) |

> **Области и квалификаторы — допустимые значения** из таксономии выше. Фактическое покрытие — в разделе «Текущее состояние»: NFR заводятся по мере выявления атрибутов качества, поэтому часть областей/квалификаторов может быть пустой.

### Правила именования

1. **area** — строго из списка областей (lowercase).
2. **qualifier** — строго из списка категорий качества (lowercase).
3. **attribute** — свободная англоязычная метка в kebab-case, отражающая суть ограничения.
4. Идентификатор устойчив: добавление или удаление NFR не меняет ID существующих требований; имя файла совпадает с ID: `REQ-NFR-<area>.<qualifier>.<attribute>.md`.

## Правила оформления

1. **Один файл — одно нефункциональное требование.**
2. **Имя файла**: `REQ-NFR-<area>.<qualifier>.<attribute>.md` — совпадает с ID требования.
3. **Язык**: русский. Технические термины — на английском.
4. **Обязательные поля**:
   - **Приоритет:** `P0` / `P1` / `P2`
   - **Источник:** ссылка на бизнес-цель (G1–G7), проблему (P1–P6) или ограничение (§2.7) из `vision.md`; для сквозных требований — §2.5
   - **Связанные функции:** ссылка на функцию/подфункцию F1–F4 из `vision.md` §2.2 (если применимо)
   - **Описание:** суть ограничения качества
   - **Критерии приёмки:** измеримые условия выполнения — метрики и целевые значения (без метрики требование не проверяемо)
5. **Рекомендуемые поля** (атрибуты требований, W&B Chapter 27):
   - **Статус:** `proposed` → `approved` → `implemented` → `verified` → `deleted` (отслеживание статуса)
   - **Связанные требования:** ссылки на родственные FR и `BR-*` (перекрёстная трассировка FR ↔ NFR)
6. **TBD-флаг**: пробелы в требовании помечаются `TBD` и фиксируются в [open-questions.md](../open-questions.md) — требование не считается готовым, пока TBD не закрыт.
7. **Трассируемость**: каждый NFR ссылается на источник в поле «Источник» — цель (G1–G7), проблему (P1–P6) или ограничение (§2.7) из `vision.md`; связанные функции указываются в поле «Связанные функции» (F1–F4). Forward-трассировка: NFR → тесты (производительность, безопасность — `qa/` §7) и реализация.

## Приоритеты

Приоритет определяет порядок реализации (W&B: prioritization по ценности, стоимости и риску):

- **P0** — критическое: без него MVP невозможен или небезопасен (например, `REQ-NFR-security.compliance.llm-contour` — безопасный контур LLM, `REQ-NFR-api.compliance.rag-accuracy` — точность ответов ≥ 70% как порог продолжения внедрения)
- **P1** — важное: ключевое ограничение качества (например, `REQ-NFR-api.performance.token-minimization` — минимизация токенов и LLM-вызовов, `REQ-NFR-process.compliance.human-confirmation` — «агент готовит — человек подтверждает», `REQ-NFR-data.maintainability.ontology-model` — модель предметной области)
- **P2** — желательное: улучшает качество, но не блокирует выпуск (например, `REQ-NFR-process.maintainability.adoption-principles` — принципы внедрения)

## Критерии качества NFR

Каждое NFR должно удовлетворять характеристикам отличного требования (W&B, Chapter 2); для NFR решающая характеристика — **проверяемость**: без метрики и целевого значения NFR не является требованием:

| Характеристика | Значение для NFR | Как проверить |
|----------------|------------------|---------------|
| **Verifiable** (проверяемость) | Метрика и целевое значение заданы («≥ 70%», «медиана и p90») | Замер/тест по критериям приёмки (`qa/` §7) |
| **Unambiguous** (однозначность) | Конкретные числа вместо «быстро», «надёжно», «удобно» | Ревью: отсутствие размытых формулировок |
| **Complete** (полнота) | Охвачены все режимы/сценарии, к которым применимо | Перечень сценариев и каналов полон |
| **Necessary** (необходимость) | Выводится из бизнес-цели/проблемы/ограничения | Трассировка NFR → G/P → §2.7 |
| **Feasible** (реализуемость) | Целевое значение достижимо в рамках архитектуры | Оценка разработкой (ADR, прототип) |
| **Prioritized** (приоритизированность) | Указан приоритет P0/P1/P2 | Наличие поля «Приоритет» |
| **Correct** (корректность) | Не конфликтует с FR и другими NFR | Сверка; учёт trade-offs атрибутов качества |

**Набор NFR** должен быть: **complete** (покрытие всех значимых атрибутов качества — см. «Текущее состояние»), **consistent** (нет противоречий между атрибутами — trade-offs разрешены и зафиксированы), **modifiable** (уникальные ID, изменения отслеживаются), **traceable** (backward: NFR → G/P/§2.7; forward: NFR → тесты/реализация).

## Типичные дефекты NFR при ревью

Чек-лист валидации (W&B defect checklist). Главный дефект NFR — **непроверяемость**:

| Дефект | Признак | Действие |
|--------|---------|----------|
| Непроверяемость | Нет метрики/целевого значения («быстрая работа», «высокая надёжность») | Ввести измеримый критерий или удалить |
| Неоднозначность | «Надёжный», «удобный», «минимальный» без числа | Конкретизировать числом или границей |
| Противоречивость | Конфликт с FR или другим NFR (trade-off не разрешён) | Согласовать, зафиксировать решение в ADR |
| Неполнота | Покрыта не вся область (сценарий, канал, режим) | Дополнить или пометить `TBD` |
| Нереализуемость | Целевое значение недостижимо в рамках ограничений | Пересмотреть цель, обосновать в ADR |
| Нет источника/приоритета | Отсутствует трассировка или P0–P2 | Восстановить по G/P/§2.7 |
| Gold plating | Избыточное качество без бизнес-обоснования | Удалить или понизить до P2 |

## Специфика проекта

- **Контур знаний — контекст исполнения**: NFR описывают ограничения компонентов GraphRAG (ядро, оркестрация пайплайнов индексации, движок запросов, MCP-сервер, веб-интерфейс, интеграции) внутри защищённого контура организации. Внешние системы (GitLab, внешнее хранилище документов, контур LLM, ИИ-агенты автоматизации разработки) — контракты; их внутренние NFR вне контура.
- **Атрибуты качества и ограничения** (W&B таксономия): NFR покрывают измеримые атрибуты качества (безопасность, производительность, точность, доступность, наблюдаемость) и ограничения на выбор разработчика (стек — Go, хранилище графа и векторного индекса, контур LLM). Ограничения фиксируются в NFR и ADR, а не в FR.
- **Trade-offs атрибутов качества**: атрибуты могут конфликтовать (безопасность vs производительность, точность vs полнота контекста при минимуме токенов). Относительная важность фиксируется приоритетом NFR и решениями ADR; неразрешённый конфликт — дефект набора.
- **Метрики-прокси, а не «отсутствие инцидентов»**: защищённость и качество измеряются проверяемыми показателями — точность ответов RAG ≥ 70% (`REQ-NFR-api.compliance.rag-accuracy`), доля обращений к LLM через корпоративный канал (G6), время от изменения источника до обновления индекса (G2), число противоречий (G3), полнота контекста при минимуме токенов (F3). Целевые значения уточняются после замера исходного уровня (`vision.md` §1.4).
- **Сквозные требования §2.5**: `REQ-NFR-security.compliance.llm-contour`, `REQ-NFR-api.performance.token-minimization`, `REQ-NFR-api.compliance.rag-accuracy`, `REQ-NFR-process.compliance.human-confirmation`, `REQ-NFR-data.maintainability.ontology-model`, `REQ-NFR-process.maintainability.adoption-principles` — входят в MVP, не являются функциями и F-кодов не получают (канон нумерации функций, §2.2).
- **Безопасность эшелонированно**: предотвращение → обнаружение → реагирование; контур LLM — фильтрация утечек и аудит обращений (событие `SecurityEventEmitted`, `vision.md` §2.4); данные разработки (код, спеки) не покидают периметр; система не оператор ПДн (`vision.md` §2.7 п.12; `REQ-NFR-security.compliance.llm-contour`).
