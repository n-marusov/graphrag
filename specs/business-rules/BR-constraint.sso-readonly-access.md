## Формулировка правила

Доступ людей к системе — через **корпоративный SSO (Keycloak, OIDC)**; по умолчанию добавлен **один пользователь `User`**; **ролей нет** (RBAC не вводится); **все запросы — только на чтение** (read-only: никаких write-операций через API/UI/MCP). ИИ-агенты автоматизации разработки подключаются **по токену** (агентский токен, выдаётся через корпоративный процесс) через MCP-канал (F4). Аудит действий пользователя — на уровне SSO (кто обращался); аудит обращений к LLM на уровне контура безопасности (`SecurityEventEmitted`) действует в полном объёме.

**Граница:** read-only-режим не отменяет сквозное требование `REQ-NFR-security.compliance.llm-contour` — фильтрация утечек, аудит и события безопасности контура остаются в силе; развёртывание — только в доверенном периметре.

## Обоснование

ИИ-агенты могут обращаться и через человеческий шлюз (API Gateway), поэтому аутентификация людей необходима уже в MVP (решение владельца продукта, 2026-08-30). RBAC не нужен: система — внутренняя, read-only, единый пользователь; роли могут быть добавлены в будущих версиях при появлении write-операций или административных функций. Прежнее правило «авторизация отсутствует в MVP» (`BR-constraint.no-user-auth-in-mvp`) заменено: без аутентификации нельзя отличить агента от человека на общем шлюзе.

## Критерии проверки

- В контракте API отсутствуют write-эндпоинты (создание/изменение/удаление данных системы); перечень эндпоинтов — только чтение (детерминированная сверка по OpenAPI-схеме)
- Запрос человека без валидного OIDC-токена SSO → отказ с кодом ошибки; неавторизованная попытка фиксируется
- Агентский запрос через MCP без валидного токена → отказ с кодом ошибки (UC-mcp A1)
- В системе ровно один пользователь по умолчанию (`User`); ролей/прав нет (нет RBAC-модели)
- События фильтрации утечек и аудита контура LLM (`SecurityEventEmitted`) фиксируются по-прежнему
- Действия пользователя (кто обратился, когда) воспроизводятся по журналу SSO/API Gateway
