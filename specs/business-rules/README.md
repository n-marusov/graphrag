# Бизнес-правила — GraphRAG

В этой директории описываются бизнес-правила (Business Rules, `BR-*`) проекта **GraphRAG** — корпоративной системы знаний на базе ontology-grounded GraphRAG: evidence-based context layer / context compiler для ИИ-агентов автоматизации разработки. Каждое правило — политика, стандарт или регуляция, управляющая поведением контура знаний и его взаимодействием с внешними системами (например, запрет на вынос данных разработки за периметр, обязательная привязка ответов к источникам, единые определения терминов).

Каталог — **enterprise-level актив** (W&B): каждое правило ведётся как отдельный файл в этой директории (`BR-<тип>.<семантический-тег>.md`), на правила ссылаются по ID все производные артефакты (vision, UC, US, QA, DDD, ADR). Данный README — методология, формат, критерии качества и навигация по артефакту.

Методологическая основа: Software Requirements Engineering (Wiegers & Beatty, 3rd ed.) — таксономия типов требований (business rule — отдельный тип, источник требований) и цикл разработки требований (Elicitation → Analysis → Specification → Validation). Референс: [software-requirements-wiegers-beatty.md](../../.ai-factory/references/software-requirements-wiegers-beatty.md).

> **Статус:** проект находится на этапе видения (Фаза 0), `src/` не содержит реализации; каталог вводится с нуля. На 2026-08-29 в каталоге **3 правила**. Кандидаты и целевые типы — в разделе «Текущее состояние»; реверс-инжиниринг кода применим после появления реализации в `src/`.

## Принципы работы с бизнес-правилами

Принципы заимствованы из Software Requirements Engineering (Wiegers & Beatty) — разделы Core Concepts, Requirements Development Process Framework, Analysis, Specification, Agile Projects:

| Принцип | Содержание (W&B) | Как применяем в проекте |
|---------|------------------|-------------------------|
| **Правило — не требование** | Business rule — политика, стандарт, регуляция; это **не требование к ПО**, а источник, из которого выводятся функциональные и нефункциональные требования | Правила живут вне FR/NFR; функциональность и границы качества из них *выводятся* (например, `BR-constraint.web-app-browser-chat` → FR/UC F1.1) |
| **Отличать от Constraint** | Constraint — ограничение на выбор разработчика (дизайн, платформа, язык); business rule — на поведение организации/продукта | Ограничения стека и инфраструктуры — в ADR (уровень `IMPL`) и NFR; политики — в `BR-*` |
| **Enterprise-level актив** | Правила принадлежат организации, а не отдельному проекту; переиспользуются всеми проектами | Директория `business-rules/` — единый источник; ссылки по ID из vision, UC, US, QA, DDD, ADR |
| **Хранение отдельно от требований** | «Record business rules — отдельно от требований» (Specification practice); в SRS правила не включаются, на них ссылаются | FR/NFR/UC/US ссылаются на `BR-*` по ID, но не содержат текст правил |
| **Выявление — шаг 7 процесса** | «Analyze requirements for quality attributes and business rules» — выявление НФТ и бизнес-правил на старте проекта (шаги 1–7 выполняются однократно) | При декомпозиции UC и vision.md правила выявляются вместе с NFR |
| **Отделение на Analysis** | Отделение функциональных требований от целей, ожиданий качества, бизнес-правил и предлагаемых решений — обязательное действие анализа | Новые правила оформляются отдельно от FR, с собственным ID |
| **Декларативная формулировка** | Правило формулируется в терминах предметной области, без указания способа реализации | «Каждый ответ подтверждается ссылками на источники», а не «формировать список ссылок в движок запросов при генерации» |
| **Происхождение и устойчивые ID** | Записывать origin каждого требования; уникальная метка, устойчивая к добавлениям/удалениям | У каждого правила ID `BR-<тип>.<тег>` и источник; ID не меняется при правках каталога |
| **Трассируемость** | Backward: от артефакта к правилу; forward: от правила к реализации | FR/NFR/UC → `BR-*` (backward), `BR-*` → код в `src/` (forward) |
| **Не меняется в agile** | Business rules — хранятся отдельно, enterprise-level; даже в agile-процессах правило не становится user story | Правила не порождают US и не «размываются» по итерациям |

## Иерархия требований

В модели W&B бизнес-правила находятся **над** проектом: они не принадлежат ни одному из трёх уровней требований (Business / User / Functional), а управляют всеми уровнями:

```
specs/business-rules/ — бизнес-правила (BR-*): политики, стандарты, регуляции (enterprise-level)
├─ README.md — методология, формат, критерии качества, навигация
└─ BR-<тип>.<семантический-тег>.md — отдельные правила (по одному файлу на правило)

Правила управляют требованиями проекта GraphRAG (specs/):
├─ vision.md — бизнес-требования (Business): SMART-цели G1–G7, проблемы P1–P6, функции F1–F4, MVP, roadmap
├─ use-cases/ — пользовательские требования (User): полное описание поведения системы (UC)
├─ user-stories/ — пользовательские истории (подмножество поведения, Gherkin) → US-*
├─ fun-req/ — функциональные требования (FR) — каталог планируется
├─ nonfun-req/ — нефункциональные требования (NFR): сквозные REQ-NFR-* из vision.md §2.5 перенесены в каталог
├─ qa/ — контроль качества: тест-планы, гейты, матрица качества
├─ domain/ — DDD-модели: ограниченные контексты, инварианты
├─ adr/ — архитектурные решения (ADR)
├─ c4/ — C4-модель (context.md — уровень 1)
├─ glossary.md — глоссарий: единый язык предметной области
└─ open-questions.md — открытые вопросы по требованиям (лакуны)
```

Связи между артефактами:

- **BR — источник требований**: FR и NFR выводятся из политик и ограничений (например, `BR-constraint.data-stays-in-perimeter` → REQ-NFR-security.compliance.llm-contour, `BR-constraint.cited-answer` → FR/UC F1.1).
- **Артефакты ссылаются на BR по ID**: UC, US, FR, NFR, DDD-модели и ADR ссылаются на `BR-*`, но не включают текст правил (W&B: правила хранятся отдельно).
- **US не трассируются на BR**: пользовательские истории выводятся из UC; правила реализуются через FR/NFR, а не через истории.
- **Правила-ограничения = инварианты DDD**: ограничивающие правила фиксируются как инварианты ограниченных контекстов в [domain/](../domain/README.md) (например, контур LLM: данные разработки не покидают периметр).

## BR в жизненном цикле требований

Выявление и спецификация BR — часть цикла W&B (Elicitation → Analysis → Specification → Validation). Стадии применяются к BR так:

| Стадия | Что делаем с BR |
|--------|-----------------|
| **Elicitation** | Выявление политик, стандартов и регуляций из vision.md (функции §2.2, ограничения §2.7, допущения §2.8), интервью и документации; в 17-шаговом процессе W&B — шаг 7 «analyze requirements for quality attributes and business rules» |
| **Analysis** | Отделение BR от FR, NFR и предлагаемых решений; декларативная формулировка в терминах предметной области; проверка необходимости и непротиворечивости |
| **Specification** | Ведение файлов правил в этой директории (по одному файлу на правило): ID, тип, формулировка, приоритет, критерии проверки, источник |
| **Validation** | Ревью (критерии качества и чек-лист дефектов ниже); сверка, что правило не продублировано в FR/NFR |
| **Management** | Изменение правила — через процесс управления изменениями (W&B Chapter 28): оценка влияния (impact analysis) на все производные артефакты; статус правила отслеживается |

## Формат идентификатора BR

```
BR-<тип>.<семантический-тег>
```

| Часть | Описание | Допустимые значения |
|-------|----------|---------------------|
| **тип** | Тип правила (см. «Типы правил» ниже) | `fact` · `constraint` · `trigger` · `inference` |
| **семантический-тег** | Англоязычная метка в kebab-case, отражающая суть правила | свободная семантическая метка |

### Правила именования

1. Только **kebab-case**, без цифр и индексов.
2. Тип — строго из списка типов правил.
3. Семантический тег — свободная метка, отражающая суть конкретного правила.
4. Идентификатор устойчив: добавление или удаление правил не меняет ID существующих правил.

### Примеры

| ✅ Корректно | ❌ Некорректно |
|---|---|
| `BR-constraint.web-app-browser-chat` | `BR-UI-01` (содержит номер) |
| `BR-fact.gitlab-authoritative` | `BR-fact.GitLabAuthoritative` (не kebab-case) |
| `BR-inference.impact-computed` | `BR-constraint.1` (содержит номер) |

## Типы правил

Таксономия — классическая типология бизнес-правил (W&B, Chapter 5; Business Rules Group; принятая в RE-практике). Правила классифицируются **по природе утверждения**, а не по предметной области: таксономия ортогональна доменам и покрывает любые политики — в том числе о форме продукта и каналах доступа.

| Код | Тип | Определение | Пример |
|-----|-----|-------------|--------|
| `fact` | Факт | Утверждение о предметной области, истинное для организации/продукта | «GitLab — эталонный источник корпуса; Confluence исключён» |
| `constraint` | Ограничение | Требуемое, запрещённое или ограниченное действие; вычислительные ограничения | «Каждый ответ подтверждается ссылками на источники»; «Авторизация не входит в MVP» |
| `trigger` | Триггер | Событие, инициирующее действие системы | «Изменение в GitLab → инкрементальное обновление графа» |
| `inference` | Вывод | Логическое следствие из фактов (если A, то B) | «Если артефакт изменён, список затронутых артефактов детерминирован» |

> **Не путать с W&B «Constraint».** Тип `constraint` в этой таксономии — подтип бизнес-правила (ограничение на поведение продукта). В таксономии требований W&B «Constraint» — отдельный тип (ограничение на выбор разработчика: дизайн, платформа, язык); такие ограничения фиксируются в ADR/NFR, а не в `BR-*`.

## Правила оформления

1. **Один файл — одно правило**: каждое правило ведётся отдельным файлом `BR-<тип>.<семантический-тег>.md` в этой директории; изменения вносятся только в файл правила, производные артефакты обновляются по ссылке.
2. **Имя файла**: `BR-<тип>.<семантический-тег>.md` — совпадает с ID правила; ID и приоритет задаются в файле правила.
3. **Язык**: русский. Технические термины — на английском.
4. **Обязательные поля** (файл правила): ID, тип правила (`fact` / `constraint` / `trigger` / `inference`), формулировка правила, приоритет (`High` / `Medium` / `Low`), критерии проверки (Verifiable: как объективно проверить соблюдение).
5. **Рекомендуемые поля** (атрибуты требований, W&B Chapter 27): источник (origin), статус `proposed` → `approved` → `implemented` → `verified` → `deleted`, обоснование, связанные требования (`FR-*` / `NFR-*` / `UC-*`), источник в коде (`src/`).
6. **Источник — реверс-инжиниринг кода**: правила восстанавливаются из реализации (`src/`); поле «Источник в коде» фиксирует файлы и символы, по которым правило извлечено. До появления реализации (этап видения, Фаза 0) правила выводятся из vision.md и фиксируются как `to be`; для таких правил в поле «Источник» указывается vision.md и фазовый контекст.
7. **TBD-флаг**: пробелы в правиле помечаются `TBD` и фиксируются в [open-questions.md](../open-questions.md) — правило не считается готовым, пока TBD не закрыт.
8. **Устойчивость ID**: добавление/удаление правил не меняет ID существующих. Каталог вводится с нуля — легаси-идентификаторов BR нет; при будущем рефакторинге ID таблица маппинга добавляется в этот README (по аналогии с маппингом схемы функций F1–F7 на канон F1–F4 в [open-questions.md](../open-questions.md) Q1.1).

## Приоритеты

Приоритет выражает значимость правила для бизнеса (W&B: prioritization по ценности, стоимости и риску). В отличие от FR/NFR (шкала P0–P2), правила каталога используют шкалу **High / Medium / Low** — приоритет указывает значимость ограничения, а не порядок реализации:

- **High** — критичные политики и ограничения: нарушение ведёт к потере доверия к ответам, утечке данных или блокировке MVP (например, `BR-constraint.no-user-auth-in-mvp`, `BR-constraint.web-app-browser-chat`, `BR-constraint.data-stays-in-perimeter`, `BR-constraint.cited-answer`)
- **Medium** — важные правила, обеспечивающие согласованность и предсказуемость (например, `BR-constraint.backend-cli-queries`, `BR-inference.impact-computed`, `BR-constraint.compiled-not-raw`)
- **Low** — желательные политики, улучшающие эксплуатацию (например, политика ведения реестра синонимов терминов)

## Критерии качества BR

Каждое правило должно удовлетворять характеристикам отличного требования (W&B, Chapter 2) — с учётом того, что правило формулируется декларативно, в терминах предметной области:

| Характеристика | Значение для BR | Как проверить |
|----------------|-----------------|---------------|
| **Verifiable** (проверяемость) | Соблюдение правила можно объективно проверить | Тест, анализ или демонстрация; сверка с кодом; критерии проверки в файле правила |
| **Unambiguous** (однозначность) | Одна интерпретация у всех читателей | Ревью; отсутствие «и т. п.», «как правило», «быстро» |
| **Complete** (полнота) | Вся информация для понимания на месте; пробелы помечены `TBD` | Нет нераскрытых терминов; TBD заведены в реестр |
| **Necessary** (необходимость) | Есть ответ «почему это нужно» — трассировка до бизнес-цели | Цепочка BR → F → G (G1–G7) |
| **Feasible** (реализуемость) | Реализуемо в рамках известных ограничений платформы | Оценка разработкой/архитектурой (ADR) |
| **Prioritized** (приоритизированность) | Указан приоритет High/Medium/Low | Наличие поля «Приоритет» |
| **Correct** (корректность) | Описывает реальную политику, не конфликтует с другими правилами и NFR | Сверка с каталогом, NFR и кодом |

**Набор BR** должен быть: **complete** (покрытие всех типов — см. «Текущее состояние»), **consistent** (нет противоречий между правилами), **modifiable** (уникальные ID, изменения отслеживаются), **traceable** (backward: FR/NFR → BR; forward: BR → код/тесты).

## Типичные дефекты BR при ревью

Чек-лист валидации (W&B defect checklist) с учётом специфики бизнес-правил:

| Дефект | Признак | Действие |
|--------|---------|----------|
| Правило-функция | Сформулировано как FR или с деталями реализации («система должна…», «проверять при…») | Переформулировать декларативно или перенести в FR |
| Неоднозначность | Разные читатели понимают по-разному | Переформулировать, убрать размытые слова |
| Противоречивость | Конфликт с другим правилом или NFR | Согласовать, зафиксировать решение |
| Непроверяемость | Соблюдение нельзя объективно проверить | Ввести проверяемое условие (критерии проверки) |
| Нет источника/приоритета | Отсутствует происхождение или High/Medium/Low | Восстановить по vision.md и каталогу |
| Дублирование | Правило продублировано текстом в FR/NFR | Убрать из FR/NFR, оставить ссылку на `BR-*` |
| Gold plating | Политика «на всякий случай» без бизнес-обоснования | Удалить или понизить приоритет |
| Неверный тип | Тип не соответствует природе утверждения (например, требование записано как `fact`) | Переклассифицировать: требование → `constraint`, вывод → `inference` и т. п. |

## Специфика проекта

- **Контур знаний — контекст исполнения**: правила описывают поведение компонентов GraphRAG (ядро, оркестрация пайплайнов индексации, движок запросов, MCP-сервер, веб-интерфейс, интеграции) внутри защищённого контура организации и контракты взаимодействия с внешними системами (GitLab, внешнее хранилище документов, контур LLM, ИИ-агенты автоматизации разработки). Внутренние функции внешних систем правилами не описываются.
- **Каноничный источник**: изменения бизнес-правил вносятся только в файлы правил этой директории; производные документы (vision, UC, US, QA, DDD-модели, ADR, C4) ссылаются на правила по ID и обновляются по ссылке.
- **Правило, а не функция**: правила-ограничения (например, «данные разработки не покидают периметр») не становятся функциями F1–F4 или прецедентами — они фиксируются как инварианты ограниченных контекстов и сквозные требования (NFR-*, vision.md §2.5).
- **Связь с DDD**: правила выступают инвариантами ограниченных контекстов (например, контур LLM: `SecurityEventEmitted` → фильтрация утечек и аудит); модели — в [domain/](../domain/README.md).
- **Этап видения**: проект на этапе видения (Фаза 0), `src/` не содержит реализации; правила выводятся из vision.md (§2.5 NFR, §2.7 ограничения, §2.8 допущения) и решений владельца продукта, фиксируются как `to be`; реверс-инжиниринг кода применим после появления реализации.
- **Источники правил в коде**: соответствие «правило → код» (`src/`) для правил, извлечённых из реализации, фиксируется полем «Источник в коде» в файлах правил.
