# C4-диаграммы — GraphRAG

В этой директории хранятся архитектурные диаграммы проекта **GraphRAG** — корпоративной системы знаний на базе ontology-grounded GraphRAG (evidence-based context layer / context compiler для ИИ-агентов автоматизации разработки) в нотации C4. Проект находится на этапе видения: кодовой базы нет (в `src/` размещён только README), поэтому диаграммы уровней 2–4 описывают целевую архитектуру (`target`) и создаются по мере фиксации проектных решений; после появления реализации в `src/` актуализируются до `as-is` по фактическому коду.

## Уровни C4

| Уровень | Назначение | Аудитория |
|---------|-----------|-----------|
| **1. System Context** | [context.md](context.md) — система и её внешние акторы: архетипы пользователей (команда разработки, эксплуатация и безопасность; руководство — в примечаниях), ИИ-агенты автоматизации разработки; внешние системы: GitLab, внешнее хранилище документов, контур LLM | Бизнес, продукт |
| **2. Container** | [container.md](container.md) — крупные исполняемые блоки системы: ядро, оркестрация пайплайнов индексации, движок запросов, MCP-сервер, веб-интерфейс, интеграции | Архитекторы, разработчики |
| **3. Component** | Компоненты по контейнерам: `component-core.md` (ядро), `component-indexing.md` (индексация), `component-query.md` (движок запросов), `component-mcp.md` (MCP-сервер), `component-ui.md` (веб-интерфейс), `component-integrations.md` (интеграции) | Разработчики |
| **4. Code** | Декомпозиция поведения компонентов до классов/модулей: автоматы состояний — `code-indexing-pipeline.md` (пайплайн индексации), `code-query-behavior.md` (обработка запроса) | Разработчики (обычно опускается) |
| **Deployment** (отдельный тип диаграммы) | Физическое развёртывание: защищённый контур организации, локальные GPU, репозиторий GitLab, хранилище графа и векторного индекса | DevOps, архитекторы |

> **Статус:** в директории размещены `README.md` (правила и индексы), `context.md` (уровень 1), `container.md` (уровень 2), `code-indexing-pipeline.md` и `code-query-behavior.md` (уровень 4, диаграммы поведения, target); остальные файлы диаграмм уровней 3–4 — плановая работа и создаются по мере фиксации проектных решений (см. «Специфика проекта»).

## Правила именования файлов

Файлы именуются по шаблону `<LEVEL>.md`, где `LEVEL` = `context` | `container` | `component` | `code` | `deployment`. При необходимости нескольких диаграмм одного уровня используется шаблон `<LEVEL>-<name>.md`, где `name` — короткая англоязычная метка в kebab-case. `deployment` — отдельный тип диаграммы (не уровень; уровень 4 — `code`).

Каждый файл диаграммы содержит:

- **Mermaid-диаграмму** в блоке ` ```mermaid `
- **Контекст** — что именно моделируется
- **Фактические компоненты** — с привязкой к пакетам/файлам реализации (`src/`)

## Уровень 3. Компоненты (мастер-индекс)

Документация уровня 3 разбита по контейнерам; по каждому контейнеру — отдельный файл. Контейнеры соответствуют функциям продукта F1–F4 ([`specs/vision.md`](../vision.md) §2.1–2.2, единый канон); механизмы (онтологический слой, контур LLM, инкрементальное обновление) — компоненты внутри контейнеров, а не отдельные контейнеры.

| Документ | Контейнер | Планируемые компоненты |
|----------|-----------|------------------------|
| `component-core.md` | Ядро | Граф знаний, граф зависимостей артефактов, онтологический слой (модель предметной области), компилятор контекста (F3) |
| `component-indexing.md` | Оркестрация пайплайнов индексации | GitLab sync/ingest, S3 ingest, извлечение сущностей/связей/утверждений, инкрементальное обновление графа, пересчёт сообществ (F2) |
| `component-query.md` | Движок запросов | Извлечение контекста (dual-level retrieval, PathRAG, PPR), генерация ответов, grounding/provenance, сверка «результат ↔ источник» (F1) |
| `component-mcp.md` | MCP-сервер | MCP-сервер и инструменты, компиляция контекста для агентов, доставка ответов (F4) |
| `component-api-gateway.md` | API Gateway | Маршрутизация, политики (authN/authZ, rate limiting, квоты), аудит, TLS |
| `component-web-server.md` | Web-сервер (статика) | Раздача hashed-ассетов, кэш-заголовки, SPA-fallback |
| `component-ui.md` | Веб-интерфейс | UI вопросов и ответов, статусы индексации, метрики, отчёты о влиянии изменений (F1, F3) |
| `component-integrations.md` | Интеграции | GitLab-клиент, S3-клиент, клиент контура LLM, CPU-компоненты (Leiden, HNSW, токенизатор) |
| `component-monitoring.md` | Мониторинг и аудит | Сбор логов и метрик, события безопасности (`SecurityEventEmitted`), панели аудита |

> **Примечание:** перечень компонентов — плановый (целевая архитектура); файлы создаются и ссылки в таблице появляются по мере фиксации ADR уровня `IMPL` и появления реализации в `src/`.

## Уровень 4. Code (поведение)

Документация уровня 4 описывает автоматы состояний (поведение) компонентов; по умолчанию строится по фактической реализации в `src/` после появления кода. Документы уровня — `code-indexing-pipeline.md` и `code-query-behavior.md` — созданы по референсам и ADR как `target` (проект на этапе видения) и будут актуализированы до `as is` по мере появления реализации.

| Документ | Контейнер | Поведение |
|----------|-----------|-----------|
| [code-indexing-pipeline.md](code-indexing-pipeline.md) | Оркестрация пайплайнов индексации | Жизненный цикл пайплайна: `DocumentIngested` → `EntityExtracted` → `GraphUpdated` → `CommunityRecomputed`; режимы инкрементального обновления |
| [code-query-behavior.md](code-query-behavior.md) | Движок запросов | Обработка запроса: `QueryReceived` → извлечение контекста → `QueryAnswered` (со ссылками на артефакты); жизненный цикл сверки «результат ↔ источник» |

**Ключевые связи между компонентами (целевая архитектура):**

- Команда обращается к GraphRAG через веб-интерфейс (SPA в браузере) и API Gateway; ИИ-агенты автоматизации разработки — через MCP (`component-mcp.md`).
- API Gateway — единый origin: маршрутизирует `/` (раздача SPA, Web-сервер статики) и `/api/*` (внутренние сервисы); агенты — через MCP-сервер.
- Движок запросов читает граф знаний и векторный индекс ядра; генерация и извлечение исполняются в контуре LLM (внешняя система, чёрный ящик).
- Оркестрация пайплайнов индексации получает изменения из GitLab (Git API / MR / webhook) и внешнего хранилища документов (S3); актуализация базы знаний (F2) — детерминированная задача и не исполняется через MCP (граница F4, `vision.md` §2.2).
- Внутри ядра компоненты связаны через граф зависимостей артефактов; онтологический слой — механизм внутри F1/F3.
- События предметной области (§2.4 `vision.md`) — триггеры каскадов между контейнерами: `DocumentIngested`, `GraphUpdated`, `QueryAnswered`, `InfluenceComputed`, `ContextCompiled`, `SecurityEventEmitted`.

## Специфика проекта

- **Этап «видение»: диаграммы — target.** Проект находится на этапе видения, кодовой базы нет (в `src/` размещён только README). Диаграммы уровней 2–4 описывают целевую архитектуру; после появления реализации актуализируются до `as-is` по фактическому коду. Возможности, не зафиксированные в требованиях, должны быть явно помечены как `planned`/`target`.
- **Внешние системы — чёрные ящики**: GitLab (эталонный источник), внешнее хранилище документов (S3, книги и легаси), контур LLM (локальные GPU), ИИ-агенты. На компонентном уровне показываются только внешние контракты: Git API / MR / webhook, S3 API / события, MCP, Local GPU.
- **Контейнер C4 не равен Docker-контейнеру**: контейнеры GraphRAG — логические исполняемые блоки (Go-сервисы/процессы, единый язык — Go) в защищённом контуре организации.
- **Функции F1–F4 — канон**: контейнеры соответствуют функциям F1–F4 (`vision.md` §2.1–2.2); механизмы (онтологический слой, контур LLM, инкрементальное обновление) и сквозные требования (`NFR-*`, §2.5) контейнерами не являются.
- **Хранилище**: Neo4j (self-hosted, Community Edition), отдельный инстанс на проект + отдельный инстанс глобального слоя (`ADR-IMPL.DATA.graph-storage`, ПРИНЯТО, [`specs/adr/README.md`](../adr/README.md)).
- **Онтологический слой**: машинно-читаемая модель предметной области (онтология) — механизм внутри F1/F3; исходная модель поставляется из репозитория модели, автоматическое построение из корпуса — Фаза 3.
- **Контур LLM**: локальные GPU и open-weight модели — основной вариант исполнения; данные разработки не покидают периметр (REQ-NFR-security.compliance.llm-contour). На диаграммах контур LLM — внешняя система.
