# Пользовательские истории — GraphRAG

В этой директории находятся пользовательские истории (User Stories) проекта **GraphRAG** — корпоративной системы знаний на базе GraphRAG: evidence-based context layer / context compiler для ИИ-агентов автоматизации разработки. Продукт — набор компонентов контура знаний (ядро, оркестрация пайплайнов индексации, query engine, MCP-сервер, веб-интерфейс, интеграции), разворачиваемый в защищённом контуре организации на локальных GPU. Все истории оформлены в формате Gherkin.

**Назначение US.** Пользовательские истории — основа для генерации E2E-тестов (GUI и API) и для общения с представителями бизнеса: каждая история описывает ожидаемое поведение системы глазами пользователя на языке, понятном обеим сторонам. US — подмножество описания поведения системы с фокусом на взаимодействии пользователя с системой; полное описание поведения хранится в прецедентах использования (UC), а UC детализируются в функциональные требования (FR). US описывают только функциональную пользу для пользователя; нефункциональные требования (безопасность контура LLM, доступность, точность ответов, производительность) фиксируются в каталоге `nonfun-req/` и не порождают US.

## Структура

- `README.md` — данный файл с описанием требований к разработке пользовательских историй
- `US-<domain>.<subdomain>.<action>.md` — отдельные файлы пользовательских историй с семантическими идентификаторами

## Семантическая классификация US

Идентификаторы пользовательских историй построены по иерархическому принципу, аналогично UC:

```
US-<domain>.<subdomain>.<action>
```

Домен соответствует функции продукта из [`vision.md`](../vision.md) (F1–F4); поддомен — один пользовательский результат внутри домена. Классификация ортогональна: каждая история относится ровно к одной паре (домен, поддомен), поддомены не пересекаются. Механизмы (онтологический слой, модель предметной области) и NFR-требования доменами US не являются.

### Домены

| Домен | Соотв. функция (vision.md) | Поддомены |
|-------|---------------------------|-----------|
| `US-answers.*` | F1. Генерация проверяемых ответов | `grounding`, `synthesis` |
| `US-knowledge.*` | F2. Индексация источников знаний | `sync`, `ingest` |
| `US-context.*` | F3. Оптимизация контекста для автоматической разработки | `impact`, `build`, `check` |
| `US-mcp.*` | F4. Доставка ответов и контекста через MCP | `access`, `compile` |

### Матрица поддоменов

| Домен.Поддомен | Соотв. функция | Пользовательский результат | Пример | Приоритет |
|---|---|---|---|---|

### Принципы ортогональности

- Каждая история описывает ровно один пользовательский результат и относится ровно к одной паре (домен, поддомен).
- Смежные области разведены по границам:
  - `answers.*` — содержание ответа; `context.build` — содержание контекста для человека; `mcp.compile` — доставка точного набора артефактов агенту через MCP (граница F4, `vision.md` §2.2).
  - `context.check` — сверка результата (артефакта) с источником (Фаза 2, K5).

## Формат описания

Все пользовательские истории оформлены единым Gherkin-шаблоном:

```gherkin
@US-<domain>.<subdomain>.<action> @UC-... @P...
Feature: US-<domain>.<subdomain>.<action> <краткое название>

  Background:
    Given <общие предусловия>

  Scenario: <основной пользовательский результат>
    Given <контекст>
    When <действие пользователя или системы>
    Then <ожидаемый результат>
```

### Теги

Каждая история содержит теги:
- `@US-<domain>.<subdomain>.<action>` — семантический идентификатор пользовательской истории
- `@UC-...` — идентификатор связанного прецедента использования
- `@P0`/`@P1`/`@P2` — приоритет (P0 — критический, P1 — важный, P2 — желательный)
- Дополнительные теги для фильтрации: `@answers`, `@knowledge`, `@context`, `@mcp`; сценарии доступности внутри функциональных историй дополнительно помечаются `@accessibility`

## Требования к разработке пользовательских историй

### 1. Структура и именование

- Каждый файл содержит одну пользовательскую историю или один сквозной сценарий.
- Имя файла соответствует семантическому идентификатору: `US-<domain>.<subdomain>.<action>.md`.
- Файл начинается с заголовка первого уровня (`#`) с полным идентификатором и названием.
- Теги Gherkin указываются в первой строке сценария.
- Идентификатор вешается якорем (`<a id="us-<domain>.<subdomain>.<action>"></a>`) перед заголовком для кросс-ссылок.

### 2. Содержание

- **Background** описывает общие предусловия для всех сценариев истории.
- **Scenario** описывает один конкретный пользовательский результат.
- Шаги `Given` задают контекст и предварительные условия.
- Шаги `When` описывают действие пользователя или системы.
- Шаги `Then` проверяют ожидаемый результат.
- Для проверки альтернативных потоков (негативные сценарии) используется отдельный Scenario.

### 3. Язык

- Все пользовательские истории пишутся **на русском языке**.
- Названия сущностей, свойств и технические идентификаторы — на английском (например, `Document`, `Chunk`, `Knowledge Graph`, `Ontology`, `Grounding`, `Provenance`, `Context Compiler`, `MCP`, `LLM`, `Artifact Graph`, `Security Event`, `hasSource`).
- Сообщения об ошибках, возвращаемые системой, указываются в кавычках на языке системы (английский).

### 4. Приоритеты

- **P0** — критические сценарии, без которых продукт не может быть выпущен: `answers.grounding`, `knowledge.sync`, `context.impact`, `mcp.compile`.
- **P1** — важные сценарии, закрывающие ключевые потребности пользователей: `answers.synthesis` (базовая версия), `knowledge.ingest`, `context.build`, `mcp.access`.
- **P2** — желательные сценарии, улучшающие пользовательский опыт: `answers.synthesis` (полный контур), `context.check`.

### 5. Связи

- US — подмножество описания поведения системы, сфокусированное на взаимодействии пользователя с системой; полное описание поведения хранится в UC.
- UC детализируются в функциональные требования (FR): US не порождают FR напрямую и не трассируются на них.
- Каждая история связана с прецедентом использования (UC), через который восходит к функциям F1–F4 из [`vision.md`](../vision.md).
- Каждая история должна иметь назначенный приоритет.

### 6. Специфика проекта

- **Контур знаний — контекст исполнения**: истории описывают поведение компонентов GraphRAG (ядро, query engine, MCP-сервер, веб-интерфейс) внутри контура знаний организации. Внешние системы — GitLab, PDF-источники, локальный контур LLM, ИИ-агенты автоматизации разработки; истории не описывают их внутренние функции.
- **Функция, а не механизм**: по принципу `vision.md` §2.2 истории — результаты, ценные для пользователя, а не каналы. MCP, REST/CLI, Git API/webhook, модель предметной области (онтологический слой), методы GraphRAG (RAPTOR, StructRAG, PathRAG, PPR, community summaries), векторный индекс — механизмы; они указываются метаданными, а не становятся доменами.
- **События предметной области**: `DocumentIngested`, `GraphUpdated`, `QueryAnswered`, `InfluenceComputed`, `ConflictDetected`, `ContextCompiled`, `SecurityEventEmitted` — триггеры каскадов в контуре знаний, и истории должны явно описывать эти каскады (например, изменение в GitLab → `DocumentIngested` → `GraphUpdated` → новые ответы опираются на актуальную версию источника).

### 7. Accessibility (доступность)

- Истории с тегами `@accessibility` описывают сценарии для пользователей, использующих screen reader (NVDA / VoiceOver) или keyboard-only навигацию.
- Все сценарии доступности должны быть реализованы в соответствии с WCAG MVP.
- Особое внимание — веб-интерфейс системы знаний: ответ со ссылками на источники, статусы индексации и метрики должны иметь текстовые альтернативы, а навигация — keyboard-доступную навигацию.
