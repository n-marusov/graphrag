# Domain baseline for GraphRAG

Эта директория хранит DDD-артефакты для **GraphRAG** — корпоративной системы знаний и evidence-based context layer / context compiler для AI Factory и Hand-off. Доменная модель описывает предметную область GraphRAG: корпус документов, граф знаний, онтологический слой, трассируемость, контекстный режим для ИИ-агентов и контур LLM. Это не каталог для общего поиска по документам и не место для технических компромиссов: границы продукта и non-goals фиксируются в `specs/vision.md`, термины — в `specs/glossary.md`.

> **Статус:** baseline в формировании. В этой директории должны появиться карта контекстов, агрегаты, доменные события и онтология GraphRAG; конкретные границы и связи выводятся из `specs/vision.md` и `specs/glossary.md`.

## Принципы оформления DDD-артефактов

### Именование файлов и идентификаторов

1. **Файлы** — английские имена в kebab-case по шаблону `<artifact>.md`; при нескольких документах одного вида — `<artifact>-<name>.md`.
2. **Ограниченные контексты** — семантические ID в kebab-case; где применимо, согласуются с функциями F1–F4 из `specs/vision.md`.
3. **Агрегаты, сущности, объекты-значения** — PascalCase, в тексте — в backticks (`Document`, `Chunk`, `Claim`, `ArtifactGraph`).
4. **Доменные события** — PascalCase, в backticks (`DocumentIngested`, `QueryAnswered`, `InfluenceComputed`); каталог расширяет `specs/vision.md` §2.4, не дублируя его.
5. **Внешние представления событий** — dotted lowercase (`document.ingested`, `query.answered`, `security.event.emitted`).
6. **Язык** — русский; имена сущностей и технические идентификаторы — на английском.
7. **Термины** — из `specs/glossary.md`; новые понятия сначала фиксируются в глоссарии, затем используются в DDD-артефактах.

### Структура документов

Каждый DDD-артефакт строится на таблицах и списках (сканируемость), без длинных абзацев.

**`context-map.md`**

| Секция | Содержание |
|--------|------------|
| Контексты | Таблица: ID, название (RU), классификация, функции F1–F4 из `specs/vision.md`, ключевые UC, инварианты |
| Отношения контекстов | Таблица «от → к»: тип отношения (ACL / customer-supplier / partnership), механизм взаимодействия |
| Инварианты | Инварианты модели; не пересекают границы контекстов |

**`aggregates.md`**

- Секции по контекстам (`### <Context>`): таблица агрегатов — корень, сущности, объекты-значения, границы транзакций, инварианты.
- Сводная таблица агрегатов всех контекстов.

**`domain-events.md`**

- Каталог событий: триггер, producer, consumer, эскиз payload.
- Матрица каскадов «событие → события».
- Внешние события для интеграций — идемпотентные и повторяемые.

### Принципы моделирования (специфика проекта)

1. **Контекст — граница знаний.** Модель описывает GraphRAG как корпоративную систему знаний: corpus, knowledge graph, ontology layer, context compiler и security contour. Внутренние технические компромиссы не должны проникать в доменную модель.
2. **Источники — через артефакты.** Знания о предметной области приходят из `specs/vision.md` и `specs/glossary.md`; DDD-артефакты фиксируют доменные границы, а не стек.
3. **Функция, а не механизм.** Контексты трассируются к функциям F1–F4 — результатам, ценным для пользователя; алгоритмы и инфраструктурные выборы описываются в архитектурных решениях.
4. **Агрегат — граница транзакционности.** Внешние ссылки на агрегат — только по ID; инварианты не выходят за границы агрегата.
5. **Офлайн-устойчивость.** Инварианты доменной модели не должны зависеть от постоянной связи с внешними провайдерами.
6. **Безопасность эшелонированно.** Контур LLM, фильтрация утечек и аудит обращений моделируются отдельно от бизнес-контуров.
7. **Кандидаты в агрегаты** — центральные понятия глоссария: `Document`, `Chunk`, `Claim`, `KnowledgeGraph`, `OntologyLayer`, `ArtifactGraph`, `ContextCompiler`.

### Object properties (отношения модели)

Связи между классами модели выражаются object properties онтологии (`ontology.ttl`). Правила:

1. **Верхний уровень** классифицирует природу связи: `structuralRelation`, `interAggregateRelation`, `contextRelation`, `eventRelation`.
2. **Средний уровень** — смысловые группы предметной области (`identityRelation`, `updateRelation`, `retrievalRelation`, `traceabilityRelation`, `securityRelation` и т.д.).
3. **Leaf-properties** выражают предметный смысл связи и являются источником правды.
4. **Generic properties** (`comprises`, `references`, `binds`) — надсвойства совместимости; они выводятся из leaf-properties через `rdfs:subPropertyOf`.
5. **`rdfs:domain` / `rdfs:range`** задаются только на конкретных leaf-properties.
6. **Именование:** IRI свойства — English lowerCamelCase; `rdfs:label`/`rdfs:comment` — русские, предметные.
7. Межагрегатные связи в OWL показывают класс-уровневый смысл; реализация хранит ID корня.
8. **Корень агрегата помечается явно** datatype-свойством `epc:isAggregateRoot true`; члены агрегата маркер не получают.

### События и каскады

Доменные события связывают контексты и запускают каскады: `DocumentIngested` → `GraphUpdated` → `QueryAnswered`; `ConflictDetected` → сигнал владельцу артефакта; `SecurityEventEmitted` → обработка в контуре LLM. Каскады фиксируются в `domain-events.md`.

### Трассируемость

Каждый ограниченный контекст трассируется минимум к одной функции F1–F4 и одному UC.
