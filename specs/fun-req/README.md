# Функциональные требования — GraphRAG

## Иерархия требований

Функциональные требования (FR) — уровень **Functional** (W&B): детализация функций F1–F4 из `vision.md` до проверяемых утверждений о поведении системы. FR выводятся из пользовательских требований (UC/US) и бизнес-правил (BR), уточняют контракт функций и поддерживают сквозную трассировку:

```
specs/fun-req/ — функциональные требования (FR)
├─ README.md — методология, формат, критерии качества, навигация
└─ FR-<domain>.<category>.<attribute>.md — отдельные требования (по одному файлу)

Цепочка: vision (Business: F1–F4) → UC/US (User) → FR (Functional) → NFR (качество) → тесты
```

Связи:

- **FR выводятся из UC**: каждое FR трассируется к UC (поле «Связанные требования»), а через него — к функции F1–F4 и BR.
- **FR и NFR не дублируют друг друга**: FR описывает *что* делает система (поведение, входной контракт), NFR — *как* (качество: скорость, безопасность, точность). Признак ошибочного размещения в NFR — требование без числовой метрики: критерии из форматов и конвейеров — это FR.

## Формат идентификатора FR

```
FR-<domain>.<category>.<attribute>
```

| Часть | Описание |
|-------|----------|
| **domain** | Домен (согласован с UC/US, `specs/use-cases/README.md`): `knowledge` · `answers` · `context` · `mcp` · `ops` · `decommission` |
| **category** | Категория поведения в домене: `ingest` · `sync` · `grounding` · `impact` · `compile` · … |
| **attribute** | Суть требования в kebab-case |

### Правила именования

1. **domain** — строго из списка доменов (согласован с `specs/use-cases/README.md`).
2. **category** — категория поведения, переиспользуемая между FR.
3. **attribute** — свободная англоязычная метка в kebab-case, отражающая суть требования.
4. Идентификатор устойчив: добавление или удаление FR не меняет ID существующих требований; имя файла совпадает с ID: `FR-<domain>.<category>.<attribute>.md`.

## Правила оформления

1. **Один файл — одно функциональное требование.**
2. **Имя файла**: `FR-<domain>.<category>.<attribute>.md` — совпадает с ID требования.
3. **Язык**: русский. Технические термины — на английском.
4. **Обязательные поля**:
   - **Приоритет:** `P0` / `P1` / `P2`
   - **Источник:** ссылка на функцию F1–F4 и раздел `vision.md`, BR
   - **Связанные функции:** функция/подфункция F1–F4 из `vision.md` §2.2
   - **Описание:** суть функционального поведения
   - **Критерии приёмки:** проверяемые условия (форматы, конвейеры, реакции системы)
5. **Рекомендуемые поля** (атрибуты требований, W&B Chapter 27):
   - **Статус:** `proposed` → `approved` → `implemented` → `verified` → `deleted`
   - **Связанные требования:** ссылки на UC, US, BR, NFR (перекрёстная трассировка)
6. **TBD-флаг**: пробелы в требовании помечаются `TBD` и фиксируются в [open-questions.md](../open-questions.md).
7. **Трассируемость**: backward — FR → UC → функция F1–F4 → BR; forward — FR → тесты (гейт `G1-TRACE`).

## Приоритеты

Приоритет определяет порядок реализации (согласован с US/UC, P0–P2):

- **P0** — критическое: без требования MVP невозможен (например, потребление спек и кода — база корпуса).
- **P1** — важное: ключевое поведение MVP (например, потребление PDF и структурированных данных).
- **P2** — желательное: улучшает, но не блокирует выпуск.

## Критерии качества FR

| Характеристика | Значение для FR | Как проверить |
|----------------|-----------------|---------------|
| **Verifiable** (проверяемость) | Критерии приёмки проверяемы (формат, конвейер, реакция) | Тест по критериям |
| **Unambiguous** (однозначность) | Конкретные форматы и условия вместо «поддерживает разные документы» | Ревью: отсутствие размытых формулировок |
| **Complete** (полнота) | Охвачены все режимы/сценарии, к которым применимо | Перечень сценариев полон |
| **Necessary** (необходимость) | Выводится из функции F1–F4, UC или BR | Трассировка FR → F → UC → BR |
| **Feasible** (реализуемость) | Достижимо в рамках архитектуры | Оценка разработкой (архитектура, прототип) |
| **Prioritized** (приоритизированность) | Указан приоритет P0/P1/P2 | Наличие поля «Приоритет» |
| **Correct** (корректность) | Не конфликтует с другими FR и NFR | Сверка; учёт trade-offs |
