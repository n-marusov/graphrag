# Прецеденты использования — GraphRAG

В этой директории находятся отдельные файлы прецедентов использования (Use Cases) проекта **GraphRAG** — корпоративной системы знаний на базе GraphRAG: evidence-based context layer / context compiler для ИИ-агентов автоматизации разработки. Продукт — набор компонентов контура знаний (ядро, оркестрация пайплайнов индексации, движок запросов, MCP-сервер, веб-интерфейс, интеграции), разворачиваемый в защищённом контуре организации на локальных GPU. Каждый файл соответствует одному UC и назван по шаблону `<UC-ID>.md`.

UC — полное описание поведения системы; пользовательские истории (US) — подмножество с фокусом на взаимодействии пользователя с системой ([user-stories](../user-stories/README.md)); UC детализируются в функциональные требования (FR).

---

## Формат идентификатора UC

```
UC-<L1>.<L2>.<L3>
```

Где:

| Часть | Описание | Допустимые значения |
|-------|----------|---------------------|
| **L1** | Домен (соответствует функции F1–F4 из vision.md §2.2) | `answers` · `knowledge` · `context` · `mcp` |
| **L2** | Поддомен — один пользовательский результат внутри домена (см. «Домены UC») | `grounding` · `synthesis` · `sync` · `ingest` · `impact` · `build` · `check` · `access` · `compile` |
| **L3** | Семантический англоязычный тег в kebab-case, отражающий суть UC | Свободная семантическая метка (не ограничена глаголами) |

### Правила именования

1. Только **kebab-case**, без цифр и индексов.
2. **L1** — строго из списка доменов.
3. **L2** — строго из списка поддоменов выбранного домена; поддомены не пересекаются между доменами (классификация ортогональна).
4. **L3** — свободная семантическая метка, отражающая конкретный сценарий.
5. UC моделируют не только GUI-сценарии: допустимы GUI, API, CLI, MCP, Webhook/Event, Schedule/Job.
6. Для каждого UC рекомендуется указывать метаданные `**Канал:** GUI | API | CLI | MCP | Webhook | Schedule | Mixed`.

### Примеры

| ✅ Корректно | ❌ Некорректно |
|---|---|
| `UC-answers.grounding.cited-answer` | `UC-1.answers.grounding` (содержит цифру) |
| `UC-knowledge.sync.gitlab-index` | `UC-knowledge.sync.gitlabIndex` (camelCase) |
| `UC-context.impact.analyze` | `UC-context.impact.1` (содержит цифру) |
| `UC-mcp.compile.context` | `UC-mcp.compile.buildcontext` (не kebab-case, слитно) |
| `UC-answers.synthesis.multi-hop` | `UC-answers.synthesis` (отсутствует L3) |
| `UC-knowledge.ingest.s3-book` | `UC-knowledge.ingest.s3` (L3 слишком короткий) |

## Формат описания UC

Каждый файл UC содержит следующие секции:

| Секция | Обязательность | Описание |
|--------|---------------|----------|
| `### <UC-ID>: <Название>` | Обязательно | Заголовок с идентификатором и кратким названием на русском |
| `**Актор:**` / `**Акторы:**` | Обязательно | Роль(и) пользователя, инициирующего прецедент (роли из vision.md §3.1; для агентов — «ИИ-агент автоматизации разработки») |
| `**Приоритет:**` | Обязательно | `P0` (критичный), `P1` (высокий), `P2` (средний) |
| `**Ключевая функция:**` | Обязательно | Ссылка на функции из vision.md §2.2 (F1–F4) |
| `**Канал:**` | Рекомендуется | `GUI` / `API` / `CLI` / `MCP` / `Webhook` / `Schedule` / `Mixed` |
| `**Описание:**` | Обязательно | Краткое описание прецедента |
| `**Диаграмма последовательности:**` | Обязательно | Mermaid `sequenceDiagram`: основной поток 1:1 с шагами и ключевые альтернативы (`alt`/`opt`); размещается после «Описание» |
| `**Основной поток:**` | Обязательно | Нумерованный список шагов основного сценария |
| `**Альтернативные потоки:**` | Рекомендуется | Варианты (A1, A2, ...) с описанием отклонений |
| `**Постусловия:**` | Обязательно | Состояние системы после успешного выполнения UC |
| `**Источник требований:**` | Рекомендуется | Ссылка на файл(ы) требований (US, ADR) или evidence paths на `src/` для `as is`-UC |

Атрибуты блока метаданных (`**Актор:**`, `**Приоритет:**`, `**Ключевая функция:**`, `**Канал:**`, `**Описание:**`) разделяются пустыми строками — каждый атрибут отдельным абзацем.

### Диаграмма последовательности

Каждый UC **обязан** содержать Mermaid-диаграмму `sequenceDiagram`, размещаемую сразу после `**Описание:**`. Отсутствие диаграммы — нарушение формата описания UC. Правила оформления:

1. **Расположение:** секция `**Диаграмма последовательности:**` — после `**Описание:**`, перед `**Основной поток:**`.
2. **Участники:** `participant ID as <Название>`; ID — короткий латинский; название — контейнер C4, персона или внешняя система из [`container.md`](../c4/container.md) (Команда разработки, Ядро, Оркестрация пайплайнов индексации, Движок запросов, MCP-сервер, Мониторинг и аудит, Хранилище графа и векторов, Интеграции, Контур LLM, GitLab); компоненты (Context compiler, Граф знаний) и роли `vision.md` §3.1 в диаграммах не используются.
3. **Сообщения:** `->>` — запрос, `-->>` — ответ; сообщения соответствуют шагам `**Основной поток:**` 1:1.
4. **Разделители глав:** комментарий `%% --- N. Заголовок ---`; заголовок секции при необходимости — `Note over X: заголовок`.
5. **Альтернативные потоки:** `alt`/`else` — взаимоисключающие ветки, `opt` — отклонение в точке; ветки помечаются кодом A-потока (`A1`/`A2`/`A3`); вложенность не глубже 2 уровней.
6. **Внутренние действия** (извлечение, резолвинг, генерация, проверка): `Note over X: описание`.
7. **Целевое состояние:** диаграммы отражают целевое состояние (to be) для компонентов, не реализованных в `src/` (context compiler, MCP-сервер, контур LLM — планируемые, см. контекст системы в vision.md §3.3); под диаграммой ставится пометка `to be`.
8. **Синтаксис:** см. [референс Mermaid sequence diagrams](../../.ai-factory/references/mermaid-sequence-diagrams.md).

## Домены UC

| Домен (L1) | Соотв. функция (vision.md) | Поддомены (L2) | Приоритет (базовый) | Описание | Пример UC-ID |
|------------|---------------------------|----------------|---------------------|----------|-------------|
| `answers` | F1. Генерация проверяемых ответов | `grounding` · `synthesis` | `grounding` — P0; `synthesis` — P1 (база) / P2 (полный контур) | Ответы на конкретные вопросы со ссылками на артефакты и происхождением (grounding, provenance); синтез обзорных ответов, связывающих факты из разных артефактов | `UC-answers.grounding.cited-answer` |
| `knowledge` | F2. Индексация источников знаний | `sync` · `ingest` | `sync` — P0; `ingest` — P1 | Автоиндексация изменений GitLab (спеки и код), индексация книг и legacy-документов из внешнего хранилища (S3); инкрементальное обновление графа — часть F2 | `UC-knowledge.sync.gitlab-index` |
| `context` | F3. Оптимизация контекста для автоматической разработки | `impact` · `build` · `check` | `impact` — P0; `build` — P1; `check` — P2 (Фаза 2, K5) | Анализ влияния изменения артефакта (детерминированный список связанных артефактов), компиляция контекста (JSON: набор артефактов с направлениями связей) для генерации, сверка «результат ↔ источник» | `UC-context.impact.analyze` |
| `mcp` | F4. Доставка ответов и контекста через MCP | `access` · `compile` | `compile` — P0; `access` — P1 | Подключение ИИ-агента к MCP-серверу (инструменты, аутентификация), доставка точного набора артефактов и фактов под задачу вместо сырого текста | `UC-mcp.compile.context` |

> Классификация ортогональна: каждый UC относится ровно к одной паре (домен, поддомен). Механизмы (онтологический слой, контур LLM, методы GraphRAG) и сквозные требования (NFR-*) доменами UC не являются — они отражаются метаданными и каналами, а не классификацией.

## Специфика проекта

- **Контур знаний — контекст исполнения**: UC описывают поведение компонентов GraphRAG (ядро, оркестрация пайплайнов индексации, движок запросов, MCP-сервер, веб-интерфейс, интеграции) внутри защищённого контура знаний организации. Внешние системы — GitLab (спеки и код), внешнее хранилище документов (S3), локальный контур LLM, ИИ-агенты автоматизации разработки; UC не описывают их внутренние функции — это зона внешних систем.
- **Функция, а не механизм**: по принципу `vision.md` §2.2 UC — результаты, ценные для пользователя (роли из §3.1), а не каналы. MCP, REST/CLI, Git API/webhook, онтологический слой (модель предметной области), методы GraphRAG (LightRAG, KAG, PathRAG, RAPTOR/StructRAG, PPR, community summaries), векторный индекс — механизмы; они указываются метаданными `**Канал:**`, а не становятся доменами.
- **События предметной области**: `DocumentIngested`, `EntityExtracted`, `GraphUpdated`, `CommunityRecomputed`, `QueryReceived`, `QueryAnswered`, `InfluenceComputed`, `ConflictDetected`, `ContextCompiled`, `SecurityEventEmitted` (vision §2.4) — триггеры каскадов в контуре знаний (например, изменение в GitLab → `DocumentIngested` → `GraphUpdated` → новые ответы опираются на актуальную версию источника); UC должны явно описывать эти каскады.
- **Канал** для автоматических сценариев (автоиндексация по MR, периодическая перестройка, инкрементальное обновление графа) — `Webhook` или `Schedule`, не `GUI`.
- **Границы продукта**: GraphRAG — не источник правды (единый источник — репозиторий спек и кода), не чат-бот и не поисковая строка; Confluence исключён как источник знаний; fine-tuning, real-time обновление графа и накопление знаний из внешних сигналов — вне рамок (vision §2.7); UC не должны описывать функции вне этих границ.
- **Безопасность контура LLM**: данные разработки (код, спеки, ПДн) не покидают периметр; UC, затрагивающие контур LLM, учитывают сквозные требования REQ-NFR-security.compliance.llm-contour (фильтрация утечек, аудит обращений) и REQ-NFR-process.compliance.human-confirmation (принцип «агент готовит — человек подтверждает и отвечает»).

### Классификация UC: `as is` vs целевое состояние (`to be`)

Каждый UC относится к одному из двух классов по наличию реализации в `src/` (**код — источник истины**):

- **`as is` (фича реализована в `src/` полностью или частично)** — UC описывает фактическое поведение компонентов: реальные каналы, компоненты и статусы из кода. Если реализация беднее целевой модели, UC фиксирует текущее поведение, а расширения выносятся в явные target-примечания (не в основной поток).
- **Целевое состояние (`to be`, фича не реализована в `src/`)** — UC описывает целевую capability, явно помеченную `to be`/target, со ссылкой на `vision.md` и корректную фазу roadmap (vision §2.6). Такой UC не подгоняется под отсутствующий код; он проверяется на здравый смысл и соответствие видению.

> **Текущий статус проекта:** проект находится на этапе видения (Фаза 0); `src/` не содержит реализации, поэтому все UC на данный момент — `to be` с пометкой фазы из `vision.md` §2.6.

Правила:

1. Для `as is`-UC диаграмма последовательности и основной поток соответствуют фактическим компонентам/каналам кода; в `**Источник требований:**` указываются evidence paths на `src/` (файлы/символы), по которым поведение восстановлено.
2. Для `to be`-UC обязательна пометка целевого состояния и фазы roadmap; формулировки не должны выдавать целевую модель за текущую реализацию.
3. Неподтверждённые в коде гарантии (порог точности RAG ≥ 70%, фильтрация утечек, инкрементальное обновление, PPR-запросы без LLM, лимиты токенов и т. п.) не указываются как основной поток `as is`-UC — при необходимости они выносятся в target-примечания.
