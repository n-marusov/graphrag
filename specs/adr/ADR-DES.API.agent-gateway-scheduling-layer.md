## Контекст

Система GraphRAG обслуживает два разных класса потребителей:

1. **Интерактивные запросы человека** — ожидают низкой задержки, понятных ответов и стабильной отзывчивости.
2. **Агентские workflow** — создают всплесковую нагрузку: многократные циклы извлечения, сборку контекста, вызовы инструментов, проверки, повторные запросы, отмены и уточнения.

Если дать обоим классам одинаковый путь в систему, то агенты начнут конкурировать с пользователями за:
- бюджет LLM;
- ёмкость извлечения;
- индексные и графовые ресурсы;
- кэш;
- фоновые воркеры переиндексации.

Для этого проекта это особенно рискованно, потому что:
- переиндексация должна быть частой;
- путь чтения должен оставаться отзывчивым;
- каждый ответ обязан сохранять grounding и происхождение (provenance);
- агент должен работать с точным набором артефактов, а не с «сырым» потоком текста.

Нужна отдельная точка управления, которая будет принимать агентские запросы, ограничивать их и маршрутизировать их по бюджету и приоритету.

## Решение

Принять **Agent Gateway + слой планирования (scheduling layer)** как отдельную архитектурную границу между агентами и внутренними контурами запросов, извлечения и выполнения инструментов.

### Основные правила

1. **Агенты не ходят напрямую во внутренние сервисы.**
   - Все агентские запросы проходят через Agent Gateway.
   - Шлюз выполняет аутентификацию, проверку политик, проверку квот, проверку бюджета и классификацию запросов.

2. **Агентский запрос получает явный режим исполнения.**
   - `interactive` — быстрый синхронный режим для коротких запросов.
   - `workflow` — управляемый многошаговый режим с шагами, контрольными точками и отменой.
   - `background` — отложенные или тяжёлые операции, которые не должны блокировать интерактивный путь.

3. **Слой планирования управляет приоритетами.**
   - Запросы пользователей имеют приоритет над агентскими.
   - Агентские workflow получают ограниченный параллелизм.
   - Долгие или тяжёлые шаги переводятся в асинхронную очередь задач.

4. **Каждый агентский шаг измеряется и аудируется.**
   - бюджет на токены, шаги извлечения и вызовы инструментов;
   - таймаут на шаг и на workflow;
   - trace-id для полной воспроизводимости;
   - журнал причин отказа или ограничения темпа.

5. **Agent Gateway работает как защитная граница.**
   - Фильтрует доступ к чувствительным действиям;
   - ограничивает fan-out;
   - запрещает бесконтрольные циклы;
   - поддерживает явные точки подтверждения там, где нужен человек.

### Логическая схема

```text
Агент / MCP-клиент
        |
        v
+---------------------------+
|        Шлюз               |
| аутентификация | политики |
| квоты | бюджет | классификация |
+-------------+-------------+
              |
              v
     +-------------------+
     | Планировщик / очередь |
     | приоритет / режим   |
     +----+----------+----+
          |          |
          |          +------------------+
          v                             v
+-------------------+         +-------------------------+
| Интерактивный путь |         | Асинхронные воркеры     |
| низкая задержка    |         | повторы / контрольные точки |
+---------+---------+         +-----------+-------------+
          |                                 |
          v                                 v
   Запросы / извлечение                  Выполнение инструментов,
   / сборка ответа                       аудит, публикация
```

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Прямой доступ агентов к Query API** | Агент вызывает те же endpoint-ы, что и человек | Нет изоляции, всплесковая нагрузка ухудшает задержку, трудно применять квоты и обеспечивать безопасность инструментов |
| **Один общий очередь без слоя политик** | Все запросы идут в единую очередь без различения режима | Пропадает приоритизация, невозможно гарантировать UX для человека и управлять бюджетами |
| **Синхронное исполнение агента** | Каждый агентский workflow выполняется целиком в одном запросе | Длинные цепочки блокируют ресурсы, растут таймауты и стоимость, сложнее откат |
| **Полностью отдельный агентский сервис** | Агентская подсистема выделяется в независимый продукт | Слишком рано для MVP; добавляет лишние границы, пока нужен прежде всего control plane, а не новая бизнес-система |

## Последствия

**Положительные:**

- Интерактивные запросы сохраняют отзывчивость, потому что агентские всплесковые нагрузки ограничены и приоритизированы.
- Можно задавать разные SLA для людей и агентов.
- Бюджеты, квоты и отмена становятся явными и измеримыми.
- Появляется единый аудит-след для агентских действий.
- Шлюз даёт место для человеческого подтверждения там, где это требуется принципом «агент готовит — человек подтверждает и отвечает».
- Становится проще связать агентские workflow с версионными снапшотами и политикой актуальности.

**Отрицательные и смягчение:**

1. **Дополнительная архитектурная граница и усложнение маршрутизации.** Смягчение: держать шлюз тонким, без доменной логики; только политики, планирование и маршрутизация.
2. **Риск избыточной задержки на переходе через шлюз.** Смягчение: быстрые проверки политик, локальный кэш по квоте/бюджету, быстрый путь для простых интерактивных запросов.
3. **Необходимость проектировать бюджеты и лимиты заранее.** Смягчение: начать с консервативных значений по умолчанию и постепенно калибровать по телеметрии.
4. **Возможные ложные отказы для легитимных workflow.** Смягчение: явные режимы исполнения, понятные ошибки и возможность ручного переопределения там, где разрешено политикой.

**Критерии пересмотра:**

- Если агентские нагрузки остаются малыми и не конкурируют с пользовательским трафиком — шлюз может быть сведён к лёгкому middleware для политик.
- Если workflow станут сложнее и длиннее — слой планирования может эволюционировать в отдельный сервис-оркестратор.
- Если появится мультиарендная эксплуатация — потребуется усилить изоляцию квот и аудит по границам арендаторов.

**Открытые вопросы (вне этого ADR):**

- Конкретный формат политики бюджета и допустимые лимиты для разных типов агентов.
- Модель точек подтверждения для рискованных операций.
- Нужно ли отдельное постоянное хранилище workflow или достаточно журнала задач и хранилища трасс.
