# ADR-DES.API.hybrid-graphrag-composition — Гибридная ontology-grounded композиция GraphRAG

- **Статус:** ПРИНЯТО
- **Дата:** 2026-08-29
- **Требование-источник:** [`.ai-factory/RESEARCH.md`](../../.ai-factory/RESEARCH.md) (Decisions — решение о типе GraphRAG перенесено в данный ADR), [`specs/vision.md`](../../specs/vision.md) §1.4 (точность RAG ≥ 70%), §2.5 (MVP: F1–F4; сквозные требования), §3.2 (приоритеты), [`specs/glossary.md`](../../specs/glossary.md) (разделы 3–4: методы GraphRAG и извлечение знаний)

## Контекст

GraphRAG — корпоративная система знаний: индексация корпуса (markdown-спеки GitLab, книги и легаси из внешнего хранилища) в граф знаний с онтологическим слоем, ответы со ссылками на источники (grounding, provenance), анализ влияния, context compiler (MCP). Требуется выбрать конкретную композицию методов GraphRAG, которая одновременно обеспечивает:

1. **Инкрементальность.** Корпус меняется через MR (GitLab) и изменения во внешнем хранилище документов; полная перестройка индекса на каждое изменение недопустима по стоимости (vision.md §3.2 — инкрементальное обновление как критический фактор; §2.5).
2. **Минимизацию токенов и числа LLM-вызовов.** Локальные GPU и open-weight модели с ограниченным контекстом; MCP-режим отдаёт агенту точный набор артефактов, а не сырой текст (vision.md §2.5 — сквозное требование минимизации токенов).
3. **Точность и непротиворечивость ответов.** Порог продолжения — точность RAG не ниже 70% на утверждённом benchmark-наборе (vision.md §1.4).
4. **Проверяемость.** Каждый факт трассируется до породивших чанков (mutual indexing), ответы атрибутированы источниками (glossary: «Привязка к источнику», «Происхождение»).
5. **Обработку PDF.** Книги/narrative и таблицы/формы/отчёты — отдельные контуры (F2.2).
6. **Глобальные и ассоциативные запросы.** Темы/тренды (community summaries) и ассоциативный поиск без LLM на этапе извлечения.

Ни один существующий метод не покрывает все требования целиком:

- **Чистый Microsoft GraphRAG** — map-reduce на каждый глобальный запрос и полная перестройка индекса; противоречит инкрементальности и локальным GPU (glossary: «GraphRAG»).
- **Векторный RAG** — эффективен для локальных фактологических запросов, недостаточен для глобальных и multi-hop (glossary: «Векторный поиск»); не даёт графа связей для анализа влияния (F3).
- **LightRAG** — даёт dual-level retrieval и инкрементальность, но не гарантирует точность/непротиворечивость и компактность контекста для MCP.
- **KAG** — набор принципов точности (mutual indexing, grounding), но не retrieval-механизм с инкрементальностью.
- **PathRAG / PPR** — оптимизируют контекст и retrieval, но сами по себе не покрывают глобальные обзоры и инкрементальное обновление.

## Решение

Принять **гибридную ontology-grounded композицию** как целевую для продукта (MVP и далее): LightRAG — ядро retrieval; KAG-принципы — точность; PathRAG — компактный контекст; PPR — ассоциативные запросы без LLM; RAPTOR/StructRAG — PDF; community summaries — глобальные обзоры и онбординг.

| Компонент | Роль | Ключевые свойства |
|---|---|---|
| **LightRAG** | Ядро retrieval | Двухуровневое извлечение (низкий + высокий уровень), инкрементальное обновление графа (glossary: «LightRAG», «Двухуровневое извлечение») |
| **KAG-принципы** | Точность и непротиворечивость | Mutual indexing (KG↔chunks), grounding, атрибуция источников (glossary: «KAG», «Взаимная индексация») |
| **PathRAG** | Компактный контекст | Pruned paths, однократное извлечение без map-reduce — критично для локальных GPU и MCP (glossary: «PathRAG») |
| **PPR (HippoRAG-стиль)** | Ассоциативные запросы | Без LLM на этапе извлечения (glossary: «PPR», «HippoRAG») |
| **RAPTOR** | PDF: книги/narrative | Рекурсивная суммаризация в иерархическое дерево (glossary: «RAPTOR») |
| **StructRAG** | PDF: таблицы/формы/отчёты | Динамическая структуризация в «структурные опоры» (glossary: «StructRAG») |
| **Community summaries** | Глобальные запросы, онбординг | Уровни C0–C1; детекция сообществ (Leiden) (glossary: «Суммаризация сообществ») |
| **Graphiti** | Real-time обновление (Фаза 3) | Битемпоральный граф, готовый MCP — вне MVP (glossary: «Graphiti») |

Правила границы:

- Запрещён полный map-reduce Microsoft GraphRAG на каждый запрос; запрещён LLM на этапе ассоциативного извлечения (PPR-сценарии).
- Компоненты реализуются на Go (см. [ADR-IMPL.STACK.go-single-language-adoption](ADR-IMPL.STACK.go-single-language-adoption.md)); референсные Python-реализации — источники для проектирования, не входят в репозиторий продукта.
- Каждый компонент отчуждается контрактными тестами на эталонных кейсах (K1, K4, K5, K17) и бенчмарками; замена компонента возможна без изменения внешних контрактов (HTTP API, MCP).

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Чистый Microsoft GraphRAG** | Map-reduce на глобальные запросы, полная перестройка индекса | Противоречит инкрементальности (vision.md §3.2) и локальным GPU; стоимость на каждый запрос |
| **Векторный RAG** | Top-k чанков по эмбеддингам | Недостаточен для глобальных и multi-hop запросов; нет графа связей для анализа влияния (F3) |
| **LightRAG-only** | Ядро без усиления | Не покрывает требования точности (grounding, порог 70%) и компактности контекста для MCP |
| **KAG-only** | Принципы точности без retrieval-ядра | Нет механизма извлечения и инкрементального обновления |
| **Готовые облачные GraphRAG-сервисы** | Внешние API | Данные разработки не покидают периметр (vision.md §2.7, п. 10) |

## Последствия

**Положительные:**

- Инкрементальность (vision.md §3.2): корпус меняется через MR и изменения во внешнем хранилище документов, пересчитываются только затронутые части графа.
- Компактный контекст: PathRAG + PPR + онтологический слой минимизируют токены и число LLM-вызовов — локальные GPU и MCP.
- Точность и проверяемость: KAG-принципы, grounding и mutual indexing обеспечивают атрибуцию и трассируемость фактов; порог точности ≥ 70% (vision §1.4) измерим.
- Гибкость: каждый компонент заменяем по контрактным тестам и бенчмаркам; внешние контракты не зависят от внутренней композиции.

**Отрицательные и смягчение:**

1. **Сложность композиции (6+ методов) — риск «лоскутной» системы и размытых границ.** Смягчение: явные роли компонентов (таблица решения), контрактные тесты на стыках, эталонные кейсы (K1, K4, K5, K17) фиксируются до реализации.
2. **Методы быстро развиваются в Python-first экосистеме — риск переписывания.** Смягчение: контрактные тесты и golden dataset отчуждают поведение от конкретной реализации; ADR уровня `IMPL` фиксируют конкретные библиотеки.
3. **LLM-вызовы на извлечении и суммаризации — основной потребитель токенов.** Смягчение: PPR без LLM на retrieval, PathRAG без map-reduce, онтологический слой сокращает контекст (vision.md §2.5 — сквозное требование минимизации токенов).
4. **Качество community summaries зависит от детекции сообществ (Leiden) и модели.** Смягчение: LLM-as-judge и регулярный замер точности; снижение ниже порога 70% — критерий пересмотра.

**Критерии пересмотра:**

- Точность RAG ниже 70% на утверждённом benchmark-наборе при сохранении композиции.
- Рост корпуса (Фаза 2/3) и профилирование показывают неэффективность инкрементального обновления LightRAG.
- Появление зрелых альтернатив (например, Graphiti для real-time сценариев — Фаза 3).

**Открытые вопросы (вне этого ADR):**

- Конкретные Go-реализации компонентов и библиотеки — фиксируются ADR уровня `IMPL`.
- Хранилище графа и векторного индекса — решение: Neo4j (self-hosted, Community Edition), см. [ADR-IMPL.DATA.graph-storage](ADR-IMPL.DATA.graph-storage.md).
- Модель обновления: инкрементальная + периодическая перестройка — кандидат `ADR-IMPL.DATA.incremental-update-model`.
- Масштаб корпуса (1k vs 100k документов) — открытый вопрос RESEARCH.md.
- Real-time контур (Graphiti) — Фаза 3, вне MVP.
