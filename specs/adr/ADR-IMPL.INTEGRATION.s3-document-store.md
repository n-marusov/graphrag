# ADR-IMPL.INTEGRATION.s3-document-store — Внешнее S3-хранилище как источник книг и легаси

- **Статус:** ПРИНЯТО
- **Дата:** 2026-08-29
- **Требование-источник:** [`specs/vision.md`](../../specs/vision.md) §2.2 (F2.2 — индексация книг и легаси из внешнего хранилища), §2.5 (MVP: F2; глобальный контекст), §2.7 п.4 (границы источников), §2.8 (внешние зависимости, A8); [`ADR-DES.API.hybrid-graphrag-composition`](ADR-DES.API.hybrid-graphrag-composition.md) (RAPTOR/StructRAG для PDF)

## Контекст

Книги и унаследованные документы (легаси) — источник глобального контекста, не привязанного к конкретному проекту (справочники, стандарты, книги по архитектуре и т. п.). Ранее F2.2 предполагала ручную загрузку PDF через интерфейс — единственный прямой канал ввода в систему, что противоречит принципам:

- **«GraphRAG — не источник правды»** (vision §2.7 п.1): все артефакты живут во внешних authoritative-хранилищах, система только индексирует.
- **Правилу каналов** (use-cases README): автоматические сценарии — `Webhook`/`Schedule`, не `GUI`/ручная загрузка.
- **Единообразию входа**: корпус обновляется автоматически (GitLab — по MR/webhook), ручной ввод выбивается из контура.

Компания уже использует объектное хранилище S3 как корпоративную инфраструктуру — использовать его как источник книг/легаси не создаёт новой инфраструктуры.

## Решение

1. **Источник книг и легаси — внешнее объектное хранилище S3** (S3-совместимое API; у компании уже есть используемый S3). В `vision.md` источник фиксируется нейтрально — «внешнее хранилище документов»; конкретная технология (S3) — в данном ADR.
2. **Триггеры индексации — оба механизма, для надёжности**: события бакета (bucket notifications) + периодическая diff-сверка (аналогично GitLab: webhook + fallback-сверка, vision §2.8 A8).
3. **Глобальный контекст — отдельный граф**: книги и легаси образуют глобальный слой знаний (не проектный), хранящийся в отдельном графе. Проектные сущности могут ассоциироваться с глобальным контекстом (например, термин проекта связан со справочной статьёй по чистой архитектуре). Ассоциации — часть онтологического слоя (механизм F1/F3).
4. **Масштаб**: сотни книг (порядок величины 10²) в глобальном слое; проектный корпус остаётся предметом открытого вопроса масштаба (1k vs 100k).
5. **PDF — формат объектов, а не канал**: RAPTOR/StructRAG-обработка книг (ADR-DES.API.hybrid-graphrag-composition) сохраняется; формат не фиксируется на уровне контракта хранилища.

Правила границы:

- Прямой ручной ввод документов в GraphRAG отсутствует: запись — только через GitLab (MR) и внешнее хранилище (S3).
- S3 — внешняя система (вне периметра разработки); доступ — через контракт (API/события), содержимое обрабатывается как корпус, данные не кэшируются вне контура.
- Глобальный граф не смешивается с проектными графами на уровне хранения; на уровне retrieval — ассоциация сущностей по онтологии.

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Ручная загрузка PDF через UI** | Прямой канал ввода файлов в систему | Единственный ручной канал; нарушает правило каналов (`GUI` вместо `Webhook`/`Schedule`), принцип «не источник правды» и единообразие входа |
| **GitLab как единственный источник** | Книги/легаси в репозитории GitLab | Книги — глобальный контекст (не проектный), не живут в проектных репозиториях; раздувают проектный корпус и MR-процесс |
| **Внутреннее хранилище (MinIO в периметре)** | S3-совместимое хранилище внутри периметра | Компания уже использует внешний S3; дублирование инфраструктуры и контура доступа |
| **Локальная файловая система / NFS** | Файловый доступ к книгам | Нет событийной модели и контракта API; хуже масштабируется и аудируется |

## Последствия

**Положительные:**

- Единообразный автоматический вход: корпус обновляется только через внешние authoritative-хранилища (GitLab + S3), прямых ручных каналов нет.
- F2.2 становится автоматической (события + сверка) — по той же модели, что F2.1 (GitLab).
- Глобальный слой знаний отделён от проектного: масштаб, обновление и retrieval не пересекаются; ассоциации дают межпроектный контекст (справочники, стандарты).
- Использование существующей инфраструктуры компании (S3) — без новой инфраструктуры.

**Отрицательные и смягчение:**

1. **Данные (книги/легаси) находятся во внешнем хранилище — вне периметра разработки.** Смягчение: доступ только по контракту (API/события, минимальные права); фильтрация и аудит обращений к хранилищу; при необходимости — шифрование и политика доступа на стороне S3; книги/легаси менее чувствительны, чем код и спеки, но политика обработки фиксируется с IT-безопасностью.
2. **Зависимость от внешней S3-инфраструктуры (доступность, лимиты, стоимость).** Смягчение: периодическая diff-сверка как fallback при потере событий; идемпотентность индексации; мониторинг задержек событий.
3. **Масштаб «сотни книг»** — большие файлы и длинные документы (RAPTOR-иерархии). Смягчение: RAPTOR/StructRAG-обработка; инкрементальная индексация; отдельный граф не влияет на производительность проектных запросов.
4. **Глобальный контекст может вносить шум в проектные ответы.** Смягчение: ассоциации — только по онтологии; retrieval разделяет проектный и глобальный слои (dual-level retrieval, LightRAG).

**Критерии пересмотра:**

- Отказ/деградация внешнего S3 в проде при отсутствии fallback-механизма (периодическая сверка).
- Рост глобального слоя за пределы сотен книг (Фаза 2/3) — пересмотр модели обновления и хранения.

**Открытые вопросы (вне этого ADR):**

- Конкретный S3-провайдер/бакеты, политики доступа и событий — операционный выбор, вне ADR.
- Хранилище графа и векторного индекса — `ADR-IMPL.DATA.graph-storage` (открытый вопрос).
- Модель обновления: инкрементальная + периодическая перестройка — кандидат `ADR-IMPL.DATA.incremental-update-model`.
