# ADR-IMPL.STACK.go-single-language-adoption — Go как единый язык реализации (ИИ-генерация кода)

- **Статус:** ПРИНЯТО
- **Дата:** 2026-08-29
- **Требование-источник:** [`.ai-factory/RESEARCH.md`](../../.ai-factory/RESEARCH.md) (Decisions — решение о языке заменено данным ADR), [`specs/vision.md`](../../specs/vision.md) §2.5, §2.6, §2.7, §2.8

## Контекст

GraphRAG — корпоративная система знаний на базе ontology-grounded GraphRAG: индексация корпуса (markdown-спеки, PDF) в граф знаний с онтологическим слоем, ответы с grounding, анализ влияния, context compiler (MCP). Нагрузочный профиль системы смешанный:

1. **I/O-bound оркестрация** — основной объём работы: конкурентный fan-out вызовов к LLM (извлечение сущностей, генерация ответов, суммаризации сообществ), к хранилищу графа и векторному индексу, к GitLab, обслуживание MCP-сервера для ИИ-агентов. Требуются конкурентность на сотни-тысячи вызовов и быстрая итерация промптов и логики пайплайнов.
2. **CPU-тяжёлые in-process алгоритмы** — детекция сообществ (Leiden), векторный поиск (HNSW), токенизация. Критичны к производительности и памяти и исполняются на локальном контуре с ограниченными ресурсами (локальные GPU, open-weight модели; минимизация токенов и числа LLM-вызовов — сквозное требование).
3. **Экспериментальный слой** — методы GraphRAG (LightRAG, KAG, PathRAG, RAPTOR/StructRAG, PPR) быстро развиваются; референсные реализации и материалы живут в основном в Python-экосистеме (LightRAG, NetworkX, graspologic, LlamaIndex).

Дополнительные ограничения: принцип «агент готовит — человек подтверждает и отвечает»; данные не покидают периметр (LLM — только в контролируемом контуре); деплой — на внутренней инфраструктуре без внешних рантаймов; масштаб корпуса — открытый вопрос (1k vs 100k документов).

**Ключевой фактор — ИИ-генерация кода.** Кодовая база создаётся и поддерживается преимущественно ИИ-агентами (это и способ разработки продукта, и его же сфера применения — context compiler). Это меняет структуру затрат выбора языка:

- Многоязычная кодовая база с FFI-границей — источник ошибок ИИ-генерации: контракты между языками (ABI, память, сериализация) — класс ошибок, который ИИ ловит хуже всего, а человеку проверять дорого.
- Один язык даёт минимальный и консистентный контекст для генерации: меньше правил, один тулчейн, один стиль, проще проверка и поддержка.
- Производительность CPU-алгоритмов на Go достаточна для старта (целевой корпус — до 10k документов в MVP, 100k — Фаза 2/3); узкие места закрываются зрелыми C-библиотеками через CGo либо оптимизацией по профилированию.

Ключевой вопрос: на каком языке реализовать систему, чтобы ИИ-генерация давала корректный, проверяемый и поддерживаемый код с минимальной сложностью, а производительность на локальном контуре была достаточной для целевого корпуса.

## Решение

**Go — единый язык реализации всей системы с первого дня.** Ядро, оркестрация, пайплайны, query engine, MCP-сервер, интеграции и CPU-компоненты — на Go. Код генерируется ИИ-агентами и подтверждается человеком (контрактные тесты, ревью).

1. **Вся кодовая база — Go.** Один язык, один тулчейн, один стиль — минимальный контекст для ИИ-генерации, консистентная генерация и простая проверка.
2. **CPU-компоненты (Leiden, HNSW, токенизация) — на Go**, при необходимости через CGo-биндинги к зрелым C-библиотекам. Производительность достаточна для старта; оптимизация — по данным профилирования и бенчмарков на целевом корпусе.
3. **Python исключён из кодовой базы, включая прототип.** Валидация методов — через тесты и бенчмарки на Go-реализациях; референсные материалы (исследования, литература, референсные реализации) остаются источниками для проектирования, но не входят в репозиторий продукта.

Правило границы: новый компонент пишется на Go; отступление (внешний нативный код) допускается только через CGo к зрелой библиотеке и только при измеримом критерии — профилирование или бенчмарк показывает, что чистая Go-реализация не достигает целевой производительности на целевом корпусе.

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Многоязычная стратегия: Go-ядро + Rust для CPU-компонентов + Python-прототип** | Предыдущее предложение (ADR-IMPL.STACK.go-core-rust-cpu-adoption, статус ПРЕДЛОЖЕНО, заменено данным ADR) | При ИИ-генерации стоимость языковых границ (FFI/ABI, два контекста генерации, два набора правил) выше выигрыша: ошибки ИИ на стыках языков трудно ловить и проверять; Python-прототип дублирует работу, которую выполняют контрактные тесты и бенчмарки на Go |
| **Моноязычный Rust** | Вся система, включая оркестрацию, на Rust | Основной объём — I/O-bound оркестрация, где преимущества Rust не реализуются; строгий borrow-checker увеличивает число итераций ИИ-генерации и стоимость проверки; меньше LLM-экосистема; выше стоимость поддержки |
| **Python в production** | FastAPI + LangChain/LlamaIndex + NetworkX (референсный стек [05-design-guide.md](../../.ai-factory/references/graphrag/05-design-guide.md) §3.2) | GIL ограничивает конкурентный fan-out; производительность и память на CPU-алгоритмах и корпусе 10k+; упаковка и деплой локального сервиса сложнее (интерпретатор, зависимости); Python остаётся только референсной экосистемой |
| **Go + Rust через FFI (без Python)** | Go-ядро + Rust-библиотеки для CPU-компонентов | Сохраняет FFI-границу и связанные с ней риски для ИИ-генерации; откладывается — подключение возможно по критерию пересмотра при росте корпуса |

## Последствия

**Положительные:**

- Один язык — минимальный и консистентный контекст для ИИ-генерации; проще проверка (типы, детектор гонок), ревью и поддержка.
- Нет FFI-границы в кодовой базе — меньше классов ошибок (память, сериализация, ABI), меньше сценариев отказа при ИИ-генерации.
- Единый тулчейн: сборка, CI, тесты, статический анализ — одна цепочка; деплой — статический бинарник без внешнего рантайма.
- Python-прототип не нужен: методы валидируются контрактными тестами и бенчмарками на Go-реализациях с первого дня.

**Отрицательные и смягчение:**

1. **Производительность CPU-алгоритмов ниже нативных реализаций (Rust/C).** Смягчение: CGo-биндинги к зрелым C-библиотекам (Leiden/HNSW), оптимизация по профилированию; критерий пересмотра — рост корпуса (Фаза 2/3).
2. **CGo (если понадобится) усложняет кросс-сборку и линковку.** Смягчение: минимизировать число CGo-зависимостей, изолировать их за тонким интерфейсом, контрактные тесты на границе.
3. **Go-экосистема графовых/LLM-реализаций беднее Python-экосистемы.** Смягчение: реализация методов по референсным материалам; эталонные кейсы (K1, K4, K5, K17) фиксируются контрактными тестами до реализации.
4. **Риск «переписывания» при появлении зрелых методов в Python-first экосистеме.** Смягчение: контрактные тесты и golden dataset отчуждают поведение от конкретной реализации; целевые метрики фиксируются до реализации (точность ответов RAG — не ниже 70%, время ответа).

**Критерии пересмотра:**

- Масштаб корпуса 100k+ и профилирование показывают, что Go/CGo-реализации CPU-компонентов — узкое место → вернуться к вопросу нативных компонентов (Rust через FFI), сохранив Go для оркестрации.
- Появление зрелых нативных реализаций CPU-алгоритмов с поддерживаемыми биндингами для Go.

**Открытые вопросы (вне этого ADR):**

- Конкретные Go-библиотеки и C-библиотеки для Leiden/HNSW/токенизатора — фиксируются при реализации.
- Схема линковки CGo (статическая vs динамическая) — при проектировании контура деплоя.
