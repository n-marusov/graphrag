# ADR-DES.API.api-gateway-adoption — API Gateway: единая HTTP-точка входа для людей (UI/прямой API)

- **Статус:** ПРИНЯТО
- **Дата:** 2026-08-29
- **Требование-источник:** [`specs/vision.md`](../../specs/vision.md) §2.5 (F1–F4, сквозные требования), §3.3 (контекст системы), §2.8 (внешние зависимости), [`specs/nonfun-req/REQ-NFR-api.performance.query-responsiveness.md`](../../specs/nonfun-req/REQ-NFR-api.performance.query-responsiveness.md), [`specs/nonfun-req/REQ-NFR-api.performance.agent-traffic-isolation.md`](../../specs/nonfun-req/REQ-NFR-api.performance.agent-traffic-isolation.md), [`specs/nonfun-req/REQ-NFR-api.observability.agent-audit.md`](../../specs/nonfun-req/REQ-NFR-api.observability.agent-audit.md), [`specs/adr/ADR-DES.API.agent-gateway-scheduling-layer.md`](ADR-DES.API.agent-gateway-scheduling-layer.md) (агентская граница), [`specs/adr/ADR-IMPL.STACK.go-single-language-adoption.md`](ADR-IMPL.STACK.go-single-language-adoption.md) (Go-only), [`specs/adr/ADR-DES.API.hybrid-graphrag-composition.md`](ADR-DES.API.hybrid-graphrag-composition.md) (заменяемость компонентов по контрактным тестам)

## Контекст

GraphRAG имеет два класса внешних потребителей:

1. **Люди** — команда разработки и эксплуатация: вопросы и ответы, статусы индексации, метрики, отчёты о влиянии. Работают через веб-интерфейс (приложение в браузере) и прямой API; трафик — HTTP(S).
2. **ИИ-агенты автоматизации разработки** — программные потребители: `answer` / `compile_context` через MCP. Агентский трафик уже изолируется отдельной границей — Agent Gateway и слоем планирования ([ADR-DES.API.agent-gateway-scheduling-layer](ADR-DES.API.agent-gateway-scheduling-layer.md)).

Веб-интерфейс становится **приложением в браузере (SPA)**: клиент не может обращаться к внутренним сервисам напрямую — нужна единая HTTP-точка входа с фиксированным внешним контрактом.

Без единой точки входа каждый внутренний сервис (Query Engine, Ядро, Оркестрация) вынужден публиковать HTTP API наружу, что приводит к:

- дублированию аутентификации/авторизации, rate limiting, квот и аудита в каждом сервисе;
- превращению внутренних контрактов во внешние — потеря свободы замены компонентов (принцип заменяемости, [ADR-DES.API.hybrid-graphrag-composition](ADR-DES.API.hybrid-graphrag-composition.md));
- отсутствию единой точки TLS-терминации и централизованного управления политиками;
- риску для отзывчивости интерактивного пути (NFR query-responsiveness) и изоляции нагрузок (NFR agent-traffic-isolation).

Требования к решению: единая политика доступа (authN/authZ), маршрутизация, защита внутренних сервисов, наблюдаемость (сквозной trace-id, аудит), rate limiting/квоты, TLS; self-hosted в периметре (NFR-SEC-1); серверная часть — Go ([ADR-IMPL.STACK.go-single-language-adoption](ADR-IMPL.STACK.go-single-language-adoption.md)).

## Решение

Принять **API Gateway** как отдельный контейнер — единую точку входа для всего HTTP-трафика к GraphRAG (UI в браузере, прямой API, инструменты эксплуатации). Внутренние сервисы (Query Engine, Ядро, Оркестрация) не публикуются наружу напрямую.

1. **Границы каналов.** Люди/UI — HTTP(S) через API Gateway. ИИ-агенты — MCP через MCP-сервер (Agent Gateway внутри, по [ADR-DES.API.agent-gateway-scheduling-layer](ADR-DES.API.agent-gateway-scheduling-layer.md)); API Gateway не обслуживает MCP-протокол. Разделение — по протоколу и классу нагрузки.
2. **Функции гейтвея.** Аутентификация и авторизация, TLS-терминация, маршрутизация (в т.ч. `/` → статик-сервер, `/api/*` → внутренние сервисы), rate limiting и квоты, единый сквозной trace-id и журнал аудита обращений; при необходимости — кэширование ответов.
3. **Тонкий гейтвей.** Только политики, безопасность и маршрутизация; без доменной логики, без дублирования retrieval/индексации/компиляции (по аналогии с agent-gateway ADR).
4. **Технология.** Go (минимум зависимостей) — в рамках [ADR-IMPL.STACK.go-single-language-adoption](ADR-IMPL.STACK.go-single-language-adoption.md).
5. **UI — приложение в браузере.** Тонкий SPA (TS/JS): рендеринг и вызовы API. Уточнение границы Go-only: правило «вся кодовая база — Go» относится к серверным компонентам; клиентский слой в браузере — вне серверной кодовой базы (зафиксировано данным ADR).
6. **Раздача статики — отдельный тонкий Go-статик-сервер за API Gateway (промышленный стандарт).** API Gateway — единый origin: маршрутизирует `/` → статик-сервер, `/api/*` → внутренние сервисы. Статик-сервер (Go) раздаёт hashed-ассеты с `Cache-Control: public, max-age=31536000, immutable`, `index.html` — `no-cache`, SPA-fallback на `index.html`, сжатие (gzip/brotli); файлы публикуются независимым деплоем фронта. Отделение слоя даёт независимый жизненный цикл фронта и зрелое кэширование без нагрузки на гейтвей.

Правила границы:

- Все внешние HTTP-запросы — через API Gateway; внутренние сервисы без прямого внешнего доступа.
- Статика и API — за единым origin (API Gateway); раздача статики — отдельный слой, не в процессе гейтвея.
- Агентский трафик — только через MCP-сервер (не через API Gateway).
- Гейтвей тонкий: без доменной логики и без дублирования функциональности внутренних сервисов.
- Сквозной trace-id и аудит обращений, включая события безопасности.
- UI — тонкий клиент без бизнес-логики.

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Прямой доступ внешних клиентов к внутренним API** | Каждый внутренний сервис публикует HTTP API наружу | Дублирование authN/authZ, rate limiting, квот и аудита; внутренние контракты становятся внешними (теряется заменяемость компонентов); нет единой точки TLS и управления политиками; риск для отзывчивости и изоляции нагрузок |
| **Middleware-«гейтвей» в каждом сервисе** | Общий набор middleware встраивается в каждый сервис | Политики пересобираются в N сервисах; изменения требуют передеплоя всех; нет единой точки маршрутизации/TLS; сложнее единый аудит и trace-id |
| **Внешний управляемый шлюз** (Kong, Traefik, облачный API Gateway) | Готовый шлюз, self-hosted или облачный | Облачные варианты нарушают NFR-SEC-1 (данные и политики не покидают периметр); self-hosted-шлюзы добавляют внешний рантайм и операционку без преимуществ для MVP; Go-only |
| **MCP-сервер как единственная точка входа (включая людей)** | Все потребители — через MCP | MCP — протокол для ИИ-агентов; люди/UI работают по HTTP(S); смешение протоколов и политик; UI-сценарии не покрываются |
| **Один универсальный гейтвей для HTTP и MCP** | Единый контейнер обслуживает и людей, и агентов | Требования изоляции агентских нагрузок (квоты, бюджеты, режимы исполнения, планирование) уже зафиксированы в [ADR-DES.API.agent-gateway-scheduling-layer](ADR-DES.API.agent-gateway-scheduling-layer.md); смешение увеличивает сложность гейтвея и риск для интерактивного пути. Сохраняется разделение: API Gateway (HTTP, люди) + MCP-сервер с Agent Gateway (MCP, агенты) |

### Раздача статики SPA — рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Статика в гейтвее (go:embed)** | SPA встроена в бинарник API Gateway | Связывает деплой фронта с гейтвеем; кэш-заголовки и SPA-fallback — в коде гейтвея (гейтвей несёт контент); допустимо только как временный компромисс MVP — отклонено в пользу целевой архитектуры |
| **Прокси впереди (nginx/Caddy/CDN)** | Внешний слой раздаёт статику и проксирует `/api/*` на гейтвей | Канон для внешних продуктов, но меняет границу «API Gateway — единая точка входа» (внешний контракт — прокси); отложено до потребности в централизованной TLS/прокси-точке для нескольких сервисов |
| **Внешний хостинг/CDN** | Статика из облака/внешнего хранилища | Вне периметра (NFR-SEC-1); CORS; избыточно для внутреннего инструмента |
| **Caddy как статик-слой** | Готовый Go-бинарник (статика + кэш) | Допустимая альтернатива; решение — свой тонкий Go-сервер (Go-only кодовая база, ИИ-генерация, контрактные тесты); Caddy — запасной вариант при потребности «не писать своё» |

## Последствия

**Положительные:**

- Единая точка управления доступом и политиками: authN/authZ, rate limiting, квоты, аудит в одном месте.
- Внутренние сервисы изолированы от внешнего мира; внутренние контракты не становятся публичными — сохраняется заменяемость компонентов (hybrid ADR).
- Стабильный внешний контракт для UI (браузерного приложения), не зависящий от внутренней композиции.
- Наблюдаемость: сквозной trace-id, единый журнал аудита (включая события безопасности).
- Раздача статики отделена: независимый деплой фронта, immutable-кэш hashed-ассетов, гейтвей не несёт контент.
- Отзывчивость интерактивного пути: тонкий гейтвей, кэшируемые политики, быстрый путь.
- Go-only для серверной части сохраняется.

**Отрицательные и смягчение:**

1. **Дополнительные контейнеры и hop.** Смягчение: тонкий гейтвей (только политики и маршрутизация), локальный кэш политик, минимальная дополнительная задержка; Web-сервер статики — тонкий Go-сервис на стандартных хендлерах, раздача из каталога без пересборки; контрактные тесты на кэш-заголовках и SPA-fallback.
2. **Пересечение с Agent Gateway (MCP-сервер).** Смягчение: явное разделение каналов (HTTP — люди, MCP — агенты); общие библиотеки политик (auth, аудит) выносятся в общий код, но границы контейнеров раздельны.
3. **UI (TS/JS) — клиентский код вне Go-only.** Смягчение: тонкий клиент, раздача статики — Go; граница ADR языка уточняется при принятии (серверная кодовая база — Go).
4. **Риск «толстого» гейтвея.** Смягчение: правило тонкого гейтвея, код-ревью, контрактные тесты на маршрутизации и политиках.

**Критерии пересмотра:**

- Если агентские нагрузки станут доминирующими и потребуют общего планировщика с людским трафиком — пересмотреть объединение API Gateway и Agent Gateway.
- Если появится мультиарендная эксплуатация — усилить изоляцию квот и аудита в гейтвее.
- Если появится зрелое Go-решение или подтверждённая необходимость внешнего шлюза в периметре — пересмотр.

**Открытые вопросы (вне этого ADR):**

- Конкретные Go-библиотеки гейтвея (маршрутизация, auth) — при реализации.
- Формат политик (rate limits, квоты) и интеграция с корпоративным SSO — при реализации.
- Схема версионирования ассетов фронта (hash-имена) — при реализации фронта.
