# Архитектурные решения (ADR) — GraphRAG

В этой директории хранятся записи архитектурных решений (Architecture Decision Records) проекта **GraphRAG** — корпоративной системы знаний на базе ontology-grounded GraphRAG: evidence-based context layer / context compiler для ИИ-агентов автоматизации разработки (AI Factory, Hand-off). Система индексирует корпоративный корпус (markdown-спеки GitLab, книги и легаси из внешнего S3-хранилища) в граф знаний с онтологическим слоем (машинно-читаемая модель предметной области), отвечает на вопросы команды проверяемыми ответами со ссылками на источники и собирает точный контекст для ИИ-агентов — вместо сырого текста и ручных переспросов.

> **Статус:** проект находится на этапе видения; приняты три ADR: язык реализации — Go как единый язык (ПРИНЯТО), тип GraphRAG — гибридная ontology-grounded композиция методов (ПРИНЯТО) и источник книг/легаси — внешнее S3-хранилище (ПРИНЯТО, см. «Реестр ADR»). На уровне требований зафиксировано: функции F1–F4 (канон, §2.1–2.2), состав MVP и roadmap — `specs/vision.md` (§2.5, §2.6); ограничения и исключения — §2.7; предположения и зависимости — §2.8; основные события предметной области — §2.4; контекст системы — §3.3. Принятые на этапе исследования проектные решения (тип hybrid ontology-grounded GraphRAG, онтологический слой на модели предметной области, локальный контур LLM) зафиксированы в `.ai-factory/RESEARCH.md` (Decisions); тип GraphRAG и комбинация методов перенесены в ADR (см. «Реестр ADR»), остальные подлежат переносу при переходе к проектированию. Подлежат дальнейшей фиксации в ADR: онтологический слой как машинно-читаемая модель предметной области (онтология), хранилище графа и векторного индекса, модель обновления (инкрементальная + периодическая перестройка), контур LLM (локальные GPU, open-weight модели), MCP-интерфейс для агентов, масштаб корпуса (открытый вопрос 1k vs 100k; глобальный слой книг — сотни, зафиксировано в ADR-IMPL.INTEGRATION.s3-document-store).

## Правила именования файлов

Файлы именуются по шаблону `<ADR-ID>.md`, где `ADR-ID` — уникальный идентификатор решения.

**Формат идентификатора:**
```
ADR-<LEVEL>.<AREA>.<semantic-tag>
```

Где:
- `LEVEL` = `BIZ` | `DES` | `IMPL`
- `AREA` = `API` | `DATA` | `INFRA` | `SECURITY` | `UI` | `PROCESS` | `INTEGRATION` | `STACK` | `OPS` | `DOC`
- `semantic-tag` — короткая англоязычная метка в kebab-case (2–5 слов), отражающая суть выбора

## Структура ADR

Каждый ADR должен содержать следующие обязательные поля:

- **Статус:** `[ЧЕРНОВИК | ПРЕДЛОЖЕНО | ПРИНЯТО | УСТАРЕЛО | ЗАМЕНЕНО]`
- **Дата:** `ГГГГ-ММ-ДД`
- **Контекст:** описание контекста проблемы
- **Требование-источник:** ссылки на файлы или ID требований
- **Решение:** краткое описание выбора (должно соответствовать semantic-tag)
- **Рассмотренные альтернативы:** перечисление рассмотренных вариантов (если применимо)
- **Последствия:** положительные и отрицательные последствия + способы смягчения

## Паттерны semantic-tag

| Паттерн | Описание | Пример |
|---------|----------|--------|
| `-vs-` / `-vs-...-vs-` | Выбор между альтернативами | `postgres-vs-mysql` |
| `-or-` | Равнозначные варианты | `redis-or-memcached` |
| `-tradeoff` | Компромисс между качествами | `latency-vs-consistency-tradeoff` |
| `-adoption` | Внедрение технологии без альтернатив | `kubernetes-adoption` |
| `-mandate` | Вынужденное решение | `gdpr-mandate` |
| `-strategy` / `-approach` / `-pattern` | Выбор подхода | `cache-strategy`, `saga-pattern` |
| `-evolution` / `-migration` | Изменение существующего | `microservices-evolution` |
| `-scope` / `-boundary` | Определение границ | `context-boundary` |

## Правила

1. **Уникальность ID** — каждый ADR-ID должен быть уникальным в рамках проекта
2. **LEVEL соответствует типу решения:** `BIZ` — бизнес-решения, `DES` — проектные, `IMPL` — реализационные
3. **Максимальная длина semantic-tag** — 40 символов
4. **Запрещены пробелы** в ID, только дефисы и точки
5. **Перед созданием нового ADR** проверьте существующие на пересечение темы
6. **Изменения принятых ADR** оформляются через обновление статуса (заменено/устарело) и создание нового ADR

## Специфика проекта

- **Роль продукта — evidence-based context layer, а не поиск.** GraphRAG — корпоративная система знаний: ответы подтверждены источниками и происхождением (grounding, provenance), а не «сырым» текстом. Два режима: (1) проверяемые ответы команде со ссылками на источники; (2) контекстный режим для ИИ-агентов — context compiler через MCP (точный набор артефактов под задачу). ADR не должны описывать «поисковую» систему: продукт отвечает, а не выдаёт документы.
- **Функции F1–F4 (канон vision.md §2.1–2.2).** Генерация проверяемых ответов (F1), индексация источников знаний (F2), оптимизация контекста для автоматической разработки (F3), доставка ответов и контекста через MCP (F4). Механизмы (не функции): онтологический слой — модель предметной области (внутри F1/F3), безопасный контур LLM (сквозное требование REQ-NFR-security.compliance.llm-contour). Накопление знаний и петля обучения — вне рамок (vision.md §2.7 п.4–5). Состав MVP и roadmap — `specs/vision.md` §2.5–2.6.
- **Источники знаний.** Authoritative-источник — markdown-спеки в репозитории спецификаций (GitLab, изменения через MR); книги и легаси — из внешнего S3-хранилища (глобальный контекст, отдельный граф; формат PDF — RAPTOR/StructRAG; триггеры — события + периодическая сверка, [ADR-IMPL.INTEGRATION.s3-document-store](ADR-IMPL.INTEGRATION.s3-document-store.md)); Confluence исключён. ADR, затрагивающие индексацию, фиксируют модель источника и триггеры обновления.
- **Языки реализации.** Go — по умолчанию (ядро, оркестрация I/O-bound, goroutines); Rust — только in-process CPU-тяжёлые компоненты (Leiden/HNSW/токенизатор) или FFI; прототип — Python (экосистема LLM/graph). ADR уровня `IMPL` (технологии, хранилище, тестирование) должны учитывать это разделение.
- **Тип GraphRAG — hybrid ontology-grounded.** Комбинация методов зафиксирована в [ADR-DES.API.hybrid-graphrag-composition](ADR-DES.API.hybrid-graphrag-composition.md): ядро — LightRAG (dual-level retrieval, инкрементальное обновление); точность/непротиворечивость — KAG-принципы (mutual indexing KG↔chunks, grounding, атрибуция источников); компактный контекст — PathRAG (pruned paths, без map-reduce) — критично для локальных GPU и MCP; PDF — RAPTOR (нарратив) + StructRAG (таблицы/формы); ассоциативные запросы — PPR (HippoRAG-стиль, без LLM на этапе извлечения); обзоры — community summaries (уровни C0–C1); real-time — Graphiti (Фаза 3). ADR уровня `IMPL` фиксируют конкретные реализации и границы компонентов.
- **Онтологический слой.** Машинно-читаемая модель предметной области (онтология) — основа резолвинга запросов и минимизации контекста; исходная модель поставляется из репозитория модели, автоматическое построение онтологии (ontology learning) — Фаза 3.
- **Контур LLM.** Исполнение open-weight моделей на локальных GPU — основной вариант; внешние провайдеры — только через корпоративный шлюз с фильтрацией утечек и аудитом; данные разработки (код, спеки, ПДн) не покидают периметр. Минимизация токенов и числа LLM-вызовов — сквозное требование (онтологический слой, PathRAG, PPR). ADR уровня `SECURITY` фиксируют модель контура и измеримые метрики (точность ответов RAG — не ниже 70%, доля обращений через корпоративный канал, покрытие аудитом).
- **Принцип «агент готовит — человек подтверждает и отвечает».** Ответы и артефакты, сгенерированные LLM, подтверждаются человеком. GraphRAG — субстрат инициатив I4 (знания), I6 (трассируемость) и I9 (петля обучения). ADR уровня `PROCESS` фиксируют, как решения учитывают этот принцип.
- **Границы проекта.** GraphRAG не является источником правды (единый источник — репозиторий спецификаций); не чат-бот и не поисковая строка; не заменяет управленческие решения; fine-tuning моделей — вне рамок; автоматический анализ инцидентов — вне рамок; real-time обновление графа — вне MVP; масштаб корпуса ограничен возможностями локального контура (рост — Фаза 2/3). ADR не должны размывать эти границы (полный список — `specs/vision.md` §2.7).
