# ADR-DES.STACK.src-directory-structure — Структура каталога `src/`: фронтенд и бэкенд как отдельные корни

| Поле | Значение |
|------|----------|
| **Статус** | ПРИНЯТО |
| **Дата** | 2026-08-31 |
| **Контекст** | `src/` — корень продуктивной кодовой базы GraphRAG (`src/README.md`): фронтенд реализован (`src/frontend/`, Vue 3 SPA), серверная кодовая база (Go) — план. Декомпозиция уровня 2 C4 зафиксирована в `ADR-DES.INFRA.container-composition` (10 контейнеров: 8 Go-компонентов, UI в браузере, Neo4j). Язык серверной части — Go, единый (`ADR-IMPL.STACK.go-single-language-adoption`); фронтенд — TypeScript, вне серверной кодовой базы (`ADR-DES.UI.spa-typescript-frontend`). Если сделать `src/` одновременно корнем всей кодовой базы и корнем Go-модуля, верхний уровень начнёт смешивать frontend, backend, точки входа Go и общие пакеты. Для ИИ-агентов и spec-driven разработки нужна структура, где границы frontend/backend и C4-контейнеров видны из пути. |
| **Требование-источник** | `ADR-DES.INFRA.container-composition` (декомпозиция 10 контейнеров; общие библиотеки политик auth/аудит/квоты); `ADR-IMPL.STACK.go-single-language-adoption` (Go — единый язык, CGo для CPU-компонентов); `ADR-DES.UI.spa-typescript-frontend` (фронтенд вне серверной кодовой базы); `src/README.md` (карта кодовой базы); `.ai-factory/RULES.md` (трассируемость, README на русском) |

## Решение

Каталог `src/` — **umbrella-каталог продуктивной кодовой базы**, а не корень Go-модуля. Внутри него явно разделяются два корня:

- `src/frontend/` — TypeScript/Vue SPA, вне серверной кодовой базы;
- `src/backend/` — единый Go-модуль серверной кодовой базы.

Границы C4-контейнеров фиксируются внутри backend: точки входа — в `src/backend/cmd/<service>/`, реализация — в `src/backend/internal/<component>/`.

**Целевая структура `src/`:**

```
src/
├── README.md                  # карта кодовой базы (на русском)
├── frontend/                  # веб-интерфейс (SPA, TS/Vue 3) — реализован
│   └── src/
│       ├── domain/            # сущности, VO, порты (чистый TS, без Vue)
│       ├── application/       # use cases, машина состояний
│       ├── adapters/          # реализации портов (api/, mappers/, state/, i18n/)
│       ├── ui/                # презентационные компоненты (dumb)
│       ├── app/               # composition root (bootstrap, router)
│       └── assets/            # токены (@theme), шрифты, иконки
└── backend/                   # серверная кодовая база (Go) — план
    ├── README.md              # карта backend и правила для агентов
    ├── go.mod / go.sum        # единый Go-модуль серверной части
    ├── cmd/                   # точки входа сервисов (бинарники)
    │   ├── api-gateway/main.go
    │   ├── web-server/main.go
    │   ├── mcp-server/main.go
    │   ├── core/main.go
    │   ├── query-engine/main.go
    │   ├── orchestration/main.go
    │   └── monitoring/main.go
    └── internal/              # реализация (закрыта для внешних модулей)
        ├── core/              #   Ядро (F3): граф знаний, онтология, компилятор контекста
        ├── queryengine/       #   Движок запросов (F1): retrieval, grounding/provenance
        ├── orchestration/     #   Оркестрация пайплайнов (F2)
        ├── mcpserver/         #   MCP-сервер (F4) + Agent Gateway
        ├── apigateway/        #   API Gateway
        ├── webserver/         #   статик-сервер (раздача SPA)
        ├── monitoring/        #   мониторинг и аудит
        ├── integrations/      #   GitLab/S3/LLM-клиенты, CPU-компоненты (CGo)
        └── ...                #   общие библиотеки политик (auth, audit, quotas)
```

**Правила:**

1. **`src/` не является Go-модулем.** Это общий каталог продуктивной кодовой базы. Серверный Go-модуль начинается в `src/backend/`; фронтенд остаётся в `src/frontend/`.
2. **Граница backend-компонентов = граница контейнеров C4.** Внутри `src/backend/` папки `cmd/<service>/` и `internal/<component>/` соответствуют контейнерам из `ADR-DES.INFRA.container-composition` — трассируемость «папка → контейнер → функция F1–F4 → US/UC».
3. **Серверная кодовая база — единый Go-модуль** (один `go.mod` в `src/backend/`). Точки входа — `cmd/<service>/main.go` (по сервису), реализация — `internal/<component>/`; общий код (политики auth/audit/квоты, общие типы контрактов) — пакеты в `internal/`, доступные всем компонентам backend-модуля.
4. **Фронтенд — вне Go-модуля.** `src/frontend/` — независимая папка с собственным `package.json`; внутренняя структура — слоистая (Clean Architecture, зависимости направлены внутрь; детали — `src/frontend/README.md` §«Архитектура»): `domain/`, `application/`, `adapters/`, `ui/`, `app/`, `assets/`.
5. **Развёртывание — вне `src/`.** Docker Compose и конфигурация развёртывания MVP — в `deploy/` (корень репозитория), а не в `src/` (`ADR-DES.INFRA.container-composition`: «состав compose-сервисов — при реализации, в `deploy/`»).
6. **README на русском** в каждой папке верхнего уровня `src/` и `src/backend/` (назначение папки, правила для ИИ-агентов); трассируемость требований — в заголовочных комментариях файлов (`RULES.md`).
7. **Что не входит в `src/`:** спецификации — `specs/`; конфигурация и планы — `.ai-factory/`; агентские скиллы — `.agents/skills/` (зафиксировано в `src/README.md`).

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Go-модуль в корне `src/`** | `src/go.mod`, `src/cmd/`, `src/internal/` рядом с `src/frontend/` | `src/` становится одновременно общим каталогом кодовой базы и корнем backend-модуля; верхний уровень смешивает frontend, backend и Go-детали. Для агентов менее очевидно, где заканчивается серверная часть. |
| **Папка на контейнер с отдельным `go.mod`** | 8 Go-модулей (`src/backend/core/`, `src/backend/query-engine/`, …) + общий `shared/` | Дублирование общих библиотек политик (auth, аудит, квоты нужны и API Gateway, и MCP-серверу — `container-composition`); сложнее версионирование и ИИ-генерация кода; для MVP изоляция версий не требуется. Критерий пересмотра — выделение модулей через `go.work`. |
| **Монолит «всё в одном процессе»** | Один бинарник со всеми сервисами | Отклонено в `ADR-DES.INFRA.container-composition`; здесь — следствие: даже при едином модуле точки входа разделены (`cmd/`), сервисы собираются отдельными бинарниками. |
| **Структура по техническим слоям без привязки к контейнерам** | `internal/handlers/`, `internal/services/`, `internal/repos/` | Теряется трассируемость «папка → контейнер → функция F1–F4» и границы владения функциями (Ядро vs Движок запросов; `container-composition`, последствия п.2). |
| **Фронтенд внутри Go-модуля** | SPA как часть `src/` Go-модуля | Отклонено в `ADR-DES.UI.spa-typescript-frontend` (фронтенд — вне серверной кодовой базы, независимый жизненный цикл). |

## Последствия

**Положительные:**

- Явная граница `src/frontend/` / `src/backend/` снижает когнитивную нагрузку: `src/` остаётся картой кодовой базы, а Go-детали не смешиваются с frontend на верхнем уровне.
- Трассируемость «папка → контейнер → функция F1–F4 → US/UC»: карта backend совпадает с картой системы (C4) и реестром функций (`vision.md` §2.1–2.2).
- Единый Go-модуль внутри `src/backend/` упрощает ИИ-генерацию кода (одни конвенции, один набор зависимостей) и размещение общих библиотек политик (auth, аудит, квоты) — прямое требование `container-composition`.
- Предсказуемость для агентов: README на русском, трассируемость в заголовках, имена папок backend-компонентов по контейнерам.

**Отрицательные и смягчение:**

1. **Дополнительный уровень вложенности** (`src/backend/cmd/...` вместо `src/cmd/...`). Смягчение: выигрыш в явности границы frontend/backend важнее одного уровня пути; команды сборки и CI работают из `src/backend/`.
2. **Риск размывания границ сервисов внутри одного backend-модуля** (нет жёсткой изоляции компиляции). Смягчение: раздельные точки входа `cmd/`, контрактные тесты на внутренние интерфейсы (K1, K4, K5, K17 — `RULES.md`); критерий пересмотра — выделение модулей через `go.work`.
3. **Два тулчейна в одном репозитории** (Go, Node). Смягчение: раздельные корни `src/backend/` и `src/frontend/`, раздельные сборки в CI — уже зафиксировано в `ADR-DES.UI.spa-typescript-frontend`.
4. **Имена Go-пакетов расходятся с kebab-case папок** (`queryengine` vs `query-engine`). Смягчение: конвенция — папки Go-пакетов в lowercase без разделителей; kebab-case — только для `cmd/<service>` и не-Go папок.

**Критерии пересмотра:**

- Рост серверной кодовой базы / потребность в независимом версионировании компонентов → разделение `src/backend/` на отдельные Go-модули через `go.work` (без смены внешней границы `src/backend/`).
- Появление реального кода: структура актуализируется до `as-is`; расхождения с данным ADR — через новый ADR (статус «ЗАМЕНЕНО»).
