# ADR-DES.SECURITY.sso-keycloak — Доступ людей через корпоративный SSO (Keycloak), агенты — по токену

| Поле | Значение |
|------|----------|
| **Статус** | ПРИНЯТО |
| **Дата** | 2026-08-30 |
| **Контекст** | GraphRAG имеет два класса внешних потребителей: люди (UI/API через API Gateway, `ADR-DES.API.api-gateway-adoption`) и ИИ-агенты автоматизации разработки (MCP через MCP-сервер/Agent Gateway, `ADR-DES.API.agent-gateway-scheduling-layer`). Агенты могут обращаться и через человеческий шлюз (API Gateway), поэтому аутентификация людей необходима уже в MVP. Прежнее правило `BR-constraint.no-user-auth-in-mvp` (авторизация отсутствует в MVP) заменено решением владельца продукта 2026-08-30. |
| **Требование-источник** | BR-constraint.sso-readonly-access; REQ-NFR-security.compliance.llm-contour (граница: фильтрация утечек, события безопасности); ADR-DES.API.api-gateway-adoption; ADR-DES.API.agent-gateway-scheduling-layer; UC-mcp.compile.context (аутентификация агентов, A1 «Нет прав / истёк токен») |

## Решение

- **Аутентификация людей** — через **корпоративный SSO (Keycloak)**, self-hosted в доверенном периметре организации (существующий корпоративный инстанс; подключается как OIDC-провайдер). API Gateway выполняет проверку токена (OIDC) и пропускает запросы только с валидным токеном.
- **ИИ-агенты** — по **токену** (агентский токен, выдаётся через корпоративный процесс) на MCP-канале; MCP-сервер (Agent Gateway) проверяет токен и политики (квоты, бюджеты — `ADR-DES.API.agent-gateway-scheduling-layer`).
- **Один пользователь по умолчанию** (`User`); **ролей нет** (RBAC не вводится — см. `BR-constraint.sso-readonly-access`).
- **Запросы — только на чтение** (read-only): никаких write-операций через API/UI/MCP (граница `BR-constraint.sso-readonly-access`).
- MFA — на стороне корпоративного Keycloak (корпоративная политика), не внутри GraphRAG.

Правила границы:

- GraphRAG не хранит пароли и не реализует собственный authN; только проверка токенов (OIDC) и агентских токенов.
- Данные идентификации (логин/личность SSO) не покидают периметр; обработка — минимальна, по корпоративной политике (см. решение по ПДн, vision.md §2.7).
- Аудит: кто обратился (человек/агент), когда, с каким результатом — в журнале аудита API Gateway/MCP (сквозной trace-id).

## Рассмотренные альтернативы

| Альтернатива | Описание | Причины отклонения |
|---|---|---|
| **Отсутствие авторизации в MVP** (прежнее правило) | Доступ без учётных записей | Агенты могут идти через человеческий шлюз; без authN нельзя отличить агента от человека; решение владельца 2026-08-30 |
| **Внешний IdP / облачный SSO** | Аутентификация через внешний облачный провайдер | Нарушает периметр (данные и политики не покидают организацию, NFR-SEC-1) |
| **Самописная авторизация (свои логины/пароли)** | Собственная модель учётных записей | Неоправданная стоимость и поверхность атаки; корпоративный Keycloak уже существует; дублирование SSO |
| **Полноценный RBAC** | Роли и права доступа в MVP | Не требуется: один пользователь, read-only; роли — будущие версии (появляются с write-операциями/администрированием) |

## Последствия

**Положительные:**
- Единый корпоративный процесс аутентификации (SSO, MFA, блокировки) без собственной реализации.
- Явная граница «человек ≠ агент» на общем шлюзе; аудит кто-что-когда.
- Read-only-граница снижает поверхность атаки и объём тестирования безопасности в MVP.

**Отрицательные и смягчение:**
1. **Зависимость от доступности Keycloak** на пути аутентификации. Смягчение: кэширование проверенных токенов (короткий TTL), понятная ошибка при недоступности SSO, деградация — только для аутентифицированных сессий; read-only контур допускает консервативный отказ.
2. **Идентификационные данные = ПДн** (логин SSO). Смягчение: минимальная обработка, без хранения профилей; решение по ПДн (vision.md §2.7): система не оператор ПДн, идентификация — по корпоративной политике; фильтрация утечек блокирует ПДн.
3. **Два класса токенов** (OIDC людей, агентские) — два пути проверки. Смягчение: общая библиотека проверки токенов, контрактные тесты на оба пути (E2E API/GUI).

**Критерии пересмотра:**
- Появление write-операций или административных функций → ввод RBAC (роли) и пересмотр BR.
- Переход на другой корпоративный IdP → замена OIDC-конфигурации без изменения архитектуры.
